# ТЗ для дизайнера: страницы Kaizen и TOC Sentinel

Статус: черновик для обсуждения с оператором, ничего не реализовано. Готовится как материал перед
передачей дизайнеру — цель этого документа не "вот финальный макет", а "вот что реально нужно
показать и почему", чтобы дизайнер не изобретал контент с нуля.

## 1. Задача и границы

Две страницы дашборда EneikProductionSys — **Six Sigma & Kaizen** (`SixSigmaKaizenPanel.svelte`) и
**TOC Sentinel** (`TocSentinelView.svelte`) — сейчас нечитаемы для нетехнического оператора. Дерево
эпиков (`ProductTree.svelte`, "Verdant Flow") — единственная страница, которая оператору нравится и
понятна; её не трогаем, но её визуальный язык — прямой референс для того, что должно получиться здесь.

Явно вне охвата этой задачи:
- Любые изменения бэкенда/данных — ничего в API не меняется, только то, как существующие реальные
  данные показаны.
- Дерево эпиков (`ProductTree.svelte`) — не трогаем.
- Финальная реализация — сначала брифуем дизайнера, реализация отдельным шагом.

## 2. Существующая система дизайна — и почему она тут не подходит

В репозитории уже есть `docs/DESIGN_SYSTEM.md` — обязательная ("Obligatory") палитра/типографика для
"любого нового UI": синий primary `#1D4ED8`, нейтральная slate-шкала, светлый фон `#F5F7FB`,
универсальный "профессиональный B2B SaaS" вид. Именно этот безликий B2B-стиль (в тёмном варианте,
слегка отклонившись от документа) и лежит в основе текущих Kaizen/TOC страниц — отсюда и ощущение
"обычная админка с цифрами".

**Важно**: у самой системы уже есть узаконенный выход — раздел "brand exception" (уникальные
AI-визуализации, требует комментария `/* BRAND EXCEPTION: обоснование */` в коде). `ProductTree.svelte`
уже им воспользовался: тёплая кремово-шалфейно-золотая палитра "Verdant Flow" целиком вне этой
B2B-системы — и именно это оператору понравилось. `design_token_compliance`-проверка в
`DesignExcellenceGate.java` пока не реализована (только `responsive_ok`/`visual_qa_ok`), то есть
формального технического препятствия для второго brand exception нет.

**Рекомендация**: Kaizen и TOC получают свой собственный brand exception, не обязаны укладываться в
голубую B2B-палитру — так же, как дерево. Не обязательно тот же самый "Verdant Flow" (это специфичная
метафора для эпиков-как-роста), но той же смелости и той же идеи "перевести абстрактные данные в
узнаваемый образ", а не "покрасить таблицу в тёплые цвета".

## 3. Кто читатель

Нетехнический оператор/фаундер — не инженер, не знает, что такое DPMO, Z-score, Drum-Buffer-Rope,
$L_q$. Он уже один раз прямо сказал: "остальное обычному дилетантскому пользователю совершенно
непонятно". Дерево эпиков он понимает без объяснений — потому что это метафора (растёт дерево =
растёт продукт), а не термины теории массового обслуживания.

## 4. Диагноз: что именно сейчас не работает (дословные примеры из кода)

**Six Sigma & Kaizen страница:**
- Заголовки карточек: "Sigma Level (Z-score)", "DPMO (Defects Per Million)", "First Time Yield Rate" —
  три статистических термина подряд, ни один не объяснён.
- Таблица "Defect Opportunities Channel Breakdown" — колонки "Opportunities" / "Defects Recorded" /
  "Channel DPMO" без единого слова, что это значит для продукта.
- Карточки Kaizen-предложений показывают `category` как есть (`WASTE_REDUCTION`,
  `ROLE_QUALITY_DRIFT`...) и голые проценты (`Expected Gain: +0%` — экспектед-гейн почти всегда 0%,
  потому что предложения review-only, но это нигде не объяснено, выглядит как баг).

**TOC Sentinel страница:**
- Заголовок карточки: "Drum-Buffer-Rope Gate (The Rope)" — метафора Голдратта без единого слова
  объяснения, что это вообще такое.
- Таблица со столбцами буквально в LaTeX-нотации: "$L_q$", "$\mu$", "$\sigma$" — это заголовки таблицы
  в реальном интерфейсе, не техническая документация.
- "ROPE THROTTLING ACTIVE" / "NORMAL ADMISSIONS" — статус-бейдж без объяснения, что "throttling"
  вообще-то хорошая вещь (система сама защищает единственное узкое место).

## 5. Ключевая находка: человеческий текст уже есть в API — просто не в фокусе

Это самое важное для дизайнера. Не нужно с нуля придумывать, как объяснять происходящее словами —
бэкенд **уже** пишет обычные человеческие предложения, просто они сейчас мелким текстом под тремя
жаргонными карточками:

- `dbrStatus.recommendation` — реальный пример прямо сейчас: *"System flow optimal. Primary
  constraint: 'AUTOMERGE_PROCESSING'."*
- `anomaly.details` — реальный пример: *"Token 'tok-3487ae7e' stalled in node 'AUTOMERGE_PROCESSING'
  for 53990 ms. Dynamic Limit: 53467.05 ms."*
- `anomaly.actionTaken` — реальный пример: *"Flagged node 'AUTOMERGE_PROCESSING' as
  STALL_BOTTLENECK."*
- Kaizen `actionDescription` — реальный пример (`ROLE_QUALITY_DRIFT`): *"Role BARCAN-TAG-02's own
  defect-weight average rose from 0.04 (7 earlier tasks) to 0.21 (6 recent tasks) within this
  project's own history — a 483% increase, not a one-off failure."*

Последний пример особенно показателен: это уже почти готовая человеческая история ("у одного из
исполнителей качество работы резко просело — стоит проверить") — просто она сейчас похоронена в
одном ряду с "u=0.0303 outside [0.0000, 0.0000]".

**Направление для дизайна**: эти готовые предложения — герои страницы. Сырые числа (DPMO, σ, μ,
u-chart пределы) — подробности "для тех, кому интересно", по клику/разворачиванию, не то, что
человек видит первым.

## 6. Что реально стоит за Kaizen (инвентарь реальных данных)

Kaizen здесь — это цикл PDCA (Plan-Do-Check-Act): система сама ищет мелкие улучшения, пробует их,
честно проверяет результат (`baselineMetric` → `postMetric`), и либо закрепляет (`STANDARDIZED`),
либо откатывает (`REVERTED`) — то есть каждое улучшение эмпирически доказано, не просто заявлено.

| Категория (`category`) | Что это значит по-человечески | Реальный пример из этого проекта прямо сейчас |
|---|---|---|
| `WASTE_REDUCTION` | Устранение простоя/ожидания в очереди | — |
| `DEFECT_ELIMINATION` | Предотвращение повторяющихся сбоев проверки качества/конфликтов | — |
| `BUFFER_TUNING` | Подстройка "буфера" очереди (сколько работы держать в запасе перед узким местом) | — |
| `SYSTEMIC_DEFECT` | Системная проблема, видна по статистике (u-chart вышел из-под контроля) | *"u-chart out of control: reviewConcerns... Эпик's own quality target: Reduce the number of task status mismatches to 0"* |
| `ROLE_QUALITY_DRIFT` | У одной из ролей/исполнителей реально просело качество за последнее время | *"Role BARCAN-TAG-02's own defect-weight average rose from 0.04 to 0.21 — a 483% increase"* |
| `PRODUCT_RUNTIME_DEFECT` | Проблема не в процессе сборки, а в уже работающем продукте (новая ветка наблюдения) | — |

`status`: `PROPOSED` (найдено, ждёт) → `STANDARDIZED` (проверено, работает, закреплено) / `REVERTED`
(проверили, не помогло, откатили) — это единственное место, где реально видно "система училась и
не ошиблась дважды", стоит сделать заметным.

Дополнительный, честный контент: 15 именованных инженерных паттернов-первопричин в
`docs/ENGINEERING_INVARIANTS_CHARTER.md` (например "Compare-And-Swap вместо read-then-write",
"Поглощающие состояния конечного автомата") — если у находки есть `rootCausePatternId`, это реальная,
узнаваемая "форма" бага, не просто "что-то сломалось". Хорошая кандидатура на маленький тег/бейдж на
карточке, не для полного текста.

## 7. Что реально стоит за TOC (инвентарь реальных данных)

TOC (Theory of Constraints, Голдратт) здесь — это буквально "у конвейера есть одно самое узкое
место, вся скорость всего конвейера ограничена именно им". Прямо сейчас в реальной системе:

- Единственное узкое место — **`AUTOMERGE_PROCESSING`** (слияние готовой работы в основную ветку).
- Загружено на **67%**, средняя задержка **~40 секунд** на операцию.
- "Верёвка" (`ropeThrottlingActive`) сейчас **не натянута** — значит, новая работа не сдерживается
  специально, узкое место справляется.

| Поле API | Что это значит по-человечески |
|---|---|
| `primaryConstraintNode` | Название реального этапа конвейера, который сейчас самый медленный — "барабан", задаёт темп всему |
| `constraintUtilization` | Насколько занято это узкое место (0-100%) |
| `constraintMeanDurationMs` | Сколько в среднем занимает одна операция на этом этапе |
| `bufferSize` / `maxBufferCapacity` | Сколько работы скопилось перед узким местом ("буфер"), сколько влезает |
| `ropeThrottlingActive` | Система сама притормаживает приём новой работы, чтобы защитить узкое место от перегрузки — это забота, не поломка |
| `nodes[].stallBottleneck` | Этап временно завис дольше обычного (не то же самое, что "постоянное узкое место") |
| аномалии (`STALL_DETECTED`/`CYCLE_DETECTED`/`DEADLOCK_DETECTED`) | Реальные, разово обнаруженные и обработанные сбои — уже с готовым текстом объяснения и готовым текстом "что сделала система" |

Важно для дизайнера: узкое место **меняется во времени** (сегодня это слияние в git, завтра может
быть что-то другое) — не статическая подпись, реальный, живой факт про систему прямо сейчас.

## 8. Референс: что взять от дерева эпиков

`ProductTree.svelte` работает, потому что:
1. Метафора вместо таблицы — рост дерева считывается без объяснений.
2. Постоянных подписей на холсте нет — детали по hover, не загромождают картину.
3. "Пульс" — визуальная реакция строго на реальное событие (идёт настоящая Jules-сессия), никогда
   не декоративная анимация "просто чтобы было живо".
4. Вмещается в один экран целиком, не растёт бесконечно вниз.
5. Ничего не выдумано — если данных для дуги/связи нет, дуга просто не рисуется, а не подменяется
   фейком.

То же самое должно быть верно и для Kaizen/TOC: честная метафора для реальных данных, не
иллюстрация поверх выдуманных чисел.

## 9. Материал для метафоры (не решение — материал для дизайнера)

**Kaizen** — по духу ближе всего к настоящей цеховой доске Kaizen (физическая доска с карточками
находок в реальных японских производствах) или к журналу мастерской: находка → попробовали →
подтвердили/отменили. PDCA — это буквально цикл с 4 стадиями, можно показать как след/путь одной
карточки, а не отдельную статичную табличку.

**TOC** — сама теория ограничений уже визуальный образ по построению: труба/конвейер, где везде
широкий поток, кроме одного места. Один реальный, названный, видимый "затор" — сильнее любой
таблицы с $L_q$/$\mu$/$\sigma$. "Верёвка"/буфер естественно ложится на образ шлюза/клапана перед
узким местом.

Дизайнеру предстоит найти свой собственный образ (как Stitch-референс дал "Verdant Flow" для дерева)
— выше не финальные решения, а достаточно материала, чтобы не начинать с чистого листа.

## 10. Открытые вопросы

1. Нужен ли для TOC человекочитаемый словарь имён узлов конвейера (`AUTOMERGE_PROCESSING` →
   "Слияние готовой работы")? Сейчас таких переводов не существует нигде в системе — либо собирать
   вручную по мере появления новых узлов, либо просить бэкенд отдавать готовую подпись.
   Backend-часть не в этом ТЗ.
   ('' - зависит от того, сколько разных узлов реально появляется со временем; сейчас в графе виден
   только один.)
2. Нужна ли на этих страницах опция "показать сырые цифры" для тех немногих случаев, когда оператор
   всё же хочет увидеть DPMO/σ напрямую — или это уходит целиком в детали/tooltip?
3. Обе страницы сейчас также используются самим Gemini-наблюдателем как источник контекста
   (`GeminiProjectObserverService.readKaizenProposals` и т.п. читают эти же данные) — редизайн
   касается только человеческого интерфейса, не трогает то, что видит Gemini.
