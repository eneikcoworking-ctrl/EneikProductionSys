# Engineering Invariants Charter

Каждый файл роли BARCAN наследует эти инварианты. Это не общие пожелания "пиши надёжный код" — каждый пункт
назван по классическому, математически обоснованному паттерну информатики и обнаружен через реальный
инцидент в этой системе. Правило проверяемо: код либо следует ему, либо нет.

## 1. Compare-And-Swap вместо read-then-write
Если код читает статус/поле, чтобы решить, разрешён ли переход, а затем ПОЗЖЕ отдельной инструкцией пишет
новое значение — между чтением и записью есть окно, где конкурентный процесс может изменить ту же строку.
Классический паттерн: атомарный compare-and-swap (Lamport/Herlihy, lock-free concurrency; в SQL —
`UPDATE ... WHERE id=? AND status=?`, с проверкой числа затронутых строк). Инцидент: терминальная (уже
`failed`) задача была молча воскрешена в очередь конкурентным потоком, продублировав уже завершённую работу.
Правило: любой переход состояния, который не должен быть отменён, пишется только через guarded conditional
update, никогда через сохранение объекта после отдельного чтения.

## 2. Критическая секция для check-then-create
CAS защищает уже существующую строку. Он НЕ защищает решение "создать новую запись, если такой ещё нет" — на
момент проверки строки ещё не существует, гарантировать нечего. Классический паттерн: критическая секция /
взаимное исключение (Dijkstra) — конкурирующие вызовы должны сериализоваться через реальную блокировку
(`SELECT ... FOR UPDATE`), а не через проверку-затем-запись. Инцидент: несколько параллельных вызовов
создавали дублирующие singleton-задачи (аудит, review-fallback) из-за гонки между "проверить, что активной
задачи ещё нет" и "создать новую".

## 3. Поглощающие состояния конечного автомата
Статусы вроде `done`/`failed`/`spike_completed` — не просто ярлыки, а поглощающие состояния формального
конечного автомата: попав туда, сущность не должна выйти обратно ни при каких условиях. Классический аппарат:
теория конечных автоматов, поглощающие состояния марковских цепей. Правило: перед тем как писать код,
задающий статус сущности, явно определи, какие её состояния поглощающие — и убедись, что ни один код-путь не
может записать не-поглощающее значение поверх уже поглощающего.

## 4. Идемпотентность операций
Операция идемпотентна, если её повторное применение к уже применённому результату не меняет исход.
Классический паттерн распределённых систем: at-least-once delivery + идемпотентный обработчик = эффективно
exactly-once. Инцидент: повторная попытка смержить уже смерженный PR ошибочно трактовалась как конфликт
вместо "уже готово, ничего делать не нужно", вызывая бесконечные повторы. Правило: перед retry-логикой любой
операции спроси — "что если эта операция уже выполнена?" — и обработай этот случай явно, а не как ошибку.

## 5. Референциальная прозрачность и детерминизм тестов
Тест, зависящий от `Random`/`System.currentTimeMillis()`/сгенерированного без фиксации ID, — недетерминированная
функция: может пройти на одном прогоне и упасть на следующем для абсолютно идентичного кода. Классический
принцип функционального программирования: референциальная прозрачность — одинаковый вход обязан давать
одинаковый выход. Правило: любой недетерминированный источник, влияющий на код под тестом, обязан быть
инжектируемым/seed-ируемым; тест обязан зафиксировать конкретный seed, а не полагаться на дефолтный генератор.

## 6. Каноническое представление на границах сериализации
JSON не имеет канонического числового типа — одно и то же значение может распарситься как `Double` или
`BigDecimal` в зависимости от нотации записи и от того, какую библиотеку выбрал парсер. Классическая ошибка
(Ryle, category error) — сравнивать значения, будто они одной логической категории, когда это не так.
Правило: любое сравнение числового значения, пересекающего границу сериализации, использует явное
типобезопасное сравнение — никогда сырой типозависимый matcher против значения неизвестного заранее типа.

## 7. Монотонные водяные знаки против бесконечных циклов
Механизм вида "переобработать, если появилось что-то новое" обязан сравнивать против монотонно растущей
метки (watermark), явно исключающей собственные же побочные результаты предыдущего цикла — иначе система
может опознать свой же артефакт как "новое" и запустить себя снова, без остановки. Классический паттерн
потоковой обработки: watermarking. Инцидент: аудит распознавал собственный PR с отчётом как новую смерженную
работу и перезапускал сам себя бесконечно, пока это не было исправлено.

## 8. Точная область подсчёта в знаменателе метрики
Соотношение "X из Y" честно ровно настолько, насколько точно определено множество Y. Элемент, который
структурно никогда не может перейти в "выполнено" (отклонённый дубликат, вспомогательная работа без кода),
обязан быть явно исключён из знаменателя — иначе метрика застревает ниже 100% навсегда, а любой код,
принимающий решения на основе этой метрики (например, "не брать новую работу, пока текущая не готова на
100%"), молча блокируется без единого объяснения. Правило: при вычислении любого прогресс-соотношения явно
перечисли, какие статусы/категории исключены из знаменателя, и почему именно они.
