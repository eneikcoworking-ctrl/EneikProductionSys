## 1. Ретроспективный анализ: Что пошло не так с предыдущими проектами?

### 1.1. Проект `test-fifty-first` (UUID: `3e9c8cad-9c2f-453e-bf22-870da25101ef`)
* **Симптом:** Проект простоял в состоянии `SYSTEM STALLED` более **995 минут** при 100% исправности контейнеров и наличии задач в очереди.
* **Причина №1 (Архитектурный замок «Уловка-22» в Предписании 57):**
  1. Метод `ContinuousOrchestrationService.checkForSystemStall()` переводил проект в `ProjectStatus.stalled`, если `minutesSinceProgress > stallThresholdMinutes`.
  2. Статус `stalled` транслировался в `FlowSpineService.decideState()` как состояние `SYSTEM_STALLED`.
  3. `OperationalPolicyService` в состоянии `SYSTEM_STALLED` аппаратно запрещал действия `ORCHESTRATE` и `DISPATCH_QUEUED_TASKS`.
  4. Главный цикл оркестратора запрашивал из базы исключительно:
     `projectRepository.findByStatusOrderByCreatedAtDesc(ProjectStatus.active);`
     В итоге проект `stalled` выбрасывался из цикла оркестрации и навсегда лишался возможности получить такт восстановления.
  5. Ветвь самоисцеления требовала свежего факта продвижения (`recordProgress`), но продвижение было заблокировано политикой.
  6. **Почему тесты были зелеными:** Юнит-тест `stalledProjectRecoversToActiveWhenProgressRecordedWithinWindow()` проходил изолированно за счет синтетической инъекции мока `tracker.recordProgress()`. Локальный тест маскировал системный дедлок глобальной топологии.
* **Причина №2 (Сбой главного CI ветки main):**
  - Фактическое состояние снимка: `"mainCiStatus": "failure", "mainCiGreen": false ("Backend Verification=failure")`.
  - Инвариант `main_ci_green_required_for_delivery` заблокировал приемку и сдачу 20 смердженных деливераблин, переведя проект в тупик `BLOCKED_BY_MAIN_CI`.
* **Причина №3 (Паралич ленивой сериализации Jackson):**
  - Ленивый прокси Hibernate `@ManyToOne dependsOn` в `TaskEntity` ронял сериализацию контроллеров с HTTP 500, ломая внешнюю телеметрию.

* **Симптом (Инцидент 24 октября 2026):** 39 задач в очереди `queued`, 0 задач в работе `claimed`, фабрика заблокирована на протяжении многих часов при 100% формально «идеальных» механизмах.
* **Причина №1 (Деонтическая антиномия коллективной дисквалификации D006 / D011):**
  - Задача ревью 21 Pull Request объединила 21 PR.
  - Правило Запрета Самоаттестации (Charter Pattern #12: автор PR не может быть его ревьюером) обошло авторов всех 21 PR.
  - Поскольку авторами были все 7 доступных аккаунтов пула Jules (`Jules-01` .. `Jules-07`), множество исключаемых аккаунтов составило **100% пула**.

* **Причина №2 (Категориальная ошибка TargetContext D002 / D012):**
  - Метод `deriveTargetContextFromSourceWishlist` возвращал `null` для задач с источником `WishlistSource.client`.
  - Задачи циклически отбрасывались: `undetermined targetContext; skipping dispatch until target context is resolved`.
* **Причина №3 (Poka-Yoke Dysphoria — иллюзия локального благополучия):**
  - Ни один сервис не падал с ошибкой. Все транзакции завершались успешно, возвращая `continue`. Внешний мониторинг процессов считал, что фабрика здорова.
