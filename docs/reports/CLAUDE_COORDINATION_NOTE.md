# 🟢 ЗАКРЫТА ЗАДАЧА $\mathcal{L}_2$ (Task 25: Цена обхода GitHub ограничена остатком работы, а не историей)

**Завершено и доказано заслоном `GitHubSweepBudgetEfficiencyTest` (все тесты зелёные).**

**Реализованные свойства по 5 пунктам заслона:**
1. **Терминальные PR не опрашиваются повторно (расход = 0):** `AutoMergeService.resurrectAlreadyMergedReviews()` исключает ревью со статусом `"closed_unmerged"`. При первом обнаружении закрытого без слияния PR статус ревью переводится в `"closed_unmerged"` навсегда, фиксируя результат в базе и исключая повторные сетевые вызовы на всех последующих тактах.
2. **Неотносимые строки не опрашиваются (Законы 11 и 13):** `AutoMergeService.belongsToActiveProject()` проверяет цепочку сессии (`session -> task -> project`) и fallback-сопоставление по репозиториям активных проектов. При отсутствии активного проекта строка остаётся в множестве решения (не удаляется, не маркируется ошибкой), получает `spend = 0`, и регистрируется в логе ровно один раз. Устранены холостые вызовы к удалённым репозиториям (`test-twentieth`, `test-twenty-first`).
3. **Кэширование снимка PR проекта на такт (20s TTL):** В `GitHubPullRequestService` добавлен per-tick кэш `projectSnapshotCache` с TTL 20 секунд. 14 независимых потребителей внутри одного такта вызывают `pullRequestSnapshot(project)` без повторных HTTP-запросов к GitHub. Кэш инвалидируется точечно при операциях мутации (`closeOpenPullRequests`, `mergeRecordPullRequest`, `closeSinglePullRequest`, `recordSuccessfulMerge`).
4. **Обратный случай сохранён:** Живые непроверенные ревью активных проектов опрашиваются и верифицируются как прежде.
5. **Анализ замера 02:27:48:** Наблюдение в 02:27:48 зафиксировало 403 на первом же запросе после снятия подавления из-за 5-минутного cooldown (`DEFAULT_COOLDOWN_SECONDS = 300`) до `02:32:48`, после чего в `02:32:48` доступ к GitHub успешно возобновился (подтверждено логами `02:32:49` [BRANCH-GC] и работой с ветками). Устранение фонового дребезга ревью ликвидирует первопричину хронического исчерпания лимита (~350 вызовов/окно по истории).

10. **Наставление $\mathcal{L}_2$: ядро и периферия по Куайну, и первый ядерный закон — приём требования.**

    **Директива оператора.** Цеха должны быть настолько близки к идеалу, чтобы дальнейшая работа не мешала
    выполнению проектов. По Куайну: **ядро в идеале, доводится только периферия.**

    **Что это значит формально** (записано в модель, раздел «Ядро и периферия»):

        ядро идеально ⟺ ∀ проект: он выполняется, пока над Π ведётся работа
        правка π ∈ Π не имеет права потребовать правки k ∈ K
        |{k ∈ K : изменён при работе над Π}| = 0

    Критерий готовности ядра — не «в нём нет дефектов», а «дальнейшая работа ему не мешает». Пока это число
    не ноль, всякая работа над периферией оплачивается остановками проектов.

    **Демаркация — не по важности, а по одному вопросу: может ли механизм удержать поток?** Цех, способный
    придержать, отменить или заблокировать продуктовую работу, периферией не является — он в ядре по факту
    своего действия. Цех, умеющий только порождать находку, — периферия. Следствие для тебя: рычаг
    подчинения TOC формально «наблюдение», но он придерживает работу, поэтому держит ядерный стандарт.

    **Обязанность периферии.** Находка возвращается в поток вишлистом (закон 3) и ждёт очереди по порядку
    допуска (закон 13). Периферийный цех **не выносит запретов**: запрет умеет сказать только «никогда», а
    находка — это «вот ещё работа».

    **ЗАДАЧА 1 (ядро, первая по порядку): закон приёма требования — новый закон 25a в модели.**

    Оператору нужна гарантированная возможность запустить новый проект. Сейчас её нет, и вот замер:
    `ProjectFlowService.createProject` объявлен `@Transactional` и внутри одной транзакции замораживает
    прежний активный проект, **закрывает его открытые PR на GitHub** (`closeOpenPullRequests` — сетевой
    вызов), освобождает все незакрытые притязания по всем проектам, создаёт строку нового проекта и
    провиженит репозиторий и рабочее пространство (ещё сетевые вызовы). Отказ в любой точке откатывает
    создание нового проекта — но **не откатывает уже закрытые на GitHub PR**.

    **Что доказать, а не что набрать.**

        dom(admit) = { w : content(w) ≠ ∅ }      единственное предусловие — непустой бриф
        admit ⊥ state(P_прежн)
        admit ⊥ availability(Jules, GitHub)
        effects(admit) ⊆ собственные данные фабрики

    1. **Разделить акт.** `admit` пишет ровно одно: строку проекта и его бриф. Ни одного внешнего вызова.
       Тогда приём **тотален**: при непустом брифе он не может не удаться.
    2. **`retire` — обычный оборот цикла** и подчиняется закону 8: своя вариантная функция, своё
       свидетельство, записанное поглощающее условие. Его неуспех не отменяет `admit`, а означает лишь, что
       ёмкость освободится позже.
    3. **Идемпотентность `retire`.** Внешние эффекты уже случились; повтор не имеет права ни считать их
       несделанными, ни делать их дважды.
    4. **Порядок, а не запрет** (закон 13): новый проект принят немедленно и берёт ёмкость по мере её
       высвобождения. Формулировка «нельзя начать, пока прежний не добит» запрещена.

    **Заслон, который это доказывает.** Не «метод существует», а свойство: при недоступном GitHub и
    недоступном Jules вызов `admit` с непустым брифом **завершается успехом**, и проект существует в базе.
    Обратный случай обязателен: при пустом брифе `admit` отказывает. И структурный: в транзакции `admit`
    нет ни одного сетевого вызова — это проверяется так же, как закреплено множество точек слияния в
    `AutoMergeLaw20InvariantS4Test`.

    **Решение Antigravity ($\mathcal{L}_2$):**
    - Закон 25a реализован: `ProjectFlowService.admitProject` — чистая локальная транзакция `@Transactional` (сохраняет проект и начальный вишлист в БД фабрики, локально переводит прежний активный проект в `frozen`). Нулевые вызовы внешних сетей в транзакции.
    - Внешний вывод из работы (`retireExternalWorkForPriorProjects`) и провизионинг (`projectFactoryService.provision`) отделены в отдельные обороты в `createProject`.
    - Написан строгий заслон `ProjectAdmissionLaw25aTest` (4/4 зелёные): тотальность при непустом брифе, отказ на пустом/пробельном, устойчивость к сбою внешних систем (проект остаётся в БД), и структурная проверка чистоты `@Transactional`.
