# План: наблюдение за реальным рантаймом активного продукта + продуктовый Kaizen

Статус: **план, ничего не реализовано**. Все 4 фазы ждут отдельного "да" перед началом каждой.

## Контекст и почему это вообще нужно

Сегодня ночью (2026-08-09) выяснилось: "доставлено" в системе — это факт бухгалтерии сборки
(все фичи смерджены), ни разу не проверенный против реальности. Метафора оператора: "мы запускаем
космический корабль, как только он чуть-чуть готов взлететь, но продолжаем строить его всегда" —
у нас нет наблюдения за кораблём ПОСЛЕ взлёта, только чек-лист сборки.

Первая версия этого плана была отвергнута оператором дважды:
1. Первая версия использовала названия математических понятий (Байес, контрольные карты, энтропия)
   как украшение, без реальных формул и чисел — не было math, только слова о math.
2. Вторая версия (детальная, с классами/миграциями/крон-выражениями) содержала
   `@Scheduled(cron = "0 0 4 * * ?")` — то есть **тот же самый антипаттерн**, из-за которого
   случилась вся сегодняшняя катастрофа (жёстко зашитое расписание вместо решения по данным).
   Оператор поймал это лично: "я вижу захардкоженные сроки!!! это явный вред и антипаттерн".

Финальный, согласованный оператором принцип: **никаких новых cron-расписаний. Никаких зашитых
чисел. Каждое решение "когда действовать" вычисляется заново из накопленной уверенности, на
каждом тике уже существующего непрерывного цикла `ContinuousOrchestrationService`** (уже тикает
~раз в минуту для активного проекта, уже решает "что сейчас разрешено делать" через
Flow Core state/`OperationalPolicyService` — новая observability-логика становится ЕЩЁ ОДНИМ
возможным действием в этом же цикле, не отдельным параллельным сервисом).

Другая важная поправка оператора: **завод строит и наблюдает ровно ОДИН активный проект в любой
момент времени.** Никакого "флота" из ~40 проектов, никакого шедулинга между проектами — эта идея
(Phase 4 из более ранней версии плана, information-theoretic scheduling) полностью выброшена.

## Phase 0 — Может ли продукт вообще запуститься (разовый факт, не бесконечный процесс)

**Что проверяется**: есть ли у активного проекта задокументированный способ запуститься
(`docker-compose.yml` или эквивалент) в его собственном GitHub-репозитории.

**Когда проверяется**: не по расписанию — по событию. Когда существующий пульс
(`ContinuousOrchestrationService`) на своём обычном тике впервые видит, что
`readinessService.computeForProject(id)` вернул `decompositionComplete=true` и
`featureReadinessRatio=1.0` (проект реально доставлен) — в этот момент, и только в этот момент,
задаётся вопрос "а запускается ли он вообще".

**Если файла нет**: НЕ пишем код в клиентский репозиторий автономно (урок сегодняшней ночи —
никогда не обходить обычный путь "находка → вишлист → задача → Jules"). Заводится ОДИН обычный
wishlist-item (новый `WishlistSource.runtime_observability_gap`), идёт через тот же
`TechnicalLeadCompiler` → обычную задачу → обычного Jules, как любая другая фича. Дедуп — не
создавать второй раз, если уже есть открытый такой же.

**Если файл уже есть**: Phase 0 для этого проекта закрыт навсегда, дальше не проверяется повторно.

## Phase 1 — Живучесть: бесконечно уточняемая уверенность (Beta-апостериор)

**Что измеряется**: каждая проверка — бинарный факт (запустился/не запустился,
health-check ответил/не ответил).

**Математика (с реальными числами)**: начинаем с полного незнания — `α=1, β=1`
(стандартный некомпетентный байесовский приор, та же математика, что уже реально работает в
`AccountHealthService` для F2 lever). После каждого наблюдения "успех" → `α += 1`, "провал" →
`β += 1`.

Ширина 95%-го доверительного интервала вероятности успеха сужается предсказуемо:
- 0 наблюдений (`α=1,β=1`): интервал ≈ [0.025, 0.975], ширина ≈ 0.95 — полная неопределённость.
- 10 наблюдений подряд "успех" (`α=11,β=1`): интервал ≈ [0.72, 1.0], ширина ≈ 0.28.
- 50 наблюдений подряд "успех" (`α=51,β=1`): интервал ≈ [0.93, 1.0], ширина ≈ 0.07.

**Правило следующей проверки**: `время_до_следующей_проверки = базовое_время × ширина_интервала`.
Широкий интервал → проверяем скоро. Узкий и стабильный → проверяем реже. Процесс никогда не
заканчивается — интервал никогда не достигает нуля, время между проверками просто растёт, пока
стабильно, и мгновенно сжимается, если что-то разладилось.

**Интеграция**: на каждом тике `ContinuousOrchestrationService` — дешёвый вопрос "пора ли по
формуле выше" (просто сравнение времени, никакого сетевого вызова). Если да — дорогое действие
(реально поднять продукт и проверить) выполняется через отдельный сервис-исполнитель.

**Архитектурное решение, требующее отдельного явного "да" оператора (не решено, только описано)**:
чтобы реально выполнить `docker compose up` для чужого репозитория, нужен доступ к Docker с хоста.
Два варианта:
- (a) Смонтировать `/var/run/docker.sock` прямо в backend — просто, но даёт всему Spring-приложению
  фактически root-доступ к хосту. Один баг в коде — уязвимость всего хоста.
- (b) Отдельный узкоспециализированный sidecar-контейнер ("launcher"), без остального кода завода,
  с тремя командами (`launch`, `healthcheck`, `teardown`), сам держит докер-сокет; backend общается
  с ним по HTTP через внутреннюю сеть.

Рекомендация (не решение): (b), принцип наименьшей привилегии.

**Схема (миграция, следующий свободный номер после V90 на момент реализации)**:
```sql
CREATE TABLE client_runtime_observations (
    id UUID NOT NULL PRIMARY KEY,
    project_id UUID NOT NULL,
    observed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    launch_success BOOLEAN NOT NULL,
    launch_duration_ms BIGINT,
    health_status_code INT,
    health_latency_ms BIGINT,
    error_text TEXT
);
```

**Гейт продвижения**: новый рычаг в уже существующем `LeverPromotionService`,
ключ `RUNTIME_OBSERVABILITY_LEVEL_0_1`, стартует на `observe_only` — копит наблюдения, ничего не
меняет в реальном поведении falsification-циклов, пока `evaluatePromotions` не подтвердит на
реальных данных, что сигнал надёжен.

## Phase 2 — Реально ли что-то сломалось, а не просто не повезло (сдвиг, не уверенность)

Другая математическая задача, чем Phase 1: не "насколько мы уверены в вероятности", а
"изменилась ли сама вероятность со временем" (детекция сдвига, не оценка параметра).

**Пример с реальными числами**: если исторически частота отказов 5% (1 из 20 проверок), а за
последние 5 проверок — 3 отказа (60%), нужно математически спросить: насколько вероятно увидеть
3 из 5 при истинной частоте 5%? Если это меньше порога значимости (например, p < 0.001) — это не
невезение, а статистически подтверждённый сигнал реальной поломки.

**Реализация**: переиспользовать уже существующий `ProcessControlService` (u-chart, рабочая
математика для DPMO завода) — новая константа-поток `STREAM_PRODUCT_RUNTIME_HEALTH`,
`recomputeForProject` для этого потока читает `client_runtime_observations` вместо build-time
сигналов.

**Явный минимальный порог выборки** (тот же принцип, что уже в `LeverPromotionService`) — карта
честно молчит ("недостаточно данных"), пока не накопится минимум N наблюдений из Phase 1 — не
судит о "сдвиге" по 2 точкам.

**Интеграция**: считается на том же тике, теми же данными, что уже собирает Phase 1 — не отдельный
процесс, не отдельное расписание.

## Phase 3 — Что делать, когда реально сломалось (событие, не расписание)

Когда Phase 2 говорит "это реальный сдвиг, не шум" — в этот момент (не по календарю) происходит
два действия одновременно:

1. Запускается настоящий falsification-цикл именно для активного проекта, с реальным фактом в
   брифе ("частота отказов выросла с 5% до 60%, статистически значимо, p<0.001") — не гадание, не
   чужой лог под чужим видом.
2. Пишется запись в `DefectJournalEntity` с новым полем `scope` (`factory` | `product`,
   по умолчанию `factory` — обратная совместимость без миграции существующих строк),
   `scope=product`. Существующий `KaizenService` (или отдельный `ProductKaizenService`, если
   логика разойдётся) читает `scope=product` отдельным, явно помеченным потоком предложений —
   "улучшение продукта", не смешивается с заводским списком.

## Порядок реализации

Phase 0 → Phase 1 (с обязательным отдельным решением оператора по (a)/(b) архитектуре launcher'а,
до написания кода) → Phase 2 → Phase 3. Каждая фаза — отдельный деплой, отдельная проверка,
`observe_only` до подтверждения на реальных данных — та же дисциплина, что уже применена сегодня
ночью к лестнице продвижения рычагов (LeverPromotionService).

## Явно вне охвата

- Наблюдение за несколькими проектами одновременно / шедулинг между ними — оператор явно исключил,
  завод работает с одним активным проектом.
- Любой новый `@Scheduled(cron = ...)` — весь план намеренно построен без единого нового
  расписания, только на существующем `ContinuousOrchestrationService`.
