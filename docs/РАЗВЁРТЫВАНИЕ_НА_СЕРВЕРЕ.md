# Развёртывание фабрики на сервере

Составлено 2026-08-22 по работающей системе: каждый путь, порт и размер прочитан с живой машины, а не по памяти. Документ на русском по прямому указанию оператора; остальные артефакты репозитория остаются на английском.

Есть два пути. **Выберите один до начала работ** — они расходятся уже на третьем шаге.

- **Путь А — чистый старт.** Пустая база, новый проект. Ничего пересылать не нужно, ключи вводятся заново. Рекомендуется, если не нужна история прошлых проектов.
- **Путь Б — перенос состояния.** База переезжает целиком со всеми проектами, задачами, наблюдениями и ключами.

---

## 1. Что представляет собой система

Пять контейнеров, поднимаются одной командой `docker compose up`:

| Служба | Порт | Назначение |
| --- | --- | --- |
| `backend` | 8080 | сама фабрика, Spring Boot, владеет всем состоянием |
| `frontend` | 3000 | веб-интерфейс оператора |
| `ml` | 8000 | тонкий HTTP-посредник для оценок, **только внутренний** |
| `runtime-launcher` | 8091 | поднимает продукт клиента для наблюдения, **имеет доступ к сокету Docker** |
| `judgment-sidecar` | 8092 | независимый рецензент на Claude Code, **только внутренний** |

Постоянное состояние лежит ровно в трёх местах, все монтируются из каталога репозитория:

- `./data` — база фабрики. **3.3 ГБ**, из них файл `eneik_db.mv.db` — **3094 МБ**.
- `./project-workspaces` — 836 КБ.
- `./runtime-launcher-workspace` — временные клоны продуктов. **Не переносить**, пересоздаётся сам.

---

## 2. Требования к серверу

- Docker Engine и плагин Compose. Больше ничего: ни Java, ни Node, ни Maven — всё собирается внутри контейнеров.
- **Оперативная память — минимум 8 ГБ.** На текущей машине 3.9 ГБ, и это отдельный записанный дефект: фабрика и её собственный набор тестов не помещаются одновременно, а один запрос к базе занимает до 10 секунд.
- Свободного места на диске — около 15 ГБ под базу, образы и кэш сборки.
- Обратный прокси с авторизацией перед машиной.

---

## 3. Безопасность — прочитать до начала

**Порты 8091, 8000 и 8092 не должны быть доступны из интернета ни при каких условиях.**

У службы `runtime-launcher` на порту 8091 примонтирован `/var/run/docker.sock`, потому что наблюдение за продуктом клиента означает запуск контейнеров на этом хосте. Кто дотянется до 8091, тот запустит контейнер на сервере и, следовательно, получит права root на машине. Это не рекомендация по укреплению, это вся граница безопасности целиком.

Наружу открывать **только 3000 и 8080**, и только за прокси, требующим входа. Если единственная защита — межсетевой экран, привяжите остальные три порта явно к локальному интерфейсу.

**Отдельно для пути Б:** файл базы содержит все учётные данные. Доступы к GitHub, Stitch и Linear хранятся внутри `eneik_db.mv.db`, а не в переменных окружения — проверено, в настройках compose из учётных данных присутствует только ключ Gemini, от которого система уходит. Копирование этого файла означает копирование ключей. Передавать только по защищённому каналу — никакой почты, мессенджеров и облачных ссылок.

## 4. Путь А — чистый старт

### 4.1 Что построится само

Flyway накатит 109 миграций и создаст всё: схему целиком, **все 13 ролей** (от архитектора до интегратора), таблицу настроек. Настраивать это не нужно.

### 4.2 Что придётся завести руками

**Учётные записи Jules.** Проверено: миграция создаёт их копированием из старой таблицы, а на пустой базе копировать нечего — записей не будет. Заводятся через интерфейс оператора или запросом `POST /api/accounts`.

**Ключи доступа.** Вводятся в разделе настроек. Нужны:

| Ключ | Для чего |
| --- | --- |
| `github_token` | создание репозиториев, коммиты, PR |
| `jules_api_key` | запуск сессий агентов |
| `stitch_api_key` | генерация дизайна |
| `linear_api_key`, `linear_team_id` | задачи в Linear, если используется |

Ключ Gemini не нужен — система от него уходит, его квота исчерпана.

**Проект.** Создаётся одной кнопкой; фабрика сама заведёт репозиторий на GitHub и проект в Linear.

Всё вместе — около получаса работы.

### 4.3 Порядок

```bash
git clone https://github.com/eneikcoworking-ctrl/EneikProductionSys.git /opt/eneik
cd /opt/eneik
# создать .env — см. раздел 6
docker compose up -d --build
```

Каталог `data/` не создаётся заранее — база возникнет при первом запуске.

## 5. Путь Б — перенос состояния

### 5.1 Остановить фабрику на старой машине

```bash
docker compose stop -t 60
```

Дождаться завершения. H2 при остановке сжимается и корректно закрывается. **Копирование файла на работающей фабрике даёт повреждённую базу** — это уже происходило и стоило восстановления.

### 5.2 Скопировать

```bash
scp EneikProductionSys/data/eneik_db.mv.db   user@server:/opt/eneik/data/
scp -r EneikProductionSys/project-workspaces user@server:/opt/eneik/
```

Около 3 ГБ по сети. Каталог `runtime-launcher-workspace/` намеренно не переносится.

### 5.3 Клонировать и положить состояние на место

```bash
git clone https://github.com/eneikcoworking-ctrl/EneikProductionSys.git /opt/eneik
# перенести скопированные data/ и project-workspaces/ внутрь /opt/eneik/
```

Каталоги `data/` и `project-workspaces/` в `.gitignore`, клонирование их не перезапишет.

## 6. Шаг, который может выполнить только владелец учётной записи

Служба `judgment-sidecar` запускает Claude Code как независимого рецензента и монтирует внутрь каталог с учётными данными. На текущей машине это путь Windows `C:\Users\<пользователь>\.claude`, которого на Linux не существует.

На сервере:

1. Войти в Claude Code **под учётной записью владельца** — инженер по развёртыванию за вас этого не сделает.
2. Запомнить созданный каталог, обычно `~/.claude`.
3. Указать его в `.env`.

Если шаг пропустить, фабрика запустится, но слой независимого суждения останется без рецензента.

### Файл `.env`

Находится в `.gitignore` и создаётся на сервере. У всех переменных есть значения по умолчанию, задать обычно нужно только эти:

```ini
CLAUDE_CREDENTIAL_DIR=/home/<пользователь>/.claude
GITHUB_ORG=eneikcoworking-ctrl
COMPOSE_PROJECT_NAME=eneikproductionsys
```

## 6.1 Доступ по SSH для рабочей машины оператора

Нужен **до запуска**, иначе придётся возвращаться к серверу второй раз.

Оператор продолжает работать со своей машины, а фабрика живёт на сервере. Всё, что делается при разборе неполадок — чтение логов контейнеров, запуск продукта клиента для наблюдения, проверка эндпоинтов, — выполняется на сервере по SSH. Без этого доступа со стороны рабочей машины возможно только писать код в репозиторий вслепую: нельзя ни прочитать лог, ни увидеть, сработала ли починка.

Добавьте этот публичный ключ в `~/.ssh/authorized_keys` пользователя, от которого запускается Docker:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIOg3iZ3wCWIGZ99+bWTvEoPCM5QNNxsNcbYIGiaaE3As eneik-factory-operator-workstation
```

Приватная часть ключа не покидает рабочую машину оператора и никому не передаётся.

Проверка со стороны оператора после настройки — на его машине должно отработать:

```bash
ssh -i ~/.ssh/eneik_server <пользователь>@<сервер> "docker ps"
```

**Ограничение доступа.** Учётной записи достаточно прав на управление Docker и чтение каталога `/opt/eneik`. Права `sudo` без пароля не нужны. Помните раздел 3: у этого пользователя есть доступ к сокету Docker, а это равносильно правам root на машине — поэтому вход по паролю на сервере лучше отключить полностью и оставить только ключи.

## 7. Запуск

```bash
cd /opt/eneik
docker compose up -d --build
```

Первая сборка занимает 10–20 минут. Flyway применяет миграции при старте, вручную ничего запускать не нужно.

---

## 8. Проверка — по уликам, а не по коду возврата

```bash
# все контейнеры подняты, ml/launcher/sidecar в состоянии healthy
docker ps

# бэкенд отвечает; при чистой базе — около минуты, при перенесённой 3 ГБ — до шести минут
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/actuator/health

# аварий при старте нет — должно напечатать 0
docker logs eneikproductionsys-backend-1 2>&1 | grep -c 'APPLICATION FAILED'

# для пути Б: состояние доехало целым — должны быть проекты, а не пустой список
curl -s http://localhost:8080/api/projects | head -c 300
```

Если на пути Б список проектов пуст при файле в 3 ГБ — копия снималась с работающей базы. Остановить, переснять с корректно остановленного источника, запустить заново.

## 9. После переезда

**Сжать базу.** 3094 МБ при примерно 88 МБ живых данных. Делать на сервере, где есть место снять копию перед операцией: остановить фабрику, скопировать файл, сжать, запустить, убедиться что `/api/projects` отвечает, и только потом копию удалить. **Снимков для отката сейчас не существует** — они были удалены ради места на старой машине, поэтому копия не опциональна.

**Вывести старую машину из работы** только после того, как пройдёт проверка из раздела 8. Ничего на ней после этого не нужно.

---

## 10. Что переезд даёт и чего не даёт

Он снимает физическое ограничение. Сборки перестают конкурировать с работающей фабрикой, запросы к базе перестают занимать секунды, полный набор тестов перестаёт требовать остановки бэкенда.

**Больше он не исправляет ничего.** Все дефекты из `LIVE_PRODUCT_PLAN_2026-08-19.md` переезжают вместе с системой без изменений. Сервер снимает физическое ограничение, а не логическое.
