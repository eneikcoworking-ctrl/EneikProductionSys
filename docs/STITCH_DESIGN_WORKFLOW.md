# Stitch Design Workflow (Дизайн → Согласование → Пиксель-в-пиксель)

## Введение

Этот документ фиксирует проверенную живыми вызовами методологию получения UI-дизайна через Google
Stitch MCP (`stitch.googleapis.com/mcp`) и переноса его в реальные Svelte-компоненты продукта.
Применяется ко всем проектам, не только к текущему. Расширяет роль **BARCAN-TAG-11
(`CLIENT-PERCEPTION`)** — deontic-критерии этой роли являются обязательными гейтами качества для
любого экрана, прошедшего через этот флоу, не рекомендацией.

**Расхождение с `docs/DESIGN_SYSTEM.md`:** тот документ описывает другую, более раннюю палитру
(синий/фиолетовый B2B SaaS, `#1D4ED8`/`#7C3AED`), которая не совпадает с реально используемыми
токенами "Verdant Flow" (`ProductTree.svelte`: `#fbf9f1`/`#7d8570`/`#3f7d32`/`#d97b29`/`#c99a2e`,
Libre Caslon Text + IBM Plex Sans). Расхождение зафиксировано здесь как факт, требующий отдельного
решения оператора — не исправлено самовольно.

## Факты о Stitch MCP (проверено живым `tools/list`, не документацией третьих лиц)

Реальный сервер отдаёт ровно 15 инструментов: `create_project`, `get_project`, `delete_project`,
`list_projects`, `list_screens`, `get_screen`, `generate_screen_from_text`, `edit_screens`,
`generate_variants`, `upload_design_md`, `create_design_system`, `create_design_system_from_design_md`,
`update_design_system`, `list_design_systems`, `apply_design_system`.

- **Ни один инструмент не принимает файл-картинку.** Все параметры — текст или структурные enum/hex
  поля. Если где-то видна информация про "reference image upload" в Stitch — это относится к
  веб-интерфейсу Stitch для человека, не к этому программному API.
- **`screenType` — единственный переключатель код/картинка**, и определяется исключительно стилем
  промпта. Фотореалистичный/иллюстративный/3D-регистр → `screenType: IMAGE`, кода не будет никогда,
  вне зависимости от количества попыток. Структурный/dashboard/"vector line art"/"SVG-style" регистр
  → `screenType: DESIGN`, `status: COMPLETE`, реальный `htmlCode.downloadUrl`.
- **Обходной путь для буквального визуального референса** (например, конкретная композиция дерева):
  раз SVG-разметка — это текст, её можно вставить как буквальный код прямо в `prompt`, с пометкой
  "render this exact vector illustration inside the layout below". Stitch читает это как структурную
  спецификацию, не как непрозрачный файл.
- **`create_design_system` — структурный, не текстовый.** Поля: `displayName`, `theme.headlineFont`/
  `bodyFont`/`labelFont` (значение — из реального enum шрифтов, например `LIBRE_CASLON_TEXT`,
  `IBM_PLEX_SANS`), `colorMode` (`LIGHT`/`DARK`), `customColor`/`overridePrimaryColor`/
  `overrideSecondaryColor`/`overrideTertiaryColor` (hex), `roundness`, опционально `designMd`.
  Возвращает id (`assets/...`).
- **Каждый вызов `generate_screen_from_text`/`edit_screens`/`generate_variants` — это реальный
  `git commit` в `main` репозитория проекта**, не песочница (см. `DesignAssetService
  .commitDraftToGitHub` → GitHub Contents API `PUT` без указания `branch`). Не более 1–2 вызовов
  подряд без явной необходимости; каждый отклонённый раунд обязан завершаться очисткой (см. ниже).
- **Параллельные вызовы `create_project` ненадёжны** — конкурентные вызовы могут уронить внутреннюю
  сессию `StitchClient` (наблюдалось: 3 параллельных вызова → все 3 упали одной и той же
  transient-ошибкой, помог только полный перезапуск backend). Генерировать экраны **последовательно**.

## Методология, шаг за шагом

### Шаг 0 — Дизайн-бриф (ТЗ)
Структурированный документ на экран: предмет/аудитория/задача, точные hex-токены и шрифты (только из
реального enum, см. выше), опись реального контента (настоящие значения из API, не lorem), и явный
**регистр стиля** — "vector line art / SVG-style / flat illustration", никогда "photorealistic / 3D
render" — даже если исходный референс фотореалистичен, его стиль осознанно переводится в векторный
регистр, а не отбрасывается вместе с содержанием (в частности: убирать иллюстрацию-центр композиции
ради получения кода — ошибка; описывать её иначе, сохраняя её присутствие — правильный путь).

### Шаг 1 — Design System, один раз на проект
`create_design_system` со структурными полями. Сохранить `designSystem` id. Каждый последующий
`generate_screen_from_text` передаёт этот id — единственный способ получить согласованность между
экранами без пересказа палитры в каждом промпте.

### Шаг 2 — Генерация экранов, последовательно
Один вызов → дождаться ответа → следующий. Буквальный визуальный референс — как SVG-код внутри
`prompt` (см. обходной путь выше), не как файл.

### Шаг 3 — Опрос до готовности
`get_screen` в цикле (уже реализовано в `StitchClient`/`DesignAssetService`) до `status: COMPLETE`.
`screenType: IMAGE` — явный отказ по критериям Шага 0 (регистр стиля соскользнул), не молчаливое
принятие как есть.

### Шаг 4 — Рендер на два вьюпорта
Через `mcr.microsoft.com/playwright:v1.48.0-jammy` (контейнеризованный — локальный Playwright требует
системных библиотек, которых нет без root в типичном WSL2-окружении). **1440px и 375px обязательны**
— это критерий `has_both_screenshots` роли BARCAN-TAG-11, Obligatory, не опция.

### Шаг 5 — Показ на согласование
Publish через Artifact, отдельным шагом от генерации. Approval — явный ответ оператора. Генерация
кода Stitch НЕ равна согласованию дизайна — это два разных события.

### Шаг 6 — Если отклонено
`edit_screens` (существующий `selectedScreenIds` + новый `prompt`) вместо нового `create_project` с
нуля — меньше коммитов, сохраняется преемственность.

### Шаг 7 — Очистка отклонённых черновиков
`POST /api/ai/resources/design-drafts-cleanup` (basenames соответствующих `design/draft/*` папок) —
обязательный последний шаг любого отклонённого раунда, не разовая уборка по жалобе.

### Шаг 8 — Пиксель-в-пиксель, вручную
Stitch HTML — референс структуры и палитры (Tailwind CDN, не компонентизирован), не готовый
компонент для вставки. Кодируется вручную в реальных Svelte-компонентах с реальными данными API
вместо примеров из макета.

## Deontic-гейты (BARCAN-TAG-11, обязательны для любого экрана из этого флоу)

**Obligatory:** CLS < 0.1; семантический HTML5/ARIA; LCP < 2.5с; скриншоты на 1440px и 375px
(`has_both_screenshots`).

**Forbidden:** `responsive_ok` нарушен (десктоп/мобайл скриншоты идентичны по контрольной сумме/
размеру); `visual_qa_ok` нарушен (скриншот < 1024 байт, пустая страница, 500-ошибка); интерактивные
элементы без клавиатурного фокуса; фиксированные px для размеров шрифтов.

## Инфраструктурные ограничения

- WSL2-хост в этом окружении стеснён по памяти (~1.9GB; backend JVM уже держит heap до 1.5GB).
  Docker-билд и Playwright-рендер конкурируют за неё с работающими контейнерами — по возможности
  временно `stop` второстепенные контейнеры перед билдом, вернуть после.
- Зависание Docker (`accept4 failed 110`, WSL2 vsock) — `wsl.exe -t docker-desktop` перезапускает
  только VM Docker Desktop, не трогая рабочую сессию, и освобождает память без потери контейнеров
  (Docker Desktop поднимает VM заново при следующей команде).
- H2 может закрыться под той же нагрузкой (`Database has been closed [90098]` /
  `Cannot allocate memory` в MVStore) — безопасный фикс: `docker compose stop backend && start
  backend` на том же контейнере (не `up --force-recreate`), без потери данных на volume.
