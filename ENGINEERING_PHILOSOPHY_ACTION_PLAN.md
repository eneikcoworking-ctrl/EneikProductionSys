# Идеальная модель потока EneikProductionSys

**Что это.** Один документ о том, каким поток обязан быть. Не отчёт, не дневник, не список задач. Каждый
закон здесь сформулирован так, что код ему либо подчиняется, либо нет, и под каждым сказано, как обстоит.

**Как пользоваться.** Сперва привести код в соответствие с моделью. Встретилась задача потока, которой в
модели нет — сперва исправляется модель, потом код. Обратный порядок и есть то, из чего растут заплатки.

**Правило документа.** Только проверенное. Утверждение без замера — не находка, а догадка, и догадка сюда
не пишется. Механизм, зарегистрированный, но ни разу не сработавший, считается неработающим. Сделанное
отсюда уходит молча: оно видно в коде и в git. Хроника — в `docs/reports/CLAUDE_COORDINATION_NOTE.md`; здесь
её нет, потому что она вытесняет модель и стареет быстрее кода.

**Три статуса, и никаких других.** Различие между вторым и первым — не формальность: чтение кода
устанавливает, что инвариант выполняется сегодня, и ничего не говорит о завтра.

    держится            инвариант выполняется в коде И заслонён тестом, который способен упасть
    держится, не заслонён   выполняется по чтению кода; теста, способного упасть на нарушении, нет
    не держится         инвариант нарушен, и названо, чем именно

Заслон, который не может упасть, заслоном не является: сюда входят красный тест (он не различает
исправное от сломанного, потому что падает в любом случае), тест на другой предмет, чем закон, тест,
возвращающий зелёное при ненайденном предмете проверки, чёрный список имён вместо утверждения о свойстве,
и сообщение механизма, утверждающее больше, чем механизм делает.

**«Держится» всегда относительно точек, где проверяли.** Статус — список того, что было рассмотрено, а не
утверждение о мире. Замерено 2026-09-05: ядро было объявлено без открытых пунктов, и через полтора часа
обнаружился ядерный дефект, стоивший четверти каждого часа, — при том что все законы, которые его
покрывают (8, 13, 25), стояли «держится». Они и держались в тех точках, где их проверяли; обход внешней
системы среди этих точек не был. Отсюда: «ядро закрыто» читается как «в рассмотренных механизмах открытых
расхождений нет», и никогда — как «дефектов больше не осталось». Полнота списка не есть полнота мира.

# I. Среда

Только то, что верно для машины, на которой фабрика работает: Hetzner, Ubuntu, `/opt/EneikProductionSys`,
живой контур в Docker. Нарушение любого пункта стоило часов.

**Живая база — только в томе Docker.** H2 встроен в процесс бэкенда, и замер по копии живого файла рван по
определению: одни и те же запросы дают противоречивые ответы, пока бэкенд пишет. Мерить со статичной копии
при остановленном сервисе, сверяя md5, либо через HTTP наружу.

**Память хоста 3.8 ГБ, свободно около 1.7 ГБ при поднятом контуре.** Сборка и тесты — в контейнере с
явным пределом памяти и с копированием исходников **внутрь** (`cp -r /src/src /work`), никогда не в общий
том с живым контуром. Полный `mvn test` проходит при `-Xmx512m` на форке; без предела он выдаёт выдуманные
падения `Cannot allocate memory` при сканировании classpath.

**Апостроф в комментарии внутри `@Query` — незакрытая кавычка.** Spring Data сканирует всё значение
аннотации на кавычные диапазоны и не исключает комментарии `--`. Один апостроф роняет контекст на старте
(`The string <SELECT ...> starts a quoted range at N, but never ends it`). Проверка — чётность апострофов
внутри каждого блока `@Query(value = """`.

**Имя аргумента сборки — `ENEIK_BUILD_GIT_SHA`, не `GIT_REVISION`.** При втором образ собирается из верного
дерева, а метка `org.opencontainers.image.revision` остаётся `unknown`, и сверить образ с `main` по метке
уже нельзя. Содержимое всё равно проверяемо прямо: `docker cp <контейнер>:/app/app.jar`, затем `zipfile` по
`BOOT-INF/classes/.../X.class` и поиск строки, которой в прежней версии не было.

**Монитор — только на однократные события** (конец сборки, падение теста). Направленный на лог работающей
фабрики, он превращает каждую строку цикла в уведомление и топит канал.

# II. Поток

## Обозначения

    W  вишлисты   status(w) ∈ {pending, compiling, converted_to_task, dismissed}
    T  задачи     status(τ) ∈ {queued, claimed, in_progress, review, pending_review,
                               done, failed, blocked, spike_completed}
    E  эпики      epic(τ) ∈ E ∪ {∅}
    A  аккаунты   ceiling(a), dailyCeiling(a), occ(a,t) — открытых сессий в момент t
    S  сессии     одна сессия = одна ветка = один PR
    R  ревью      ciStatus(r), merged(r), session(r)

    carrier(τ)   ⟺ payload(τ).taskType ≠ ∅               носитель фабрики
    accepted(s)  ⟺ externalSessionId(s) ∉ {∅, skipped}   Jules принял сессию
    refused(s)   ⟺ externalSessionId(s) = ∅ ∧ status(s) = failed
    merged(τ)    ⟺ diff задачи присутствует в main
    terminal(τ)  ⟺ status(τ) ∈ {done, failed, spike_completed}

## Цепь

    w ─κ─▶ (e, {τ₁…τₙ}) ─δ─▶ s ─▶ PR ─ρ─▶ гейты ─μ─▶ merged ─▶ done

`κ` компиляция, `δ` отправка, `ρ` ревью, `μ` слияние — частичные функции с предусловиями. Ни одна не
выполняется дважды для одного элемента без явного возврата предыдущего шага.

## Контур ценности

Поток есть замкнутый контур: один вход извне и шесть дуг обратной связи, все возвращающиеся в одну точку.

    клиентский бриф
          │
          ▼
    ┌──▶ ВИШЛИСТ ──κ──▶ ЭПИК ──▶ ЗАДАЧИ ──δ──▶ сессии ──▶ PR ──ρ──▶ гейты ──μ──▶ слияние
    │                                                                                 │
    │                                                                                 ▼
    │                                                                       суждение о доставленном
    │      ┌──────────────────────────────────────────────────────────────────────────┤
    │      │ фальсификация ролей          ночной круг по критериям отказа каждой роли  │
    │      │ аудит покрытия               на каждый клиентский вишлист по мере слияния │
    │      │ реальность доставки          отчиталось done, в main не попало            │
    │      │ наблюдение живого продукта   запуск, здоровье, снос контрольной карты     │
    │      │ дрейф дизайна                реальный отданный HTML против дизайн-системы │
    │      │ наблюдатель проекта          Gemini                                       │
    └──────┴──────────────────────────────────────────────────────────────────────────┘

    ∀ находка f любого департамента:  f ↦ вишлист,  и далее по цепи

Дуга, не возвращающая находку в цепь, разомкнута. Разомкнутая дуга — не наблюдение, а потеря.

## Три слоя

    ℒ₁  инфраструктура и оркестрация — планировщик, H2, CAS-аренды (300 с), память хоста, квоты провайдеров
    ℒ₂  агентное производство — декомпозиция на срезы, задачи работников, PR-ревью, миграции
    ℒ₃  продуктовая реальность клиента — живой рантайм, порты 18080 и 5432, HTTP 200 на домене клиента

Слои не пересекаются, и это проверяется в точке, где действие физически совершается, а не у вызывающего:

    Code(t) ∩ ℒ_factory = ∅                        изоляция Тарского: заводская семантика не течёт в продукт
    H_ProductWorker ∩ H_FactoryMeta = ∅            изоляция Рассела в RAG

# III. Законы

Порядок работы обязателен для каждого: **замер → разбор на корпусе → математическое предложение в этот
документ → и только потом правка.** Заплатки не принимаются. Чинить механизм, а не симптом.

## Ядро и периферия

Фабрика есть паутина убеждений по Куайну. У неё есть **ядро** `K` — механизмы, от которых зависит всякий
проект, — и **периферия** `Π` — цеха, порождающие находки. Требование оператора формулируется так:

    ядро идеально  ⟺  ∀ проект: он выполняется, пока над Π ведётся работа

То есть критерий готовности ядра — не «в нём нет дефектов», а **«дальнейшая работа ему не мешает»**.
Отсюда правило минимальной мутиляции, и оно проверяемо:

    правка π ∈ Π не имеет права потребовать правки k ∈ K
    |{k ∈ K : изменён при работе над Π}| = 0

Пока это число не ноль, ядро не готово, и всякая работа над периферией оплачивается остановками проектов.

**Демаркация.** Принадлежность к ядру определяется не важностью и не размером, а одним вопросом: **может ли
этот механизм удержать поток?** Цех, способный придержать, отменить или заблокировать продуктовую работу,
периферией не является — он в ядре по факту своего действия, как бы его ни называли, и обязан держать
ядерный стандарт. Цех, умеющий только **порождать находку**, — периферия.

    K = { приём требования, компиляция брифа, отправка, притязание, гейт и слияние,
          ёмкость и бюджет, необратимость статуса }
    Π = { дизайн-цех, фальсификация, аудит покрытия, наблюдение рантайма, суждение,
          сборка мусора веток }

**Отсюда — обязанность периферии.** Находка возвращается в поток вишлистом (закон 3) и ждёт своей очереди
по порядку допуска (закон 13). Периферийный цех не выносит запретов: запрет умеет сказать только «никогда»,
а находка — это «вот ещё работа». Механизм периферии, который придерживает поток, нарушает этот закон
независимо от того, верно ли его наблюдение.

**Порядок починки, по минимальной мутиляции.** Сперва ядро — до состояния, в котором оно перестаёт
требовать пересмотра. Затем периферия, и только теми правками, которые ядра не касаются. Список ниже
упорядочен этим правилом, а не величиной дефекта.

Не держатся либо не заслонены, в порядке того, сколько ценности освобождает исправление:

    ЯДРО — открытых пунктов нет: каждый ядерный закон выполняется в коде и заслонён тестом,
           способным упасть.

           Критерий Куайна подтверждён серией замеров: обе периферийные правки (законы 21, 22 и
           уточнение закона 17) затронули исключительно классы периферии (`JudgmentAgentClient`,
           `CriteriaEvidenceSelector`), ядро не тронуто: `|{k ∈ K : изменён при работе над Π}| = 0`.

    ПЕРИФЕРИЯ — открытых пунктов нет: законы 17, 21, 22 закрыты и заслонены (`JudgmentAgentClientLaw17Test`,
                `NonConcurrencyLaw21Test`, `FailureDemarcationLaw22Test`), включая обратные случаи.

Закрытое отсюда уходит молча. Приём требования, вывод из работы, множество решения, основание отказа,
предмет слияния, непараллельность, свидетельство, демаркация сбоев — держатся и заслонены; их место здесь занимать нечем.

## 1. Закон единственной точки применения

    |impl(I)| = 1   для всякого инварианта I

Проверка живёт там, где совершается действие, и ровно в одном экземпляре. Различие путей выражается
**аргументом**, а не второй копией. Тест на верность предиката — не тест на его применение; нужен и второй.

Отсеивать негодное у каждого читателя запрещено: читателей со временем больше, один пропущенный возвращает
дефект целиком.

**Держится.** Предикат носителя и его тип определены строго на `TaskEntity` (`isCarrier`, `carrierTaskType`,
`isCarrierOfType`, `isWishlistCompiler`, `isHousekeepingCarrier`); все читатели сведены к вызову метода
сущности, различие видов носителя выражено аргументом. Отправка в Jules сведена на `dispatchToGeneralPool`,
и запросы блокировки аккаунта вызываются ровно из одного места. Предикат доставки — один
(`hasRequiredMergeEvidence`, закон 4). Заслон: `TaskEntityLaw1CarrierTest` (структурный, со списком
написаний `has`/`hasNonNull`/`path`/`get` и с падением при ненайденном дереве исходников),
`ProjectFlowServiceLaw1JulesDispatchTest`.

## 2. Закон носителя и продукта

    T = T_прод ⊔ T_нос,   τ ∈ T_нос ⟺ carrier(τ)
    ∀τ (carrier(τ) → epic(τ) = ∅)

Правило о продукте не применяется к носителю, и наоборот. Ремонт носителя не есть требование клиента и не
имеет права заказывать продуктовый объём.

**Совместность с законом 7.** Возьмём носителя, закрывшегося без свидетельства слияния:
`carrier(τ) ∧ ¬landed(τ)`. Закон 3 требует, чтобы находка о нём стала вишлистом; закон 7 требует
`epic(w) = epic(τ)`; закон 2 даёт `epic(τ) = ∅`. Три выхода, и все три закрыты:

    завести эпик носителю            — запрещено вторым предложением закона 7
    привязать к продуктовому эпику   — запрещено законом 2: ремонт носителя заказал продуктовый объём
    подать вишлист с epic = ∅        — то самое «существует и невидимо одновременно» из закона 7

Значит `{2, 3, 7}` несовместимы на `T_нос`, пока дуга закона 3 обязана оканчиваться **вишлистом**. Ни один
из трёх законов не ослабляется: уточняется область определения ремонта. Ремонт — частичная функция, и её
область есть продуктовая часть разбиения:

    dom(ремонт) = T_прод                     носитель в область определения не входит
    carrier(τ) ∧ ¬landed(τ)  ⟹  находка записана в канал носителя, но не заказана как объём

Носитель при этом не исчезает: молчание запрещено законом 8 и есть ровно та потеря, против которой написан
закон 3. Разбиение `T = T_прод ⊔ T_нос` держится и **в записи**: канал носителя отдельный, иначе читатель,
считающий ценность по журналу, снова сольёт то, что закон развёл. Запрет заказывать клиентский объём по
заводскому факту — то же требование закона 22 (`ℒ₁ ↛ ℒ₂`), высказанное с другой стороны.

**Держится.** Носитель отсекается до подачи объёма и не порождает ни находки доставки, ни вишлиста, ни
эпика. Канал носителя отдельный: незаехавший housekeeping-носитель пишется в журнал дефектов категорией
`CARRIER_CHANNEL` с `featureId = null`. Носитель-компилятор против main не мерится вовсе — его продукт есть
декомпозиция, а не diff. Предикат заезда один и тот же (закон 1). Заслон:
`DeliveryRealityLaw2CarrierChannelTest`, включая обратные случаи.

**Следствие о файловом канале — держится.** То же разбиение обязано держаться не только на задачах, но и на
файлах:

    F = F_прод ⊔ F_нос,   f ∈ F_нос ⟺ f описывает работу фабрики о себе
    ∀f ∈ F_нос: f ∉ рабочее дерево продукта

Прежде разбиение обеспечивалось **уборкой на выходе**: гейт снимал `.eneik/records/*` из PR перед слиянием.
Уборка есть свидетельство нарушения, а не его отсутствия: к моменту снятия работа на порождение файла уже
потрачена, diff уже был им испорчен, а окно, в котором заводская запись лежала в продуктовом PR, уже
состоялось. Заслон, удаляющий `f`, и канал, неспособный `f` пронести, — разные вещи, и закон требует второго.
Теперь запрет стоит в самих точках записи (`commitFile`, `upsertFile`, `copyFile`): путь, признанный
заводской записью, отвергается на месте. Заслон:
`DeliveryRealityLaw2CarrierChannelTest.writingSitesRefuseFactoryRecords` — бьёт по настоящим точкам записи и
требует отказа; на прежнем коде красный. Уборка сохранена вторым рубежом.

**Множество точек записи закреплено.** Оно выводится сканером по телам методов транспорта и приравнивается
к названному множеству, поэтому точка, добавленная завтра, ломает равенство под любым именем; каждая точка
множества обязана отвергнуть заводскую запись. Регулярное выражение для этого негодно: неограниченный зазор
между построением URL и глаголом переходит границы методов и считает чтения записями, а ограниченный теряет
настоящие места с длинными телами.

**Остаточное, названное прямо.** Классификатор внедряется как `@Autowired(required = false)`: в живом
контексте бин есть и запрет работает (проверено), но отсутствие бина выключило бы запрет молча — «не смог
проверить» снова неотличимо от «проверил».

## 3. Закон замкнутости контура

Всякая находка любого департамента становится вишлистом и идёт обычной декомпозицией. Задача, созданная в
обход компиляции, не наследует эпик, а завершённость эпика — то, чем меряется ценность; такая задача
исполняется, сливается и не двигает ничего.

**Держится.** Реализация утверждённого дизайна подаётся вишлистом со статусом `pending` и идёт через
компилятор, наследуя эпик. Заслон: `DesignImplementationLoopClosureLaw3Test`.

**Область определения находки — не держится, и это источник перепроизводства.** Закон говорит «всякая
находка становится вишлистом», но не всякое наблюдение есть находка. Требуется различение, которого нет:

    требование не выполнено          — находка, порождает объём
    мы не сумели доставить его в этот раз — не находка, объём уже заказан

Замер по живому проекту: из 251 заявки **196 имеют один источник — `delivery_never_reached_main`**, и 155 из
них потом отброшены как ненужные. Клиент за всё время попросил **15**. То есть фабрика произвела о себе в
шестнадцать раз больше заказов, чем получила снаружи, и четыре пятых собственного производства выбросила.
Доля отброшенного и есть мера того, сколько из этого никогда не было работой.

Контур при этом замыкается сам на себя: отправка отклонена → работа не заехала в main → наблюдение «не
заехало» → заявка → задача → снова запрос сессии → снова отклонён. **Механизм, написанный чтобы ни одна
потеря не пропала, стал генератором потерь**, потому что считает собственную неудачу доставки новым
требованием клиента. Это то же смешение, что запрещает закон 2 на носителе, только здесь оно проходит по
продуктовой стороне и потому заслоном закона 2 не ловится.

Отсюда ограничение области: наблюдение «не заехало» о требовании, **уже** заказанном и не отменённом, есть
факт о доставке, а не о требовании. Ему место в журнале дефектов доставки; заказывать по нему объём заново
запрещено. Заявку порождает только то наблюдение, которое сообщает о требовании нечто, чего в нём ещё нет.



## 4. Закон предмета слияния

Слияние доставляет требование только если слитый diff несёт **код** — для роли, которая кодом обязана.

    landed(τ)  ⟺  ∃ r: merged(r) ∧ base(r) = main ∧ hasCode(r)     для роли, обязанной кодом
    landed(τ)  ⟺  ∃ r: merged(r) ∧ base(r) = main                  иначе

Фабрика намеренно разрешает агенту остановиться и записать блокер вместо бесконечного цикла — правило верное.
Но запись блокера, слитая в main, есть находка, а не доставка. Отсюда: предикат «доехало», по которому
департамент решает, есть ли о чём говорить, и предикат «доставлено», по которому считается ценность, обязаны
отвечать на один вопрос одинаково. Расхождение между ними — это в точности множество требований, о которых
никто не говорит.

**Держится.** Все три читателя — департамент реальности доставки, виджет заблокированного и сверка
против GitHub — спрашивают один предикат `hasRequiredMergeEvidence`, и у каждого есть заслон на оба случая.
Заслон: `DeliveryPredicateAgreementTest`, `ProjectFlowServiceTest`, `JulesDispatchServiceLaw4MergeEvidenceTest`
(задача со свидетельством слияния до опроса сессий не доходит, задача без него доходит).

## 5. Закон независимого свидетеля

    доставка   ⟸ реально слитый diff
    работа     ⟸ реально запущенный продукт
    дизайн     ⟸ реально отданный HTML

    done(τ) ⇏ merged(τ)
    ℒ₂ ⇏ ℒ₃    слияние всех PR не есть доставка ценности

Сторона, производящая результат, не может быть единственным подтверждением его корректности. Три
наблюдателя, ни один не заменяет другого. Эпик закрыт только при живой фальсифицирующей проверке на рантайме.

**Держится.** Заслон на слияние держится и заслонён (`MergeChokePointPokaYokeTest`). Утверждение «ни одна метрика ценности не считает status = done за доставку без проверки слияния» заслонено тестом `IndependentWitnessLaw5Test` (6/6), включая проверку неполных веток фич, отсутствие diff кода для кодовых задач, отрицательную фиксацию дефектов в `DeliveryRealityProducerService` и структурный аудит предикатов.

## 6. Закон погашения требования

Требование несёт плановый элемент, а не задача. Задача — попытка.

    repairs(w′) = τ            ⟺  sourceTaskId(w′) = τ
    slices(w)   = {v : originWishlist(v) = w}
    tasks(w)    = {τ : sourceWishlist(τ) ∈ {w} ∪ slices(w)}
    closure(w)  = tasks(w) ∪ {τ′ : τ′ ∈ tasks(w′) ∧ repairs(w′) ∈ closure(w)}
    fulfilled(w) ⟺ ∃ τ ∈ closure(w) : merged(τ)

Ремонтный бриф — **корень**, а не срез: компиляция создаёт под ним срезы, и задача ссылается на срез.
Замыкание, ищущее задачи прямо по вишлисту ремонта, не находит их никогда — по построению, а не по данным.
Требование погашено, если слит diff любого звена цепи. Замыкание конечно: каждое звено ссылается на задачу,
существовавшую раньше него. Область источников замыканием не расширяется: ремонт не становится отдельным
требованием, он гасит существующее.

**Держится.** Оба случая замыкания описаны тремя тестами (`aRequirementIsFulfilledWhenItsRepairMergedRatherThanItsFirstAttempt`, `aRepairDeliveredThroughItsSliceStillDischargesTheRequirement`, `aRequirementWhoseRepairHasNotMergedIsStillUnfulfilled`). Фикстуры `ClientDeliverableReadinessServiceTest` переведены на `initializeStatus`. Заслон зелёный (49/49 в `ClientDeliverableReadinessServiceTest`).

## 7. Закон принадлежности ремонта

    epic(w_ремонт) = epic(требования)      всегда
    ¬∃ новый эпик, порождённый находкой

Работа, ушедшая в эпик вне продуктового набора, исполняется, сливается и не двигает ничего: она существует и
невидима одновременно.

**Держится.** Носители отсекаются до подачи объёма и уходят в свой канал (закон 2, там же разбор
совместности). Продуктовые задачи наследуют эпик через каноническое сопоставление (`resolveCanonical`) и
сквозной проход по цепочке задач и вишлистов. Заслон: `DeliveryRealityLaw8SecondOrderRepairTest`,
`DeliveryRealityLaw2CarrierChannelTest`.

## 8. Закон вариантной функции

    ∀ цикл L ∃ v: Состояние → ℕ,  v ограничена снизу,  v строго убывает на каждом обороте L

    отправка задачи:   v = A_max(τ) − A(τ),  A_max = 2·|{a : status(a) ≠ decommissioned}|
    компиляция брифа:  v = A(w) − compileAttempts(w),  обороты разрежены кулдауном
    повторы носителя:  v = MAX_RETRIES − retryCount(τ)
    оживление:         v = 1 − resumeCount(τ)
    ремонт:            v = A(w) − repairDepth(w),  глубина принадлежит требованию, не задаче
    возврат бюджета:   каждый возврат потребляет строго более позднее событие канала

Цикл без такой величины — проживание, а не повтор, и запрещён. Исчерпание величины поглощающе и обязано быть
**записано**: требование, которое ремонт не доставил за отведённые обороты, перестаёт порождать работу и
остаётся названным как недоставленное. Молча прекращать нельзя — непорождающее и невыполненное требование,
о котором нигде не сказано, есть ровно та потеря, ради устранения которой написан закон 3.

**Начальное значение выводится, а не назначается**:

    A(w) = f(наблюдения о том, на каком заходе компиляции этого проекта удавались)
    вниз  — по свидетельству о брифе (компилятор ответил пустотой)
    вверх — по успеху на самой границе (план принят на последнем доступном заходе)
    собственная непересмотренная константа не двигает предел ни в одну сторону

Условие корректности снимать нельзя: `A(w)` конечен, списание строго убывает на каждой попытке, о которой
что-то установлено о брифе. Меняется начальное значение, а не характер функции.

**Скорость расхода величины — часть закона, а не подробность реализации.** В этом репозитории уже записана
половина: кулдаун ограничивает, как **часто** оборот происходит, и не может ограничить, **сколько раз** он
произойдёт. Верна и обратная половина, и без неё закон неполон:

    величина без разрежения ⟹ она расходуется за время t_расх, и если t_расх < t_условия,
    требование гибнет от преходящего, а не от собственной исчерпанности

Величина может убывать правильно и всё же не спасать: если притязание возвращается в очередь и берётся
снова тотчас, предел вычерпывается за минуты, а условие живёт десятками минут. Отсюда: **у всякой вариантной
функции два параметра — предел и разрежение, и назначать один без другого нельзя.** Предел отвечает на
«сколько раз», разрежение — на «за какой срок»; порознь они не дают того, ради чего написан закон.



* Ревьюерский путь — **держится**: сведён к единой реализации и получает ротацию, освобождение притязания
  при отказе и величину попыток. Заслон: `ProjectFlowServiceLaw1JulesDispatchTest`.
* Оборот ремонта второго порядка и поглощающее условие — **держится**: глубина считается по цепочке задач,
  второй порядок наследует продуктовый эпик, исчерпание предела пишется в журнал дефектов, а не сбрасывается
  молча. Заслон: `DeliveryRealityLaw8SecondOrderRepairTest`.
* Вариантная функция, пределы циклов и временные окна — **держится**. Начальное значение $A(w)$ выводится из эмпирической истории проекта (`deriveInitialCompileCeiling`), поднимается при успехе на границе (`raiseCompileCeilingIfTheProbeSurvivedAtTheBoundary`) и зажимается вниз при пустом ответе компилятора (`clampCompileCeilingOnEmptyCompilerAnswer`). Цикл слепых заходов управляется единственным предельным условием ($v = \text{forcedUnblockBlindCycleThreshold} - \text{blindCycleCount}$ завершает цикл без зависания в 60-минутном окне доверия). Четыре временных окна заземлены на наблюдаемые факты канала: чистка эпиков проверяет факт активной компиляции (`compilationInFlight`), блокировка задач немедленно распознаёт осиротевший `in_progress` без клейма (`unclaimed_in_progress`), детекция узких мест мгновенно фиксирует структурное истощение пула (`poolStructurallyDepleted`), а кулдаун оркестрации проверяет факт занятости компилятора. Заслоны: `VariantFunctionLaw8Test` (7/7), `DeliveryRealityLaw8SecondOrderRepairTest`, `ProjectRetirementLaw8Test`.

* Взаимная блокировка компиляции — **держится**. Контур был замкнут: восстановление возвращало заявки в
  `pending`, завершение задачи захватывало только из `compiling`, а отправка не бралась за эти заявки, пока
  задача активна; убывающей величины не было ни у одной стороны. Разомкнут двумя правками: захват допускает
  и переход `pending → finalizing` (завершение, держащее PR и план, вправе забрать заявку, сброшенную чужой
  чисткой), и выход по `IN_PROGRESS_ELSEWHERE` освобождает захват сессии, а не ждёт истечения аренды. Заслоны:
  `JulesDispatchServiceTest.admitWishlistCompilationCompletionClaimsPendingWishlistsWhenCompilingWasReset` и
  `...completeWishlistCompilationReleasesPrOpenedClaimWhenInProgressElsewhere` — оба утверждают свойство и на
  прежнем коде краснели; `StrandedFinalizingSweepServiceTest` держит аренду самого `finalizing`.

## 9. Закон бюджета

Пусть бюджет `B` со счётчиком `c` ограничивает повторы относительно предмета `X`, а `Ev(X)` — множество
событий, являющихся свидетельством о `X`.

    Δc = 1  ⟺  произошло e ∈ Ev(X)

| бюджет | предмет `X` | `Ev(X)` |
|---|---|---|
| `compileAttempts(w)` | бриф | компилятор ответил: пустой ответ **или** принятый |
| `A(τ)` = \|{s : task(s)=τ ∧ refused(s)}\| | потраченная ёмкость | всякий отказ; вина не вменяется |
| `retryCount(τ_нос)` | наши просьбы к одному носителю | каждая просьба |
| `resumeCount(τ)` | оживление задачи | одно на задачу |

Попытка, не дошедшая до компилятора, бюджет брифа не тратит. Попытка, ответ на которую отвергла **наша**
проверка, — тоже: о брифе она не сказала ничего.

**Держится.** Пустой ответ компилятора выделен именованной константой, и только он тратит бюджет брифа;
отказ внутреннего валидатора схемы возвращает попытку с ограничением снизу `c ≥ 0`. Заслон:
`WishlistCompileBudgetLaw9Test`, включая обратный случай.

**Внешний бюджет — не держится, но не потому, что счёта нет.** Счёт есть, и устроен он верно. У аккаунта
хранится выученная суточная ёмкость `estimatedDailyCapacity`: она растёт на настоящем успехе, достигшем
потолка, и сжимается **только** на настоящем отказе по суточному лимиту — пересмотр по свидетельству, а не по
собственному убеждению. Рядом `consecutiveApiBlockCount` даёт экспоненциальный откат. Есть и мост
`reclassifyPreconditionDailyLimitedAccounts`, прямо признающий безымянный `failed_precondition` суточным
лимитом. Механизм полон.

Не держится он потому, что **свидетельство до него не доходит**:

    отказ наступает на создании сессии  ⟹  строки сессии не появляется
    все три механизма читают строку сессии  ⟹  они не видят ничего
    «ничего не записано» ≡ «ничего не случилось»  ⟹  аккаунт остаётся `idle`

Классификатор `dailyLimitOrQuota` ищет слова `quota`, `daily`, `rate limit`, `resource_exhausted` или код
429; внешняя сторона отвечает `400 FAILED_PRECONDITION` без единого из них, отказ падает в
`PRECONDITION_UNSPECIFIED` и по §12 не вменяется никому. Мост, который должен был это починить, читает
`closure_reason` **существующей** сессии — требует ровно того, чему отказ помешал возникнуть, и потому
ограничитель слеп там, где он нужен.

Отсюда общая форма, а не частный случай: **путь свидетельства не должен зависеть от того объекта, чьё
несоздание и есть свидетельство.** Отказ до создания — тоже событие, и он обязан иметь собственную запись,
независимую от сущности, которая не родилась. Пока её нет, ограничитель слеп именно там, где он нужен, и
фабрика тратит, полагая себя здоровой.

**Третье, и оно тяжелее.** Отказ по внешней квоте списывается с `A(τ)` наравне с прочими: в журнале это
«attempt 1/14». Значит исчерпание чужой суточной квоты за четверть часа обнулит предел четырнадцати требований
подряд, и каждое будет объявлено недоставленным, хотя о самих требованиях не установлено ничего. **Фабрика
обращает собственный перерасход в вердикты против требований клиента** — то самое, что запрещает закон 12.
Отказ, различённый как исчерпание внешнего бюджета, обязан приостанавливать требование до пополнения, а не
списывать его попытку.

## 11. Закон множества решения

    ¬∃ путь x → done       ⟹  x покидает множество решения ровно один раз, в данных
    о x ничего не установлено ⟹  x множество НЕ покидает

Элемент, структурно неспособный дойти до «выполнено», обязан покинуть знаменатель — иначе решающий код
блокируется молча. Но незнание из знаменателя не выводит.

**Держится.** Читатели знаменателя исключают только структурно недостижимые элементы. Рычаг подчинения TOC (`TocSubordinationLever`) разделяет состояние наблюдения на три истинностных значения: установленное здоровье (`isEstablishedHealthy`), установленный отказ (`isEstablishedUnhealthy`) и незнание (`isUnestablished` при `healthStatusCode == null`). Незнание не открывает ограничение и не закрывает отложенные наблюдения ложным "deny". Заслон: `TocSubordinationLeverTest` (12/12 тестов), `DecompositionVerdictTest`, `FailingReviewCompositionTest`, `ClientDeliverableReadinessServiceTest`.

**Откуда берётся `null`: вопрос о здоровье иногда не задаётся вовсе.** Замер по журналу лаунчера:
`launch` — 3, `healthcheck` — **2**, `teardown` — 3, в порядке
`launch → healthcheck → teardown | launch → teardown | launch → healthcheck → teardown`. Один запуск из трёх
поднял продукт и снёс его, **ни разу не спросив о здоровье**. Именно такой цикл и даёт
`launchSuccess = true, healthStatus = null`: это не «продукт болен», это «мы не спрашивали». Рычаг же
подчиняет работу на основании вопроса, который не был задан.

Требуется третье состояние — установлено здоровым, установлено нездоровым, не установлено — и подчинение
строго на втором. Отдельно: пропуск пробы между `launch` и `teardown` — сам по себе дефект наблюдателя по
закону 5, потому что свидетель, снёсший предмет, ничего у него не спросив, свидетелем не является.

## 12. Закон основания

    запрет действия a состоянием S обоснован  ⟺  S есть свидетельство о предмете a
    denial(действие, состояние) = c,  где c — конъюнкт, который не выполнился
    отказ без читаемой причины  ⟹  он не может быть основанием поглощающего вердикта

Состояние, вынесенное по одному элементу, свидетельством о несвязанном элементе не является. Провальное
ревью говорит о своём PR и ничего не говорит о том, безопасно ли компилировать другой бриф.

    терминальность проекта (FROZEN, ACCEPTED, ARCHIVED)  — свидетельство: работать нельзя вовсе
    BLOCKED_BY_DUPLICATE_CONTENT   — дубликаты порождаются компиляцией, это о ней самой
    GITHUB_RATE_LIMITED            — компиляция обращается к GitHub, предел о ней
    BLOCKED_BY_REVIEW / _BY_TASK / _BY_FAILED_FRONTIER  — условия ОТДЕЛЬНЫХ элементов, о компиляции молчат

Довод «новая декомпозиция ждёт своей очереди» запрет не спасает: это сдерживание WIP, а не утверждение о
свидетельстве, а сдерживание выражается **порядком** (закон 13), не запретом, потому что запрет умеет
сказать только «никогда».

**Держится.** Компиляция отказывается только по состояниям, которые суть свидетельство о ней самой;
состояния отдельных задач и ревью её не запрещают. `BLOCKED_BY_FAILED_FRONTIER` оставлен запрещающим,
потому что денящим не наблюдался, а менять неизмеренное — превращать правку в догадку. Заслон:
`OperationalPolicyServiceTest`, все три обязательных случая (провальное ревью разрешает, дубликат запрещает,
терминальный проект запрещает).

**Сообщения.** Одно сообщение — один конъюнкт; норма пишется INFO, не WARN; неизменный факт записывается
один раз, а не на каждом такте. Сообщения, называющие несколько причин сразу, запрещены.

## 13. Закон ёмкости

Департаменты делят одну ёмкость — живые аккаунты.

    порядок допуска:  компилятор ≺ продуктовая работа ≺ самопорождённая ≺ носители фабрики
    ∀ o: spend(o, W) наблюдаем, и при исчерпании окна разложение называется целиком

Выражается порядком, не запретом. Общая ёмкость обязана быть **относимой к потребителю**: порядок допуска —
утверждение о том, кто уступает кому, и применить его к расходу, который нельзя разложить по потребителям,
невозможно в принципе. Предел, съеденный неизвестно кем, повторится в следующем окне и в каждом следующем.

**Держится.** Состояние бюджета шардировано по отпечатку токена; величины остатка, предела, времени сброса
и расхода определены строго на контексте пары ⟨отпечаток токена, окно⟩, так что исчерпание одного токена не
парализует фабрику под другими. Ключи операций нормализуются до базового пути, что делает их множество
конечным. Цена обхода внешней системы ограничена остатком работы, а не накопленной историей: терминальные PR выбывают из опроса, неотносимые строки удерживают spend=0, снимок PR кэшируется на такт. Заслоны: `GitHubApiBudgetLaw13Test`, `GitHubSweepBudgetEfficiencyTest`.

Не установлено: съедает ли дизайн-цех ёмкость у продуктовой работы — он ходит своим тактом и в порядке
допуска не участвует. Требуется замер и покрытие класса задач, доходящих до отбора аккаунта.

## 14. Закон убеждения о внешней системе

    ceiling(a) ← ceiling(a) + шаг        при accepted(s) ∧ occ(a, t(s)) ≥ ceiling(a)
    ceiling(a) ← max(1, ⌊k · откат⌉)     при отказе, где k = occ(a, t) в момент отказа

Внешние пределы суть гипотезы. Рост только от настоящего успеха, падение только от настоящего отказа,
никогда — от собственной константы. Убеждение, замороженное на пределе, которого уже нет, не
пересматривается никогда, и это запрещено: для каждого поглощающего вердикта, вынесенного по внешнему
условию, обязан существовать путь **пробы**, а не только ожидания.

Различать: `A(w)` и `MAX_RETRIES` — **наши** проектные решения, не гипотезы о чужой системе, и этому закону
не подчиняются.

**Держится.** Исходы отправки разделены на взаимно непересекающиеся классы, и канал опровержения ёмкости
отделён от неклассифицированного: неизвестное не двигает потолок ни вниз, ни вверх и никого не обвиняет.
Отказ по одновременной ёмкости пересматривает оценку вниз от фактически наблюдённой точки занятости, успех
на потолке — вверх с шагом зондирования; значение из конфигурации убеждение не двигает. Всякое движение
пишется в журнал с прежней оценкой, пересмотренной, наблюдённой занятостью и основанием. Заслон:
`AccountHealthServiceLaw14Test`, `JulesRefusalKindsTest`.

## 15. Закон готовности

    ready(P, t)   ⟺ decompositionComplete(P, t) ∧ ratio(P, t) = 1
    trigger(P, t) ⟺ ready(P, t) ∧ ¬ready(P, t−1)

Полнота недостижима по построению, пока проект активен: фальсификация, покрытие и наблюдение непрерывно
добавляют работу. Значит механизм, ждущий готовности, срабатывает на **фронте**, а ждущий «продукт
закончен» не сработает никогда.

**Держится.** Готовность оценивается по фронту: полнота декомпозиции и порог отношения (параметр, а не
константа) либо достижение терминального фронта фальсификации; запуск строго на нарастающем фронте, с
названной причиной удержания. Заслон: `DesignShopOrchestrationServiceLaw15Test`.

## 16. Закон предмета ревью

    review(τ)  ⟹  ∃ r: артефакт ревью, принадлежащий τ

Квантор по задаче, а не по проекту. Задача в ревью без собственного артефакта продвинуться не может:
рецензенту нечего смотреть, а отправка в ревью при этом разрешена и будет отправлять в пустоту.

    τ в ревью, артефакта нет вовсе   — дефект: состояние без выхода
    τ в ревью, её артефакт уже слит  — норма: задача вот-вот уйдёт дальше

**Держится.** Выход: задача, чья роль обязана кодом и у которой на main ничего нет, уходит в `failed`, а
заявка освобождается. Вход трёхзначен: артефакт есть — допуск; сессия активна без артефакта — решение
откладывается (защита от гонки по закону 11); сессия терминальна и артефакта нет — `failed` и освобождение
заявки. Заслон: `ReviewAdmissionLaw16Test`.

Не установлено: хребет потока сравнивает `reviewTasks > 0` с `openReviews == 0` — агрегат против агрегата.
Требуется считать задачи в ревью, у которых нет ни одной строки ревью, и называть их число.

## 17. Закон свидетельства

    evidence(τ) выбирается по criteria(τ), не по позиции в потоке
    ¬settled(τ) ∧ truncated(evidence)  ⟹  ограничение принадлежит спрашивающему, не отвечающему

Свидетель, которому отказано в свидетельстве, свидетелем не является. Независимость бесполезна, если
свидетелю показывают первые N символов подряд: решающее оказывается за обрезом не потому, что его нет, а
потому, что оно стояло дальше по алфавиту имён файлов.

**Держится.** Отбор свидетельства по критериям инкапсулирован в `CriteriaEvidenceSelector`:
$\mathrm{dom}(\text{отбор по criteria}) = \{ \tau : \mathrm{criteria}(\tau) \neq \emptyset \}$.
Для запросов с diff свидетельство отбирается по файлам с сохранением файлов целиком и ранжированием по критериям приёмки.
Для запросов без diff при наличии критериев (`extractCriteria`) разделы свидетельства ранжируются по релевантности критериям (`selectNonDiff`) с сохранением формулировки инварианта и итогового вопроса; опущенные разделы явно именуются в дисклеймере.
Для запросов без критериев уведомление честно констатирует отсутствие критериев для ранжирования и предписывает отвечать `UNDECIDABLE`, если решающее могло остаться в опущенной части, исключая дефект недостоверного сообщения. Заслон: `JudgmentAgentClientLaw17Test` (4/4), `EvidenceSelectedByCriteriaTest`, `UnsettledGroundNamesTheAskerTest`.

## 18. Закон неразрешённого вопроса

    unsettled(τ)  ⟹  ¬decided(τ)
    ask(τ) снова  ⟸  ground(τ) изменилось
    stop(τ)       ⟸  ground(τ) повторилось

Вердикт, ничего не решивший, решением не является. Повторный вопрос есть оборот цикла, и по закону 8 ему
нужна убывающая величина; она не назначается, а наблюдается — это **основание отказа**. Пока каждое новое
основание отлично от прежнего, узнаётся что-то новое; как только основание повторилось, вопрос закрывается
как неразрешимый, с записанным основанием, а не молча.

**Держится.** Неразрешённая задача допускается к повторному суждению, пока её основание не повторилось;
при повторении вердикт поглощается и опрос прекращается. Заслон: `UnsettledQuestionIsAskedAgainTest`.

## 19. Закон перезаказа

    order(w_ремонт) ≠ order(τ_провалившейся)   всегда, когда основание отказа записано
    ground(отказ) ⊆ order(w_ремонт)

Заказ, тождественный тому, который отказ породил, не есть новый оборот цикла — это тот же оборот,
повторённый: исполнитель получает ту же задачу, в том же виде, с тем же незнанием, и производит тот же
результат. Отказ, чьё основание записано, но не передано следующему исполнителю, эквивалентен отказу без
основания. Ремонтный бриф обязан назвать вердикт предыдущей попытки и его причину — и не выдумывать
причину там, где она не записана.

**Держится.** Ремонтный бриф несёт вердикт предыдущей попытки и его основание, и не выдумывает основание
там, где оно не записано. Заслон на оба случая: `DeliveryPredicateAgreementTest`
(`aReissuedOrderCarriesTheGroundOfTheDenialItAnswers`, `anUnrecordedGroundIsNotInvented`).

## 20. Закон необратимости и живости

**Безопасность.**

    S1  ∀τ: |{s : task(s)=τ ∧ живая(s)}| ≤ 1
    S2  terminal(τ) ⟹ статус τ более не переписывается
    S3  carrier(τ) ⟹ его PR не сливается как продуктовый
    S4  ∀ путь к слиянию: он проходит через гейт

**Живость.**

    L5  ∃ допустимая работа ∧ ∃ свободная ёмкость ⟹ за конечное число тактов что-то продвигается
        уточнение: ёмкость читается у ТОГО ресурса, к которому действие привязано
    L6  внешнее условие изменилось ⟹ фабрика узнаёт за конечное число тактов
    L7  всякий цикл завершается (закон 8), всякое ожидание ограничено (закон 14 либо кулдаун)

**Anti-Starvation.** Смена статуса атомарно пишет `t_state`; при `null` нижняя граница
`min(t_heartbeat, t_updated, t_created)`. Кулдаун с полным джиттером `U(T_base, T_ceiling)`. Гистерезис:
отказ `k ← min(k+1, k_max)`, успех `k ← max(0, k−1)`. `offline` со свежим пульсом релаксирует в `idle`.

**S2 — держится.** Терминальность `{done, failed, spike_completed}` защищена в точке смены статуса:
перезапись терминального статуса иным блокируется исключением, повторная запись того же идемпотентна,
первичное назначение отделено. Заслон: `TaskEntityLaw20Test`.

Заслон S2 имеет цену, которую обязан оплатить сам закон: фикстуры, строившие состояние перезаписью
терминального статуса, теперь падают, и вместе с ними падают заслоны законов 6 и 11. Инвариант верен,
фикстуры обязаны строиться через первичное назначение.

**S4 — держится.** Ungated-обход устранён, и решение о слиянии продуктового кода принимается в одном
сервисе. Заслон переписан со списка запрещённых имён на **счётное утверждение о множестве точек слияния**:
пусть `M` — множество мест в исходниках, откуда уходит слияние продуктового кода в защищённую ветку; S4
требует, чтобы каждый элемент `M` был загейчен, а это проверяемо только если `M` закреплено — о
неперечисленной точке нельзя показать, что она загейчена. Поэтому заслон фиксирует `M` и падает на любом
добавлении, где угодно в дереве и под любым именем.

`M`, измеренное на реальном потоке: `executeMerge` (загейчено, `rejectByFactoryPokaYoke` строго до выдачи
запроса), слияние закрывающего PR ветки фичи в main, слияние fix-PR в ветку треда. Вне `M` намеренно
оставлены record-PR (`mergeRecordPullRequest`): они несут заводскую запись — вердикт ревью, отчёт аудита, —
а не продуктовый код, и мерить их продуктовым гейтом значит смешивать каналы, разделённые законом 2.

Заслон: `AutoMergeLaw20InvariantS4Test` — три утверждения: вне сервиса-гейткипера никто слияния не выдаёт,
множество точек внутри него закреплено, и в загейченной точке заслон спрашивается **до** выдачи запроса, а
не после.

**Связанный ресурс делает живость условной.** Если действие привязано к единственному экземпляру ресурса
по решению — как компилятор к своему аккаунту, — то свободная ёмкость в другом месте живости не даёт: L5
выполняется только при свободной ёмкости **у связанного** ресурса. Замерено 2026-09-05: при семи живых
аккаунтах диспетчер за 34 попытки выбирал один и тот же, потому что вся допустимая работа была
компиляцией; тот аккаунт отказывал, и поток стоял шесть часов при шести свободных аккаунтах рядом.

Привязка — решение оператора, не дефект, и здесь она не оспаривается. Оспаривается умолчание: L5, записанный
без уточнения, обещает продвижение там, где механизм его дать не может. Цена привязки должна быть видна тому,
кто её выбирает.

**S1 — не заслонён**: требуется тест на реальной базе — после двух конкурентных отправок одной задачи живая
сессия одна. **L6 — не заслонён**: для каждого поглощающего вердикта по внешнему условию требуется
названный механизм, который его пересматривает.

## 21. Закон непараллельности круга и мнения

    |{w : source(w) = self_falsification ∧ w открыт}| ≤ 1     на проект
    |{τ : аудит покрытия для w ∧ ¬terminal(τ)}| ≤ 1           на вишлист
    ожидание мнения ограничено сроком; по истечении круг закрывается непродвинутым

Новый аудит покрытия допускается только когда прежний терминален **и** старший слитый PR этого вишлиста
продвинулся, то есть появился новый предмет проверки. Дизайн-ревью и философская фальсификация могут
задержать круг, но не отменить поток.

Перед отправкой аудита стоят три затвора:

    G₁  готовность:    decompositionComplete(P) ∧ selfFalsificationReadyRatio(P) ≥ θ
    G₂  нет открытого: ¬∃ w: source(w)=self_falsification ∧ status(w) ∈ {pending, compiling}
    G₃  есть новое:    diff(merged PR > highest_pr_number_audited) ≠ ∅

**Держится.** Ограничения на единственность открытого круга самофальсификации ($G_2$), затвор готовности ($G_1$), диффовый затвор ($G_3$), единичный незавершённый аудит покрытия на вишлист, монотонность меток и 48-часовой предел ожидания мнения подтверждены. Заслон: `NonConcurrencyLaw21Test` (7/7).

## 22. Закон демаркации сбоев

    ℒ₁ ↛ ℒ₂                     сбой инфраструктуры есть свидетельство об ℒ₁ и не имеет права порождать
                                задачу на изменение кода клиента
    контрпример(e)           ⟺  e есть наблюдение состояния артефакта C_sha
    инструментальный_сбой(e) ⟺  e есть сбой среды наблюдения (таймаут git, память хоста, падение демона)

Инструментальный сбой не изменяет апостериорную оценку надёжности продукта: он уменьшает доступность
инструмента и адресуется самолечением ℒ₁.

**Внутренняя самофальсификация.** Фабрика фальсифицирует и собственные гипотезы: цех, за `N` тактов не
продвинувший метрику ℒ₃, объявляется мудой и уходит в `standby`; гипотезы о пределах внешних систем
пересматриваются зондами, а не захардкоженными эвристиками (закон 14).

**Держится.** Инструментальные сбои среды наблюдения (`observation.isInstrumentFailure() == true`, таймаут лаунчера, сбой демона) никогда не открывают продуктовое ограничение, не создают продуктовых вишлистов, исключаются из детектора сдвига надёжности продукта и маршрутизируются строго в дефекты фабрики (Kaizen). Заслон: `FailureDemarcationLaw22Test` (5/5).

## 25a. Закон приёма требования

    admit(w)   приём нового клиентского требования
    retire(P)  вывод прежнего проекта из работы

    dom(admit) = { w : content(w) ≠ ∅ }      единственное предусловие — непустой бриф
    admit ⊥ state(P_прежн)                   приём не зависит от состояния прежнего проекта
    admit ⊥ availability(внешние системы)    и от того, отвечают ли Jules и GitHub

    effects(admit) ⊆ собственные данные фабрики
    effects(retire) ∩ внешний мир ≠ ∅   ⟹   retire не входит в атомарность admit

Приём требования и вывод прежнего проекта из работы — два разных акта. Связанные в один атомарный, они
ставят возможность начать новую работу в зависимость от того, удалось ли закрыть чужие PR и отменить чужие
сессии. Это запрещено законом 12, высказанным с другой стороны: состояние прежнего проекта не есть
свидетельство о том, можно ли принять новый бриф. Единственное свидетельство о брифе — сам бриф.

**Внешнее действие не откатывается.** Транзакция, охватывающая внешний вызов, при отказе делает вид, что
его не было, и оставляет мир в состоянии, которого нет ни в одной ветви её собственной логики: чужие PR уже
закрыты, а проекта, ради которого их закрывали, не существует. Экстент атомарности задаётся не тем, где она
написана, а тем, что в неё втянуто.

`retire` есть обычный оборот цикла и подчиняется закону 8: у него своя вариантная функция, своё свидетельство
и записанное поглощающее условие. Его неуспех не отменяет `admit` — он означает лишь, что ёмкость
освободится позже. Сдерживание выражается **порядком** (закон 13), не запретом: новый проект принят
немедленно и берёт ёмкость по мере её высвобождения, а не ждёт, пока прежний будет добит.

`retire` обязан быть идемпотентным: внешние эффекты уже случились, повтор не имеет права считать их
несделанными и не имеет права делать их дважды.

**Держится.** Приём разделён: `admitProject` транзакционен и пишет только фабричные локальные данные (проект, начальный вишлист, локальная заморозка прежнего активного проекта); уборка и провижининг вынесены наружу, отказ провижининга записывается в `factoryStatus`. Структурный заслон реализован как белый список над объявленными полями сервиса, исключающий любые внешние сетевые клиенты во всём транзитивном графе вызовов приёма. Цикл вывода из работы (`retire`) подчиняется закону 8 и закону 9: вариантной функцией служит `MAX_RETIRE_ATTEMPTS - retireAttempts(P)`, списание происходит только при реальном обращении к внешним системам, исчерпание не молчит и пишет запись в `defect_journal`, отменённое не отменяется повторно. Заслоны: `ProjectAdmissionLaw25aTest` (4/4) и `ProjectRetirementLaw8Test` (5/5).

**Второе место того же принципа — держится, заслонён у́же свойства.** Тот же экстент атомарности нарушался у
другого приёма: мьютекс допуска пакета ревью держал строку проекта `FOR UPDATE` и через сетевую отправку в
Jules. Замер живой: два невыдержанных ожидания замка и три предупреждения об удержанном соединении; после
разведения допуска и отправки — по нулю. Заслон добавлен
(`ProjectAdmissionLaw25aTest.structuralDemarcationInvariantForReviewFallbackAdmission`) и зелёный, но он
проверяет **один именованный метод** и чёрный список из трёх идентификаторов в его теле, без транзитивных
вызовов. Прежний заслон 25a был белым списком над объявленными полями по всему графу вызовов приёма — то есть
новый слабее по роду, а не сильнее, хотя назван обобщённым.
Свойство закона говорит о **всяком** приёме: `∀ приём a: внешний вызов ∉ транзакция(a)`. Перечень, у́же
предиката, который он стережёт, — пункт 10 опровергнутого; здесь этот класс дефекта появился **третий раз, и
уже внутри заслона, написанного чтобы закрыть второй**. Отсюда правило: обобщить заслон значит сменить его
род — с перечня мест на утверждение о множестве мест, — а не дописать в перечень ещё одну строку.

# IV. Опровергнутое — не воскрешать

Все одной формы: вывод выдавался за измерение.

1. **«У рычага TOC ноль разрешённых наблюдений».** Считалось по одной величине, а промоция считает по
   другой. Не поднимается из-за подменённой величины, а не из-за нехватки данных.
2. **«Фаза декомпозиции должна завершаться».** Не должна и не может: девять сервисов порождают вишлисты
   непрерывно, множество открытых брифов не опустеет никогда.
3. **«Бюджет должен списываться только на отвеченных попытках».** Ломает завершаемость: при вечно занятом
   канале вариантная функция не убывает. Различать вердикты, а не менять её.
4. **«Реализовано» без сборки.** Наблюдалось дважды. Второй раз — два коммита подряд объявили законы
   держащимися, вызывая метод, которого нет, и неся тесты, которые не компилировались: гарнитуры,
   названные доказательствами, не запускались ни разу, при том что CI гоняет `mvn clean test` на каждый
   push, то есть красный CI на main никем не читался. Строка о статусе пишется только после прогона,
   чей вывод виден.
5. **«`FAILED_PRECONDITION` означает исчерпание одновременных сессий».** Взято из надписи в интерфейсе
   Jules, а не из ответа Jules. Тот же статус приходит и как «Repository access is not ready».
6. **«Миграция навсегда закрепила настройку в базе».** Миграция присваивает один раз и ничего не запирает.
7. **«`teardown` лаунчера всегда безопасно звать».** Его `success` не означает, что что-то погашено: при
   потерянном указателе в памяти он возвращает успех, не сделав ничего.
8. **«Привязка компилятора к аккаунту — про квоту, значит её можно ослабить».** Ослабление отменено
   оператором: компилятор работает на своём аккаунте и только на нём.
9. **«Отсеять негодные задачи у каждого читателя».** Фильтр поставили на один список отбора из двух, и
   дефект вернулся через второй.
10. **Тесты, которые не могут упасть.** Подстановка на вызов, которого код больше не делает, возвращает
    пустоту — и тест, ожидающий пустоту, проходит, не проверяя ничего. Того же рода: структурный заслон,
    чей список написаний уже́ предиката, который он стережёт; заслон, возвращающий зелёное при ненайденном
    дереве исходников; и красный тест, названный доказательством, — он падает и при исправном коде.
    Четвёртое написание того же: **проверка с трёхзначным исходом, чьё «не смог проверить» обрабатывается
    как «проверил, всё хорошо»**. Если из `VISIBLE` / `MISSING` / `UNKNOWN` вызывающий останавливается только
    на `MISSING`, то отказ листинга, исключение и упор в предел пагинации проходят наравне с успехом. Такая
    проверка не может провалиться и потому ничего не стережёт. Правило: у проверки три исхода, и третий
    обязан быть виден в результате, а не растворяться во втором.
11. **«Зависимость — это порядок работ, поэтому мёртвую можно не ждать».** Несовместимо с правилом, по
    которому зависимый при мёртвой зависимости есть тупик и уходит в `blocked`: допуск снимает блокировку,
    восстановление поднимает задачу, тратя единственный автоматический повтор, и блокировка повторяется по
    той же зависимости. Расход единственного восстановления, а не восстановление.
12. **«По части припаркованных задач работа не заказывается вовсе».** Получено вычитанием числа обновлённых
    узлов свидетельства из числа задач — величин разного рода. Свод называет то и другое порознь.
14. **Первое объяснение, совпавшее с наблюдением, принято за диагноз.** Трижды за один вечер, и каждый
    раз объяснение было единственным рассмотренным. «Фабрика простаивает» — замер двухчасовой давности,
    пересказанный в настоящем времени; конкурент «состояние изменилось» не рассматривался. «Ревью через
    Gemini сломано» — подпись в логе принята за данные о состоянии системы, тогда как Gemini был снят
    директивой оператора; едва не отправило чинить намеренно убранное. «Поток встал» — из «нет слияний
    час»; конкурент «медленно по конструкции: сводка раз в 15 минут и целая сессия на пакет» объяснял то же
    самое и был верен. Отсюда: причина не называется, пока не выписаны минимум два объяснения, дающих то же
    наблюдение, и пока не названо наблюдение, которое убьёт предпочитаемое. Строка лога, имя метода,
    комментарий — данные о том, **что кто-то написал**, а не о том, что делает система.

13. **«Повторный ремонт блокируется заслоном по существующей записи».** Заслон ключуется по чинимой задаче,
    а у провалившейся задачи ремонта ключ свой.

15. **«Конвейер стоит, потому что компилятор привязан к одному аккаунту».** Гипотеза объясняла наблюдение
    (Jules отказывает всегда через `eneikdru`, шесть аккаунтов с ключами простаивают) и держалась несколько
    тактов как рычаг, поданный оператору. Опровергнута прямым опытом: при привязке к другому аккаунту Jules
    отказывает тождественно — тот же `FAILED_PRECONDITION`, сменилось лишь имя в строке отказа. Отсюда
    правило поверх пункта 14: **рычаг, который подан, но не потянут, — это гипотеза, а не вывод**, и держать
    его как объяснение нельзя. Отдельно: опыт был поставлен вопреки пункту 8, где ослабление привязки уже
    отменено оператором; правило модели старше моей догадки, и проверять его следовало спросив, а не молча.

16. **«Заявки застряли в `finalizing`».** Выведено из кода: раз исход `IN_PROGRESS_ELSEWHERE` наступает при
    пустом захвате, а захват берётся переводом `compiling → finalizing`, значит строки лежат в `finalizing`.
    Опровергнуто одним запросом: среди 245 заявок проекта в `finalizing` **ни одной**. Пустой захват
    наступает и тогда, когда захватывать нечего — заявки лежали в `pending`. Отсюда правило: **прочитать
    условие перехода — не то же, что измерить состояние**; у пустого множества больше одной причины, и
    сообщение механизма («кто-то финализирует») называет лишь ту, которую предположил автор. Ошибка того же
    рода, что пункт 14, но на своём же выводе, уже записанном в модель как замер.

17. **`git add -A` в общем дереве.** Коммит, объявленный документацией, унёс с собой незакоммиченную правку
    ядра, которую в это же время писал другой работник: сообщение коммита говорит одно, содержимое — другое,
    и история перестаёт быть свидетельством. Правило уже было записано и всё равно нарушено, поэтому здесь
    оно ставится жёстко: **в общем дереве индексировать только поимённо**, своими путями, и перед коммитом
    сверять состав с сообщением. Отсюда же следствие для суждений: утверждение о коде, снятое с рабочего
    дерева, устаревает за минуты; замер живой системы и чтение дерева — разные свидетельства, и смешивать их
    нельзя.

18. **«Промпт длинный, значит его надо обрезать по константе».** Введён предел `MAX_PROMPT_LENGTH = 60000` и
    молчаливое усечение. Константа не выведена ни из одного наблюдения: длина промпта на живом контуре не
    измерялась ни разу, а исходная догадка о её роли (моя) была прямо записана как **не установленная**.
    Закон 8 требует обратного: начальное значение выводится из наблюдений, собственная непересмотренная
    константа не двигает предел ни в одну сторону. Хуже того, в худшей ветке усекается **само описание
    задачи**, а не контекст: компилятор получает изувеченное требование и работает по нему, а единственный
    след — строка лога. Это потеря до всякого заслона, ровно та, против которой написан закон 3, и
    свидетельство, которого нет, — закон 17. Правка заслона не имеет.

19. **Точечная правка с одной границей.** Замена «от найденного начала до конца файла», где конечный якорь
    берётся с запасным вариантом `len(s)`, при отсутствии якоря молча удаляет хвост: так из модели пропал
    весь раздел «Опровергнутое», 83 строки. Отсюда: у всякой замены **две** границы, обе обязаны быть
    найдены, и после записи сверяется число строк с прежним. Восстановление — из HEAD, а не по памяти.

20. **«У фабрики нет счётчика внешнего бюджета».** Заявлено мною как замер после двух грепов: нет
    перечисления сессий у клиента, нет эндпоинта со счётом. Оператор указал на код, и счёт нашёлся —
    `AccountEntity.estimatedDailyCapacity` с ростом на успехе у потолка и сжатием только по настоящему
    отказу о суточном лимите, `consecutiveApiBlockCount` с экспоненциальным откатом, и мост
    `reclassifyPreconditionDailyLimitedAccounts`. Отсюда правило, третье за смену и потому записанное
    жёстко: **отсутствие механизма нельзя устанавливать поиском по именам, которые я для него придумал**.
    Не найдя `listSessions` и эндпоинта, я заключил «механизма нет», тогда как механизм назывался иначе и
    жил в другом слое. Отрицательное существование доказывается разбором того, кто пишет и кто читает
    предмет, а не неудачей двух запросов. Верный вывод оказался и сильнее ложного: механизм есть, он полон, и
    он слеп, потому что читает строку сессии, которой отказ не дал возникнуть.
