## 1. Как здесь работать (дорого добытое)

Нарушение любого пункта стоило этой сессии часов.

**Файловая шара Windows ненадёжна.** Она теряет записи и чтения под нагрузкой, отдаёт компилятору
только что записанные файлы как отсутствующие, и держит блокировки от убитых контейнеров. Проявления:
`MVStoreException ... read 0`, `Writing to FileChannel failed`, `cannot find symbol` сразу после успешной
компиляции, `The file is locked` на файле, который никто не держит.

* Живая база — только в томе Docker, никогда на шаре.
* Сборка и тесты — копировать исходники **внутрь** контейнера (`cp -r /src/src /build`), не собирать
  на монтировании. Это превращало воспроизводимый провал в зелёный прогон без единой правки кода.

**Ресурсы хоста ~3.3 ГБ.** Сборка образа при поднятом контуре не проходит; при остановленном проходит
с первой попытки. Полный `mvn test` одной командой сначала выдаёт выдуманные падения через
`Cannot allocate memory` при сканировании classpath, затем роняет демон Docker. Гонять тесты по классам.

**Замер базы достоверен только при остановленном сервисе.** Копия живого H2-файла рвана по определению:
одни и те же запросы давали противоречивые ответы, пока бэкенд писал. Мерить со статичной копии,
сверяя md5.

**Интероп WSL рвётся.** `accept4 failed 110` на `docker.exe`. Лёгкие команды переживают, тяжёлые — нет.
Оборачивать вызовы ретраями.

**Апостроф в комментарии внутри `@Query` — незакрытая кавычка.** Spring Data сканирует всё значение
аннотации на кавычные диапазоны и не исключает комментарии `--`. Один апостроф в слове с притяжательным
падежом уронил контекст на старте: `The string <SELECT ...> starts a quoted range at 3712, but never ends
it`, 43 перезапуска подряд, 29.08. Проверка — чётность апострофов внутри каждого блока `@Query(value = """`.

**Монитор — только на однократные события** (конец сборки, падение теста). Направленный на лог
работающей фабрики, он превращает каждую строку цикла в уведомление и топит канал.

## 2. Действующие инварианты

Не предложения, а норма. Нарушение — дефект, а не повод для обсуждения.

**Онтологическая стратификация.** `Code(t) ∩ ℒ_factory = ∅`. Проверяется в точке, где слияние физически
происходит, не у вызывающего.

**Одна точка применения (Хартия, инв. 10).** Проверка живёт там, где совершается действие. Тест на
верность предиката — не тест на его применение; нужен и второй.

**Точный знаменатель (Хартия, инв. 8).** Элемент, структурно неспособный дойти до «выполнено», обязан
покинуть множество, по которому принимается решение. Иначе решающий код блокируется молча.

**Независимый свидетель (Хартия, инв. 12).** Сторона, производящая результат, не может быть единственным
подтверждением его корректности.

**Монотонная метка (Хартия, инв. 7).** Механизм «повторить, если появилось новое» сравнивается с меткой,
которую сам не может продвинуть.

**Укоренённость.** `EE = 0.40·C + 0.35·K + 0.25·E_EMS`. Неклассифицированная ось стоит 20, а не середину:
неизвестное положение в паутине убеждений — самое слабое, а не среднее. При `E_EMS = 0` потолок 67.5,
то есть в CORE без верифицированного контракта не войти.

**Anti-Starvation.** Смена статуса атомарно пишет `t_state`; при `null` нижняя граница
`min(t_heartbeat, t_updated, t_created)`. Кулдаун с полным джиттером `U(T_base, T_ceiling)`. Гистерезис:
отказ `k ← min(k+1, k_max)`, успех `k ← max(0, k−1)`. `offline` со свежим пульсом релаксирует в `idle`.

**Zero Muda.** Механизм зарегистрированный, но ни разу не сработавший, — муда, а не защита.

## 3. Закрыто и подтверждено измерением

Строка стоит здесь только если рядом наблюдение, а не намерение.

**Штатное завершение контейнера.** `ENTRYPOINT ["sh","-c","exec java ..."]`. Наблюдено дважды: код
выхода `143` вместо `137` и строка `H2 store compacted on shutdown in 3772 ms`.

**База вне файловой шары** — в томе Docker; старт бэкенда ускорился в разы.

**Память ограничена у всех пяти служб.** `backend` 1 ГБ, `ml` 768 МБ (модель 0.22 ГБ + onnxruntime),
`judgment-proxy` 256 МБ, `runtime-launcher` 256 МБ, `frontend` 128 МБ. Сумма 2432 из 3500 МБ потолка
WSL. Пул Hikari 24 → 12. Второе число `-Xmx` из `Dockerfile.backend` удалено: величина одна — `mem_limit`.

**Образ 1.59 ГБ → 639 МБ.** Из `apt-get` убраны семь пакетов. Замер: JVM запускает процесс только через
`ProcessBuilder` или `Runtime.exec`; вторых ноль, первых три, и все три — `git`.

**Стоимость чтений на горячих путях.** `AutoMergeService` 10 полных чтений таблицы за такт → 0,
`JulesDispatchService` 4 → 2 (обе на ограниченных таблицах), `ContinuousOrchestrationService` 2 → 1.
Плюс пять мест сверх исходного порядка работ. Заслон: `ScheduledQueryCostInvariantTest` падает на любом
классе, который планирует работу чаще суточного и читает растущую таблицу целиком.

**Пока-ёкэ на слиянии.** `MergeChokePointPokaYokeTest` требует, чтобы всякое место, строящее
`PUT /merge`, сперва спросило гейт. Проверено: мусорный PR №170 закрыт, в `main` клиента не попал.

**Разбор PR не вклеивается в задание.** Задание на ревью несёт ссылку; ревьюер читает PR в
репозитории, где работает. До правки одно такое задание достигало 1 788 060 знаков при медиане 10 437.

**Отказы Jules различаются по тому, чьё условие не выполнилось.** `INVALID_ARGUMENT` — дефект фабрики,
аккаунт не наказывается; `401/403` и названные условия аккаунта — вина аккаунта; условие без названия
не вменяется никому. Наблюдено на живых данных: отказ пришёл, аккаунт остался цел.

**Отбор аккаунта не переизбирает сам себя.** Было `ORDER BY открытые сессии ASC, last_heartbeat DESC`,
а `ClaimService` пишет `lastHeartbeat` в момент притязания — выбранный становился самым свежим и
выбирался снова. Наблюдено: 34 отказа подряд через один аккаунт при шести свободных. Стало `ASC` в трёх
запросах отбора; четвёртый выбирает по имени, там порядок ни на что не влияет.

**Носители с заданием удалённого построителя закрыты в данных** (`V117`), а не отсеиваются при чтении.

**Отправка перестала быть незавершаемой** (бывш. §4.1, `4ea9bc4`). Цикл `queued → отказ при создании
сессии → queued` не имел убывающей величины: `retry_count` растёт только там, где сессия уже существовала.
Замер до правки: один носитель — 67 отказных сессий на 7 аккаунтах за 4.5 суток при `retry_count = 0`,
компиляторное задание — 123, и 375 из 775 сессий за всю историю — отказы, не породившие ничего. Допуск
`A(τ) < 2·N_live`, где `A` — число уже записанных отказов при создании (счётчик лежал в данных, монотонен,
растёт на 1 за итерацию), `N_live` — число не-`decommissioned` аккаунтов. Выход — `blocked` плюс
`NeedsHumanReview`, тем же путём, что у компилятора; вина не вменяется, фиксируется расход. Наблюдено
29.08 01:58:01 на живых данных: `Task b2c7e8fe ... left the dispatch queue: 14 refused session creations
against a budget of 14. Routed to human review rather than requeued.`

**Чистая база снова строится** (`f6891f8`). V113 удалял строки из трёх таблиц, которых на свежей цепочке
нет: `project_event_log` и `project_observer_watermark` удалены миграцией V58 за пятьдесят пять шагов до
него, `role_threads` переименована в `feature_threads` миграцией V45 за шестьдесят восемь — и V113 удалял из
обоих имён, так что старое было мёртвым всегда. Следствие было измерено дважды: `TaskClaimServiceTest` — 8
ошибок загрузки контекста, `OrchestrationStatusTest` — 1, обе с `Table ... not found`, и развернуть систему
с нуля было нельзя. Три мёртвых оператора удалены. Правка применённой миграции безопасна здесь и только
здесь: `validate-on-migrate` выключен, а `EneikProductionApplication` зовёт `flyway.repair()` до `migrate`.
Наблюдено с обеих сторон: на пустой схеме `Successfully applied 118 migrations ... now at version v118` и 9
из 9 тестов зелёные; на живой базе `Successfully repaired schema history table`, `Current version: 118`,
старт чистый, 0 перезапусков.

**Бюджет вишлиста списывается за ответ компилятора, а не за попытку до него дойти** (бывш. §4.19,
`5c6c435`). `compileAttempts` рос на каждой попытке отправки, а `lastCompileReachedAt` пишется только когда
сообщение действительно ушло компилятору. Вишлист вычёркивался по выбранному бюджету, даже если компилятор
его ни разу не получил — то есть за занятость Jules, а не за содержание брифа. Дальше круг: вишлисты
вычеркнуты → компиляторная задача не создаётся → сессию у `eneikdru` никто не просит → фабрика не узнаёт, что
аккаунт снова свободен → вишлисты остаются вычеркнутыми. Замер в момент, когда оператор освободил Jules:
шесть вишлистов на 3 из 3 попыток, `last_compile_reached_at` пуст у всех шести, две задачи в очереди за
провалившимися зависимостями, и **ни одной попытки отправки во всей фабрике**. Последнее звено круга
поставила правка §4.10: сузив признак живого канала до принятой сессии на аккаунте компилятора, она
остановила бесконечный перезапуск и вместе с ним единственный способ проверить канал. Теперь удержание по
выбранному бюджету применяется только к `decompositionRefused` — бюджет выбран **и** компилятор ответил;
недостигнутый вишлист продолжает предлагаться, не чаще существующего кулдауна в 15 минут из того же цикла
допуска. Наблюдено 29.08 09:05:55: `Dispatched compiler task ad7879a8 to account eneikdru`, **ноль отказов**,
следом `Compiled 6 wishlist item(s) into 1 task(s)`. 27 из 27 тестов зелёные; прежний тест переписан в два —
достигнутый удерживается, недостигнутый нет.

**Оживление провалившихся снова может сработать** (бывш. §4.12, `d026114`). Замер до правки: 311 `done`,
68 `failed`, 3 `queued`, открытых сессий ноль; все три очередные ждали провалившуюся зависимость.
`RECOVER_FAILED_FRONTIER` разрешался каждый такт и был пригоден **ни для одной из 68**: белый список
`PRODUCT_SOURCES` требовал источник вишлиста из четырёх названных, а у провалившихся источники были
`<none>` (58), `delivery_never_reached_main` (9), `frontend_unbacked_records` (1). Список поддерживался
руками и уже отклонял законную работу однажды — его собственный комментарий описывает, как попытки Gemini
молча отвергались три цикла подряд. Признак, который список подменял, замерен: из 68 у 60 есть `feature_id`,
8 — носители фабрики, **носителей с `feature_id` ноль**. Белый список и обязательный вишлист убраны, признаком
стало наличие фичи; карантин внецикловой работы сохранён и вынесен на `WishlistSource` одним определением для
обоих читателей. Сколько раз (`resumeCount < 1`) и почему (`RETIRED_WITH_NOTHING_LEFT_WORKING_IT`) — не
тронуты, радиус тот же. Наблюдено 29.08 05:19:42: `Resumed 3 existing planned task(s)`, и все три отправлены
за полминуты на `fivedmitr-sys`, `eneikcoworking-ctrl`, `EneikGroup`. 51 из 51 тестов зелёные.

**Отказ называет то, что его вызвало** (бывш. §4.6, `c3cbbd2`). Замер до правки: `policy denied
DISPATCH_REVIEW_TASKS` пятнадцать раз за пятнадцать минут, единственное запрещённое действие, с текстом
«denied by Flow Core state DECOMPOSING» — при том что в тех же тактах разрешён `CHECK_COVERAGE_AUDITS`, чьё
множество запрещающих состояний побайтово то же. Значит `DECOMPOSING` не запрещал ни того ни другого, а
отказ шёл по собственному конъюнкту действия (`reviewTasks > 0 || openReviews > 0`), то есть «ревьюить
нечего». Это стоило часа прямо в этой сессии: состояние разбиралось как блокирующее поток именно потому, что
его назвало сообщение. Введён предикат `stateBlocks(state, projectStatus)`; при его ложности отказ не
приписывается состоянию. Уровень записи следует из того же предиката: норма пишется INFO. Попутно множество
`{FROZEN, PROJECT_NOT_ACTIVE, ACCEPTED, ARCHIVED, GITHUB_RATE_LIMITED, BLOCKED_BY_DUPLICATE_CONTENT}`,
выписанное в файле одиннадцать раз, сведено к одной константе — десять копий заменены, одиннадцатая
намеренно оставлена литералом, потому что она есть то же множество **минус** одно состояние, и разница
должна быть видна на месте. Наблюдено 29.08 04:49: `DISPATCH_REVIEW_TASKS is not blocked by Flow Core state
DECOMPOSING; its own precondition is unmet - there is nothing for it to act on right now`, уровень INFO, ни
одного WARN за окно. 43 из 43 тестов зелёные, четыре новых в `OperationalPolicyReasonTest`.

**Действия внутри такта не переспрашивают состояние** (бывш. §4.18, `ce36c13`). После §4.5 такт строил
модель четыре раза: один снимок оркестрации и три `requireAllowed` внутри самих действий, вызванных
синхронно микросекундами позже, когда между двумя вопросами не произошло ничего. Замер: 76 побайтово
одинаковых пересчётов за 20 минут при том, что работы у фабрики не было вовсе. Снимок теперь живёт ровно
кадр такта — `snapshot` кладёт его в `ThreadLocal`, `authorize(projectId, action)` берёт оттуда, если он
есть для того же проекта на том же потоке, оркестрация очищает в `finally` рядом с `LogScope.clear()`.
Это не кэш: ни срока, ни размера, область равна кадру вызова; контроллеры на других потоках строят своё.
Наблюдено: 6 тактов — 6 построений. 30 из 30 тестов зелёные.

**Состояние строится раз за такт, а не раз на вопрос** (бывш. §4.5, `5e1e301`). Замер до правки: 52 строки
`FlowSpine: delivery verification` за 20 минут, побайтово одинаковые (`passed=92 failed=0 REFUTED=45
NEVER ASKED=245 of 382 tasks`), до пяти в одну секунду. Каждая — полный пересчёт: вся история задач проекта,
вишлисты, сессии по этим задачам, ревью по этим сессиям, расчёт готовности и пятнадцать проходов стримом.
Спрашивал `ContinuousOrchestrationService`: **десять `isAllowed` за такт**, и
`authorize(projectId, action)` строил модель на каждый. Перегрузка `authorize(FlowCoreDto, action)` уже
существовала — не хватало способа получить снимок; добавлен `snapshot(projectId)`, такт берёт его один раз
на проект. Замер после: 8 тактов, 33 построения — **4 на такт**, из них одно от оркестрации вместо десяти.
Оставшиеся три — `requireAllowed` внутри `ProjectFlowService`, `AutoMergeService` и
`ClientDeliverableReadinessService`, то есть предусловия самих действий; по доводу этой же правки они
обязаны читать свежее состояние, и в снимок их не заводят. Заслон `ScheduledQueryCostInvariantTest` этого не
ловил и не ловит: он смотрит классы с `@Scheduled`, а `FlowSpineService` зовут из помеченного.

**Признак отказного ряда считает, а не даёт один бит** (бывш. §4.13, `47a8b19`). Введённый утром ведущий
член был двоичным, и под нагрузкой он насыщался ровно так, как предупреждало собственное предложение: недавний
отказ есть у всех, бит у всех равен единице, решает следующий ключ — «меньше открытых сессий», — а он
предпочитает того, кто ничего не несёт. Замер: за 15 минут 10 отправок против 37 отказов, из них 21 на
`eneikdru` при нуле успехов, и **`eneikdru` выбирался первым одиннадцать раз** при 0 занятых из 15 и восьми
часах без единой принятой сессии. Член заменён на число отказов, записанных после последней принятой сессии
этого аккаунта: у принимающего иногда он мал, у не принимающего равен всей серии, обнуляется единственным

прошли на пяти аккаунтах. 19 из 19 тестов зелёные, включая `AccountRepositoryIntegrationTest` на настоящей

**Детектор зависания судит по измеренному среднему, а не по константе** (бывш. §4.17, `0fc6134`).

**Отчёт для человека перестал быть одной фразой** (бывш. §4.16, `03932c2`). `withholdFromCompileDispatch`

**1 235 знаков, 6 вхождений**. 34 из 34 тестов зелёные, V119 применилась и на чистой базе, и на живой.

**Один список «сессия жива» вместо двух** (бывш. §4.15, `311ceca`). `JulesDispatchService.ACTIVE_SESSION_STATUSES`
включал `stuck`, а `ClaimService.isActiveExternalJulesSession` — нет; расхождение ровно в одном значении, и

Jules в статусе `stuck` с непустым внешним идентификатором, обновлённые минутами раньше; самолечение не
видело живой сессии, снимало притязание и возвращало задачу в очередь, следующая отправка находила ту же
сессию активной и отвечала `already dispatched, skipping duplicate`, притязание бралось снова — по три
снятия на задачу. `stuck` не значит «сессии нет»: это статус, который фабрика сама выставляет живой сессии,

детектор молчания, через час и через два. Окно молчания стоит на директиве «тишина сама по себе не
доказательство провала»; здесь тишина ни при чём, свидетельство есть с первой минуты и оно в закрытом PR.
Притязание перестало вето́вать сверку для носителей фабрики; продуктовые задачи не тронуты — у реализатора
закрытый PR не конец работы, та же сессия может открыть новый. Наблюдено на ближайшей сверке: носитель
помечен провалившимся именно по закрытому без слияния PR, притязание снято, сессия закрыта, запертые за ним
брифы вернулись в очередь.

## 4. Открытые задачи

### 4.3 Безымянное `FAILED_PRECONDITION` — привязка к аккаунту опровергнута

**Что было записано и отозвано.** 29.08 04:00 это стояло в §3 как закрытое: 206 таких отказов, все на
`eneikdru`, ни одного на прочих шести — значит свойство аккаунта. Вывод был сделан на данных, где **никого,
кроме `eneikdru`, и не спрашивали**: общий пул стоял пустым, работал только закреплённый компиляторный путь.
Отсутствие отказов там, где не было попыток, я прочёл как отсутствие условия. Утверждение отозвано.

**Замер 29.08 05:40, когда работа пошла на шесть аккаунтов.** За 20 минут: 19 отправок и **39 безымянных
отказов**, распределение по аккаунтам — `eneikdru` 20, `sixdmitrsix-ops` 7, `fivedmitr-sys` 7,
`dmitriieneik-rgb` 3, `EneikGroup` 2. Условие возникает на каждом аккаунте, которому дают работу.

**Что при этом установлено твёрдо.** Занятость аккаунта, как её считает фабрика, отказ не объясняет — и
объясняет наоборот. Два аккаунта **у потолка** (`dmitrefrem-eneik` 3/3, `eneikcoworking-ctrl` 3/3) не
отказали ни разу: запрос ёмкости их не возвращает, их не спрашивают. Отказывают те, кто **ниже** потолка:
`eneikdru` при 0 из 15, `fivedmitr-sys` и `sixdmitrsix-ops` при 1 из 3. То есть фабрика полагает, что место
есть, и получает отказ.

**Чего это не воскрешает.** Толкование «`FAILED_PRECONDITION` означает исчерпание одновременных сессий»
остаётся отозванным (§5.5): оно было прочитано с интерфейса Jules, а не измерено, и здесь не измерено тоже.
Установлено другое и более слабое: **наша собственная оценка ёмкости не опровергается ничем** — Хартия,
инвариант 15, который прямо называет `jules.max-concurrent-sessions-per-account` оставшейся фиксированной
константой.

**Занятость исключена.** Пары «занятость аккаунта в момент попытки → исход» накоплены. В агрегате доля
отказов выглядела падающей с ростом занятости — 78% при нуле занятых, ноль при 11 и выше. При контроле по
аккаунту эффект исчезает и меняет знак: `EneikGroup` 23%→68%, `dmitrefrem-eneik` 18%→69%,
`dmitriieneik-rgb` 61%→41%, `eneikcoworking-ctrl` 50%→46%. Агрегат был парадоксом Симпсона от 330 попыток
`eneikdru` при нуле занятых с 98% отказов. Наша собственная оценка занятости отказ не объясняет.

**Что установил оператор.** 29.08 около 09:00 оператор вручную освободил Jules от накопившихся сессий.
Сразу после этого первая же компиляторная отправка прошла: `Dispatched compiler task ... to account
eneikdru`, ноль отказов, тогда как до того на этом аккаунте не проходило ничего с 28.08 21:36 и по всей
фабрике отказывало около двух попыток из трёх. Одно наблюдение одного перехода — не закон, но оно указывает
на состояние стороны Jules, а не на нашу занятость и не на содержание запроса.

**Что закроет.** Повторение того же перехода: накопление отказов → освобождение → приём. Пока таких переходов
один, и правки на этом не строится.

### 4.4 Ёмкость по параллельным сессиям — константа, которую ничто не опровергает

**Определение оператора 29.08.** Jules отказывал из-за ограничения параллельных сессий. Это установлено
оператором на его собственной системе, а не выведено мной; §5.5 отзывал не этот факт, а мою попытку прочесть
его с интерфейса Jules вместо ответа Jules.

**Что это объясняет в замерах.** Доля отказов не следовала за занятостью — но за **нашей** занятостью, то
есть за числом строк в нашей таблице. Аккаунты выглядели свободными: `eneikdru` при 0 из 15, остальные при
1 из 3. Удаление сессий на стороне Jules при этом подтверждено ответами API — 472 из 473 строк несут отметку
об удалении. Наши книги говорили, что в Jules пусто; Jules отказывал по переполнению. Значит расходится не
учёт удалений, а сама величина: `max_concurrent_sessions` — 3 у шести аккаунтов, 15 у `eneikdru` — это
непроверенная догадка о чужой системе, застывшая в конфиге.

Хартия называет этот случай прямо, инвариант 15, и там же сказано, почему для параллельных сессий пересмотр
не сделали: «у `DispatchOutcome` нет отдельного сигнала „отказано из-за числа одновременных сессий“, значит
нет и канала опровержения». Канал теперь назван: безымянное `FAILED_PRECONDITION` и есть этот отказ.

#### Решение

Зеркало уже работающего механизма для дневной ёмкости, тот же вид, те же настройки, ни одного нового числа.

    ceiling(a) = estimated_concurrent_capacity(a) ?? max_concurrent_sessions(a) ?? default

    приём сессии при occupancy(a) ≥ ceiling(a)  →  ceiling(a) + probeStep   (смелая проба выжила)
    безымянный отказ при occupancy(a) = k       →  max(1, round(k · backoffFactor))   (опровержение)

`probeStep` и `backoffFactor` — те же настроенные величины, которыми уже пересматривается дневная ёмкость.
Начальное значение — существующая константа, так что до первого свидетельства поведение прежнее.

*Опровержение только от настоящего отказа Jules, рост только от настоящего успеха.* Собственная
непересмотренная константа не может ни поднять, ни опустить убеждение — требование инварианта 15.

*Occupancy считается тем же выражением, что и в отборе.* Иначе убеждение пересматривалось бы про одну
величину, а допуск решал по другой — та самая пара несогласованных счётчиков, которую Хартия запрещает
инвариантом 10.

*Что это чинит на потоке:* фабрика перестаёт настаивать на числе, которое Jules только что опроверг, и
перестаёт занижать его навсегда после одного плохого дня — потолок возвращается вверх от реальных приёмов.

**Сделано 29.08** (`97ff12e`, развёрнуто, V120 применилась): колонка `estimated_concurrent_capacity`,
пересмотр вниз по безымянному отказу от наблюдённой точки, вверх — по принятой сессии на потолке, тем же
шагом и тем же коэффициентом, что у дневной ёмкости. Отбор читает `COALESCE(estimated_concurrent_capacity,
max_concurrent_sessions, ...)`, занятость считается тем же выражением, что и в допуске. 20 из 20 тестов
зелёные, включая отбор на настоящей H2.

**Не наблюдено.** Убеждение движется только от настоящего события: отказа или приёма на самом потолке. После
того как оператор освободил Jules, отказов нет, а до потолка в три сессии текущая нагрузка не доходит. Пункт
остаётся здесь до первого движения.

### 4.14 Обращение к человеку — тупиковая ветвь, убрана

**Указание оператора 29.08:** фабрика полностью автономна; ветвь «нужен человек» тупиковая, убрать всё
подобное.

**Что было.** Две точки отправляли работу человеку и на этом останавливались:

* `JulesDispatchService` — компиляторное задание, не давшее годного плана за отведённые попытки,
  закрывало PR, помечалось выполненным и уходило в список.

Плюс сам список: сущность, таблица, репозиторий и чистка, которую я добавил утром, чтобы он не копил уже
отвеченные вопросы. Замер тогда же: 18 записей, 8 из них про задания, которые уже `done`.

**Чем заменено — тем, что у фабрики уже есть.**

Исчерпавшее бюджет задание остаётся в `blocked` с записанной причиной. Оттуда его забирает

не берёт.

*Ни одного нового механизма:* обе замены — ступени, которые уже работают и уже наблюдались.

**Довычищено в тот же день.** Обращения к человеку оставались ещё в трёх местах, уже не как ветвь логики, а
как текст, который её предполагает: строка отчёта «бриф нуждается в человеческом прочтении, а не в новой
попытке»; предупреждение `FlowSpine` о брифах, которым компилятор ничего не дал, заканчивавшееся тем же —

меняется); и бриф, который `AutoMergeService` заводит сам себе после исчерпанных перебазирований, где одним

самой модели и доходит до панели, третий переписан в единственный исход, который фабрика может исполнить
сама: собрать оставшийся объём заново от текущего main.

### 4.23 «Компилятор ответил пустотой» и «мы отвергли его ответ» — один вердикт на два разных факта

**Замер 29.08, после того как носитель разобран.** Брифы вернулись в очередь, но бюджет их выбран и отметка
достижения компилятора проставлена, значит вердикт `decompositionRefused` вынесен и к отправке они больше не
допускаются. Другого источника работы у фабрики нет: декомпозиция единственный.

**Что стоит за вердиктом.** Предикат читается как «спросили и ничего не получили». Но компилятор ответил —
вернул эпики со слайсами, — и оба раза этот ответ отверг **наш** валидатор. Это два разных факта:

* компилятор не смог разложить бриф на эпики и слайсы — свойство брифа, вердикт заслужен;
* фабрика не приняла то, что он вернул — свойство нашей проверки, о брифе не говорящее ничего.

Сейчас они складываются в один поглощающий вердикт. Брифы сняты навсегда по второму случаю, и причина отказа
тогда даже не записывалась — она пишется только с §4.20, развёрнутого позже. Вердикт вынесен по
свидетельству, которого никто не может прочесть.

#### Решение

Различать эти два факта уже можно: с §4.20 проверка возвращает причину, и «не вернулось ни одного эпика»
отличается от всякой другой. Первое — компилятор ответил пустотой, о брифе установлено; второе — мы не
приняли ответ, о брифе не установлено ничего.

Попытка, отвергнутая **нашей** проверкой, брифу возвращается: она не сказала о нём ничего, ровно как
попытка, не дошедшая до компилятора (§4.19, тот же довод этажом ниже). Попытка, на которую компилятор ответил
пустотой, списывается как прежде.

*Существующий механизм:* возврат делается там же, где уже возвращаются притязания на вишлисты при негодном
ответе — компенсирующая запись рядом с той, что уже есть. Ни новой колонки, ни числа.

*Завершаемость.* Если наша проверка отвергает раз за разом, каждый носитель ограничен собственным числом
повторов и завершается, а бриф предлагается снова не чаще существующего кулдауна. Цикл разрежён и на каждом
обороте оставляет записанную причину — ровно то свидетельство, которого сейчас нет.

*Уже вынесенные вердикты.* §8.8 говорит прямо: отказ, чью причину никто не может прочесть, не может быть
основанием поглощающего вердикта. Шесть вердиктов вынесены до §4.20, когда причина не записывалась. Опознание
точное и замерено: сырые брифы, бюджет выбран, компилятор достигнут, и ни один из них ни разу не породил
задачу. Их бюджет возвращается один раз, в данных, тем же приёмом, каким V117 снимала носителей удалённого
построителя. Это не смягчение: следующий круг вынесет вердикт заново, но уже с записанной причиной.

**Сделано 29.08** (`347b4a2`, развёрнуто, V122 применилась). Отказ нашей проверки возвращает брифу списанную
попытку — на обоих путях компиляции; пустой ответ компилятора опознаётся отдельной константой и попытку
по-прежнему списывает. Наблюдено сразу после старта: компиляторная задача принята на `eneikdru` **без
отказа**, шесть вишлистов ушли в компиляцию. 111 из 111 тестов зелёные.

**Открытым остаётся то, ради чего это делалось:** увидеть записанную причину отказа и понять, отвергает ли
фабрика ответ компилятора за дело или её проверка слишком строга. Круг идёт; до записи вердикт не выносить.

## 5. Ошибочные утверждения — не воскрешать

Все одной формы: вывод выдавался за измерение.

1. **«У рычага TOC ноль разрешённых наблюдений».** Считалось по одной величине, а промоция считает по
   другой. Не поднимается он из-за подменённой величины, а не из-за нехватки данных.
2. **«Фаза декомпозиции должна завершаться».** Не должна и не может: девять сервисов порождают вишлисты
   непрерывно, множество открытых брифов не опустеет никогда.
3. **«Бюджет должен списываться только на отвеченных попытках».** Ломает завершаемость: при вечно
   занятом канале вариантная функция не убывает. Верное решение — различать вердикты, а не менять её.
4. **«Реализовано» без сборки.** Весь массив правок пролежал несобранным; первая же сборка нашла отказ
   компиляции за 90 секунд.
5. **«`FAILED_PRECONDITION` означает исчерпание одновременных сессий».** Взято из надписи в интерфейсе
   Jules, а не из ответа Jules. Существующий тест это опроверг: тот же статус приходит и как
   «Repository access is not ready».
6. **«Миграция V111 навсегда закрепила настройку в базе».** Значение в живой базе — противоположное.
   Миграция присваивает один раз и ничего не запирает.
7. **«`teardown` лаунчера всегда безопасно звать».** Его `success` не означает, что что-то погашено:
   при потерянном указателе в памяти он возвращает успех, не сделав ничего.
8. **«Привязка компилятора к аккаунту — про квоту, значит её можно ослабить».** Ослабление отменено
   оператором: компилятор работает на своём аккаунте и только на нём.
9. **«Отсеять негодные задачи у каждого читателя».** Заплатка: фильтр поставили на один список отбора
   из двух, и дефект вернулся через второй. Негодное обязано покидать множество один раз (V117).
10. **Тесты, которые не могут упасть.** Подстановка на вызов, которого код больше не делает, возвращает
    пустоту — и тест, ожидающий пустоту, проходит, не проверяя ничего. Найдено дважды.

## 8. Математическая модель потока и что сделать в коде

Раздел нормативный и **исполнимый**. Формулировка — множествами и предикатами; под каждой — что именно
поменять в коде. Выполняет другой агент; порядок §7 обязателен для каждого пункта.

Словарь — три слова: **Вишлист**, **Задача**, **Эпик** (docs/GLOSSARY.md). Слово «фича» не употребляется.

### 8.0 Обозначения

    W  вишлисты   status(w) ∈ {pending, compiling, converted_to_task, dismissed}
    T  задачи     status(τ) ∈ {queued, claimed, in_progress, review, pending_review,
                               done, failed, blocked, spike_completed}
    E  эпики      epic(τ) ∈ E ∪ {∅}
    A  аккаунты   ceiling(a), dailyCeiling(a), occ(a,t) — открытых сессий в момент t
    S  сессии     одна сессия = одна ветка = один PR
    R  ревью      ciStatus(r), merged(r), session(r)

    carrier(τ)      ⟺ payload(τ).taskType ≠ ∅            носитель фабрики
    accepted(s)     ⟺ externalSessionId(s) ∉ {∅, skipped}  Jules принял сессию
    refused(s)      ⟺ externalSessionId(s) = ∅ ∧ status(s) = failed
    merged(τ)       ⟺ diff задачи присутствует в main
    terminal(τ)     ⟺ status(τ) ∈ {done, failed, spike_completed}

### 8.1 Цепь потока

    w ─κ─▶ (e, {τ₁…τₙ}) ─δ─▶ s ─▶ PR ─ρ─▶ гейты ─μ─▶ merged ─▶ done

`κ` компиляция, `δ` отправка, `ρ` ревью, `μ` слияние — частичные функции с предусловиями. Ни одна не
выполняется дважды для одного элемента без явного возврата предыдущего шага.

**Что сделать в коде:** ничего; это определение, к которому апеллируют остальные пункты.

### 8.2 Разделение носителей и продукта

    T = T_прод ⊔ T_нос,   τ ∈ T_нос ⟺ carrier(τ)
    замерено 29.08:  ∀τ (carrier(τ) → epic(τ) = ∅)   и   |{τ : carrier(τ) ∧ epic(τ) ≠ ∅}| = 0

**Инвариант.** Правило о продукте не применяется к носителю, и наоборот.

**Что сделать в коде.**
1. Свести предикат `carrier` к одному определению. Сейчас он написан минимум трижды:
   `ProjectFlowService.isWishlistCompilerTask` / `isHousekeepingCarrierTask`,
   `FlowSpineService.isFactoryCarrierTask`, инлайн в `JulesDispatchService.reconcileTaskStatusAgainstGitHubTruth`.
   Оставить один — методом на `TaskEntity`, — остальные заменить вызовами.
2. Структурный тест: `payload.hasNonNull("taskType")` встречается ровно в одном месте кодовой базы.

### 8.3 Правило бюджета

Пусть бюджет `B` со счётчиком `c` ограничивает повторы относительно предмета `X`, а `Ev(X)` — множество
событий, являющихся свидетельством о `X`.

    Δc = 1  ⟺  произошло e ∈ Ev(X)

| бюджет | предмет `X` | `Ev(X)` |
|---|---|---|
| `compileAttempts(w)` | бриф | компилятор ответил: пустой ответ **или** принятый |
| `A(τ)` = \|{s : task(s)=τ ∧ refused(s)}\| | потраченная ёмкость | всякий отказ; вина не вменяется |
| `retryCount(τ_нос)` | наши просьбы к одному носителю | каждая просьба |
| `resumeCount(τ)` | оживление задачи | одно на задачу |

**Следствие.** Попытка, не дошедшая до компилятора, бюджет брифа не тратит (сделано, §4.19). Попытка, ответ
на которую отвергла **наша** проверка, — тоже: о брифе она не сказала ничего.

**Что сделать в коде.**
1. Ввести константу пустого ответа рядом с `JulesDispatchService.compilerPlanRejection` — строку, которую та
   возвращает при `epics.isEmpty()`. Сравнивать по ней, не по подстроке.
2. В `completeWishlistCompilation`: при `rejection ≠ ∅ ∧ rejection ≠ EMPTY` вызвать новый
   `ProjectFlowService.returnCompileAttempt(Set<UUID> wishlistIds)` рядом с уже стоящим
   `releaseUnfinishedClaims`. То же в персистентном пути, где вычисляется `cycleRejection`.
3. `returnCompileAttempt` уменьшает `compileAttempts` на единицу, не ниже нуля, и ничего больше.
4. Миграция: вернуть бюджет брифам, чей вердикт вынесен до появления записи причины. Опознание точное и
   замерено: `status='pending' ∧ compiled_by_role IS NULL ∧ compile_attempts ≥ 3 ∧ last_compile_reached_at
   IS NOT NULL`, и ни один из них не породил ни одной задачи. Обоснование — §8.8: вердикт по нечитаемому
   свидетельству недействителен.
5. Тесты: отказ нашей проверки `compileAttempts` не двигает; пустой ответ двигает.

### 8.4 Правило цикла

    ∀ цикл L ∃ v: Состояние → ℕ,  v ограничена снизу,  v строго убывает на каждом обороте L

    отправка задачи:   v = A_max(τ) − A(τ),  A_max = 2·|{a : status(a) ≠ decommissioned}|
    компиляция брифа:  v = бюджет(w) − compileAttempts(w),  обороты разрежены кулдауном
    повторы носителя:  v = MAX_RETRIES − retryCount(τ)
    оживление:         v = 1 − resumeCount(τ)
    возврат бюджета:   каждый возврат потребляет строго более позднее событие канала

### 8.5 Правило метки

    mark: Состояние → Время ∪ {−∞},  монотонна,  и ни один переход самого цикла её не продвигает

Метку двигает только событие внешней стороны: принятая сессия, слияние, ответ.

### 8.7 Правило убеждения о внешней системе

### 8.12 Контур ценности целиком

Флоу есть **замкнутый контур**: один вход извне и шесть дуг обратной связи, все возвращаются в одну точку.

    клиентский бриф
          │
          ▼
    ┌──▶ ВИШЛИСТ ──κ──▶ ЭПИК ──▶ ЗАДАЧИ ──δ──▶ сессии ──▶ PR ──ρ──▶ гейты ──μ──▶ слияние
    │                                                                                 │
    │                                                                                 ▼
    │                                                                       суждение о доставленном
    │      ┌──────────────────────────────────────────────────────────────────────────┤
    │      │ фальсификация ролей          ночной круг по критериям отказа каждой роли  │
    │      │ аудит покрытия               на каждый клиентский вишлист по мере слияния │
    │      │ реальность доставки          отчиталось done, в main не попало            │
    │      │ наблюдение живого продукта   запуск, здоровье, снос контрольной карты      │
    │      │ дрейф дизайна                реальный отданный HTML против дизайн-системы  │
    │      │ наблюдатель проекта          Gemini                                       │
    └──────┴──────────────────────────────────────────────────────────────────────────┘

    ∀ находка f любого департамента:  f ↦ вишлист,  и далее по цепи §8.1

**Что сделать в коде.**
1. Дизайн-цех на третьей ступени создаёт задачу напрямую из утверждённого макета, минуя `κ`; такая задача не
   наследует эпик, а завершённость эпика — то, чем меряется ценность. Привести к правилу: ступень 3 создаёт
   **вишлист** с источником дизайна, и он идёт обычной декомпозицией.
2. Тест: ни один департамент не вызывает создание `TaskEntity` иначе как через `buildTaskGraphFromSlices`.

### 8.13 Правило готовности

    ready(P, t) ⟺ decompositionComplete(P, t) ∧ ratio(P, t) = 1

Полнота недостижима по построению, пока проект активен: фальсификация, покрытие и наблюдение непрерывно
добавляют работу. Значит механизм, ждущий готовности, срабатывает на **фронте**:

Механизм, ждущий «продукт закончен», не сработает никогда (§5.2).

**Что сделать в коде.**
1. Проверить каждого потребителя `ClientDeliverableReadinessService.computeForProject`: срабатывает ли он на
   фронте или на состоянии. Образец фронта — `DesignShopOrchestrationService` с признаком прошлого состояния.
2. Тест: потребитель, ждущий готовности, срабатывает дважды при двух фронтах и ни разу при удержании.
