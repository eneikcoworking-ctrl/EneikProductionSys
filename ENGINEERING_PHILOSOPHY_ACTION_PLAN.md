# 🎯 Идеальная модель потока EneikProductionSys

**Что это.** Модель того, каким поток обязан быть, и правила, по которым к ней приводится код. Не хроника.
История правок целиком лежит в git — документ ей не замена, и дублировать её здесь запрещено.

**Как этим пользоваться.** Порядок один: сперва **привести код в соответствие с моделью**. Если встречена
задача потока, которой в модели нет, — сперва **исправляется модель**, потом код. Обратный порядок —
правка вперёд модели — и есть то, из чего вырастают заплатки.

**Правило документа.** Только проверенное или явно помеченное как непроверенное. Утверждение без измерения
— не находка. Механизм, зарегистрированный, но ни разу не сработавший, считается неработающим, пока не
показано обратное. Строка, описывающая **сделанное**, в этот документ не попадает вовсе: сделанное видно в
коде и в git, а здесь стоит только то, чему код обязан соответствовать.

**Нумерация разделов сохранена** от прежней редакции, чтобы перекрёстные ссылки внутри текста оставались
рабочими. Разделы 0 (снимок состояния), 3 (закрытое) и 6 (первое действие) удалены как хроника.

## 1. Как здесь работать (дорого добытое)

Нарушение любого пункта стоило этой сессии часов.

**Файловая шара Windows ненадёжна.** Она теряет записи и чтения под нагрузкой, отдаёт компилятору
только что записанные файлы как отсутствующие, и держит блокировки от убитых контейнеров. Проявления:
`MVStoreException ... read 0`, `Writing to FileChannel failed`, `cannot find symbol` сразу после успешной
компиляции, `The file is locked` на файле, который никто не держит.

* Живая база — только в томе Docker, никогда на шаре.
* Сборка и тесты — копировать исходники **внутрь** контейнера (`cp -r /src/src /build`), не собирать
  на монтировании. Это превращало воспроизводимый провал в зелёный прогон без единой правки кода.

**Ресурсы хоста ~3.3 ГБ.** Сборка образа при поднятом контуре не проходит; при остановленном проходит
с первой попытки. Полный `mvn test` одной командой сначала выдаёт выдуманные падения через
`Cannot allocate memory` при сканировании classpath, затем роняет демон Docker. Гонять тесты по классам.

**Замер базы достоверен только при остановленном сервисе.** Копия живого H2-файла рвана по определению:
одни и те же запросы давали противоречивые ответы, пока бэкенд писал. Мерить со статичной копии,
сверяя md5.

**Интероп WSL рвётся.** `accept4 failed 110` на `docker.exe`. Лёгкие команды переживают, тяжёлые — нет.
Оборачивать вызовы ретраями.

**Апостроф в комментарии внутри `@Query` — незакрытая кавычка.** Spring Data сканирует всё значение
аннотации на кавычные диапазоны и не исключает комментарии `--`. Один апостроф в слове с притяжательным
падежом уронил контекст на старте: `The string <SELECT ...> starts a quoted range at 3712, but never ends
it`, 43 перезапуска подряд, 29.08. Проверка — чётность апострофов внутри каждого блока `@Query(value = """`.

**Имя аргумента сборки — `ENEIK_BUILD_GIT_SHA`, не `GIT_REVISION`.** 29.08 передал второе; сборка прошла,
образ собрался из верного дерева, а метка `org.opencontainers.image.revision` осталась `unknown` — то есть
проверка §6 «сверить образ с `main`» стала невозможна на верном образе. Если метка сбита, содержимое всё
равно проверяемо прямо: `docker.exe cp <контейнер>:/app/app.jar`, затем `zipfile` по
`BOOT-INF/classes/.../X.class` и поиск строки, которой в прежней версии не было. `unzip` в WSL нет, python3
есть.

**Монитор — только на однократные события** (конец сборки, падение теста). Направленный на лог
работающей фабрики, он превращает каждую строку цикла в уведомление и топит канал.

## 2. Действующие инварианты

Не предложения, а норма. Нарушение — дефект, а не повод для обсуждения.

**Онтологическая стратификация.** `Code(t) ∩ ℒ_factory = ∅`. Проверяется в точке, где слияние физически
происходит, не у вызывающего.

**Одна точка применения (Хартия, инв. 10).** Проверка живёт там, где совершается действие. Тест на
верность предиката — не тест на его применение; нужен и второй.

**Точный знаменатель (Хартия, инв. 8).** Элемент, структурно неспособный дойти до «выполнено», обязан
покинуть множество, по которому принимается решение. Иначе решающий код блокируется молча.

**Независимый свидетель (Хартия, инв. 12).** Сторона, производящая результат, не может быть единственным
подтверждением его корректности.

**Монотонная метка (Хартия, инв. 7).** Механизм «повторить, если появилось новое» сравнивается с меткой,
которую сам не может продвинуть.

**Укоренённость.** `EE = 0.40·C + 0.35·K + 0.25·E_EMS`. Неклассифицированная ось стоит 20, а не середину:
неизвестное положение в паутине убеждений — самое слабое, а не среднее. При `E_EMS = 0` потолок 67.5,
то есть в CORE без верифицированного контракта не войти.

**Anti-Starvation.** Смена статуса атомарно пишет `t_state`; при `null` нижняя граница
`min(t_heartbeat, t_updated, t_created)`. Кулдаун с полным джиттером `U(T_base, T_ceiling)`. Гистерезис:
отказ `k ← min(k+1, k_max)`, успех `k ← max(0, k−1)`. `offline` со свежим пульсом релаксирует в `idle`.

**Zero Muda.** Механизм зарегистрированный, но ни разу не сработавший, — муда, а не защита.

## 4. Где код не соответствует модели

Каждый пункт — **утверждение о расхождении**, а не отчёт. Пункт уходит отсюда, когда код приведён в
соответствие и это подтверждено замером на живом контуре; уходит молча, без надгробия.

### 4.3 Отказ Jules не имеет имени, и модель не может о нём рассуждать

**Расхождение с §8.7.** Модель требует, чтобы внешний предел был опровержимым убеждением. Канал опровержения
существует только если отказ различим по причине. У `DispatchOutcome` такого сигнала нет: безымянный
`FAILED_PRECONDITION` покрывает все причины сразу.

**Что установлено твёрдо и не подлежит переоткрытию.** Наша собственная оценка занятости отказ не объясняет
и объясняет наоборот: отказывают аккаунты **ниже** потолка, не отказывают стоящие **у** потолка. При
контроле по аккаунту знак зависимости меняется — агрегат был парадоксом Симпсона.

    H₁ (наша):      R(a,t) → occ(a,t) ≥ cap(a)          — опровергнута обоими способами сразу
    H₂ (остаточная): R(a,t) → S(t), S — состояние Jules  — невыводима: канала нет по построению

**Что требуется от кода.** Различимый сигнал причины отказа в `DispatchOutcome`. До него любая правка о
ёмкости — догадка, и §8.7 неисполним.

### 4.4 Убеждение о ёмкости построено, но ни разу не двинулось

**Расхождение с §2, Zero Muda.** Механизм пересмотра `estimated_concurrent_capacity` зарегистрирован: вниз
по настоящему отказу от наблюдённой точки, вверх по принятой сессии на самом потолке, тем же шагом и
коэффициентом, что у дневной ёмкости. Ни одного движения не наблюдалось. По правилу документа он считается
неработающим, пока обратное не показано.

**Что требуется.** Наблюдение хотя бы одного настоящего движения в любую сторону. Пока его нет, пункт стоит
здесь, а не в модели.

### 4.36 Предел декомпозиции — назначенное число

**Расхождение с §8.3 и инвариантом 15.** `A(w) = 3` — константа. Модель требует:

    A(w) = f(наблюдения о том, на каком заходе компиляции этого проекта удавались)
    вниз  — по настоящему свидетельству о брифе (компилятор ответил пустотой)
    вверх — по настоящему успеху на самой границе (план принят на последнем доступном заходе)
    собственная непересмотренная константа не двигает предел ни в одну сторону

**Условие корректности, снимать нельзя.** `A(w)` конечен, списание строго убывает на каждой попытке, о
которой что-то установлено о брифе. Меняется начальное значение вариантной функции, а не её характер.
Попытка списывать бюджет только на отвеченных попытках уже ломала завершаемость (§5.3).

**Рядом, тем же порядком, открыто:** `ORCHESTRATION_COOLDOWN_SECONDS 300`,
`BLOCKED_ITEM_STALE_THRESHOLD_HOURS 2`, `WAITING_THRESHOLD_MINUTES 10`, `EPIC_CLEANUP_MIN_AGE_MINUTES 10`.
Для каждого сперва вопрос: замещает ли окно длительность или наблюдаемый факт? Если факт — окно заменяется
фактом, а не подбирается.

### 4.41 Цикл фальсификации не порождает работу

**Расхождение с §8.12.** Контур ценности замкнут только если опровержение продукта порождает работу. Три
затвора стоят перед отправкой аудита:

    G₁  готовность:   decompositionComplete(P) ∧ selfFalsificationReadyRatio(P) ≥ θ
    G₂  нет открытого: ¬∃ w: source(w)=self_falsification ∧ status(w) ∈ {pending, compiling}
    G₃  есть новое:    diff(merged PR > highest_pr_number_audited) ≠ ∅

`G₂` и `G₃` проходят. Значит держит `G₁` — либо цикл не запускается вовсе, и данные этих двух случаев не
различают. Область журналирования у службы теперь проектная, то есть её отказ стал прочным; пункт закрыт не
будет, пока первый настоящий отказ не прочитан.

### 4.42 Дизайн-цех держит фронт, которого не было

**Разрешено замером 30.08.** Два объяснения — «ни разу не опрашивался» и «опрашивался и выходил» — больше не
равноправны: оба флага `true` в базе, крон идёт каждые пять минут, значит верно второе. Причина выхода:

    ready(P) ⟺ decompositionComplete(P) ∧ ratio(P) = 1        (§8.13)
    живьём:   decompositionComplete = true,  ratio = 0.556      (сказано самой выдержкой 15:35:00)

Сама выдержка **правильна**: §8.13 срабатывает на переднем фронте готовности, а фронта не было. Неподвижный
`updated_at` — следствие того же: ни одна ветвь не пишет строку. Дефектом было то, что различить это было
нельзя; выдержка теперь называет себя один раз на изменение (§8.11 O8, O9).

**Что осталось открытым.** Фронт `ratio = 1` не наступал 45 часов, и вопрос «достижим ли он на активном
проекте вообще» §8.13 отвечает отрицательно по построению. То есть цех может оказаться механизмом, чьё
условие срабатывания в живом проекте не наступает никогда. Это проверяется первым же наступлением фронта, и
до него правки здесь не делаются.

### 4.43 Стадия 3 дизайн-цеха создаёт продуктовую задачу без эпика

**Расхождение с §8.12, пункт 1 — verified in code 30.08.** `ProjectFlowService.dispatchDesignImplementation`
создаёт `TaskEntity` с ролью BARCAN-TAG-11, без `featureId` и без `sourceWishlistId`, и отправляет её
напрямую. Завершённость эпика — то, чем меряется ценность, поэтому доставка такой задачи не двигает ничего.

Модель предписывает: ступень 3 создаёт **вишлист** с источником дизайна, и он идёт обычной декомпозицией.
Правка не сделана намеренно: путь мёртв, пока держит §4.42, и проверить её на живых данных нельзя. Делается
первым же движением цеха.

### 4.44 Свойство безопасности S2 не защищено ничем

**Расхождение с §8.11 S2, измерено 30.08.** `terminal(τ) ⟹ статус τ более не переписывается` держится только
там, где запись идёт через `writeStatusUnlessTerminal` (7 мест) или compare-and-set (13). Прямых
`setStatus(TaskStatus.…)` — **35**, в десяти файлах, и ни одна из них терминальность не проверяет.

Модель до сегодняшнего дня утверждала, что свойство «уже держится». Это было неверно, исправлено там же.

**Что требуется.** Разделить 35 мест на два класса — инициализация новой задачи и мутация загруженной, — и
перевести второй класс на терминально-осведомлённую запись. Заслон формулируется по референту, а не по
подстроке `setStatus`, иначе он ловит инициализацию. Пока разделение не сделано, ни одного утверждения о
том, что S2 выполняется, делать нельзя.

### 4.45 Часовой лимит GitHub съедается перечислением PR и роняет весь поток

**Замер 30.08.** В 17:20 контур встал целиком: `GITHUB_RATE_LIMITED` — состояние глобально блокирующее.
Предел настоящий, не наш: GitHub отвечает `used 5000 / limit 5000, remaining 0`. Через 142 секунды после
сброса израсходовано уже **234** запроса, то есть окно кончается примерно за сорок минут и повторяется
каждый час.

Учёт по операциям (§8.17) назвал самого крупного **из учтённых** потребителей:

    158  GET /repos/eneikdru/test-fiftieth/pulls
      3  GET /repos/eneikdru/test-fiftieth/branches
      2  GET .../pulls/<n>

**Но учёт был неполон, и вывод из него был бы неверен.** Замер 17:43 → 17:50: окно потеряло **1063**
запроса, а учтено за то же время **82**. Четыре пятых расхода не видел никто: бюджет записывался в двух
службах, а третья — `GithubAccessService`, с шестью собственными точками вызова — не записывала ничего.
Счёт, видящий пятую часть расхода, называет не причину, а то, что ему попалось.

**Учёт сведён.** Замер 18:02 → 18:06 после того, как каждая точка вызова стала записывать свою стоимость:
израсходовано 598, учтено 588 — **98%**. Теперь число обосновано, и оно называет одно:

    420  GET /repos/eneikdru/test-fiftieth/pulls    ← 420 из 595 за четыре минуты, 71% всего расхода
     15  GET .../branches
     10  GET .../pulls/<n>

Скорость расхода 598 за 4 минуты ≈ 150/мин ≈ 9000/час при пределе 5000. Окно не может выжить, и остановка
повторяется каждый час по построению.

**Причина в коде.** `GitHubPullRequestService.fetchPullRequests` обходит **до десяти страниц по сто** за один
вызов, то есть один вызов стоит до десяти запросов, и обходит он всю историю PR репозитория заново. При 420
запросах за четыре минуты это порядка десяти полных обходов в минуту.

**Решение — §8.5, монотонная метка.** Полный обход всей истории на каждом такте есть в точности отсутствие
такой метки: ничто не говорит «только то, что изменилось с X». GitHub умеет отдавать список, отсортированный
по времени изменения; обход обязан идти от свежайшего и **останавливаться на метке**, а метка — продвигаться
не самим обходом, а появлением нового PR.

    walk(repo) = страницы sort=updated&direction=desc, пока updatedAt(pr) > watermark(repo)
    watermark(repo) ← max updatedAt увиденного PR, записывается после успешного обхода

Число страниц тогда не назначается, а следует из того, сколько PR действительно изменилось. До реализации
утверждать, что предел исправлен, нельзя.

### 4.46 Счёт бюджета GitHub складывает разные окна в одно

**Замер 30.08 18:33 → 18:37.** Учтённый расход за четыре минуты вышел **отрицательным** (12 → 11), а доля
перечисления PR — с 12 до 2. Причина не в вызовах: состояние бюджета одно на всю фабрику
(`AtomicReference<BudgetState>`), а вызовы идут под **разными токенами**. `GitHubPullRequestService` берёт
один `github_token` из настроек, но `GithubAccessService` принимает токен аккаунта параметром, и у каждого
токена свой предел и свой `x-ratelimit-reset`. Разложение по операциям, добавленное в тот же день,
обнуляется при каждой смене окна — то есть при каждом переключении токена.

    remaining, limit, resetAt, spend(o)  — величины ОДНОГО окна одного токена
    состояние                            — одно на все токены

**Следствие.** Ни `remaining`, ни разложение нельзя читать как факт о какой-либо конкретной ёмкости: они
перемешивают окна. Вывод «столько-то съело такое-то обращение» обоснован только внутри одного токена.

**Что требуется.** Ключевать состояние бюджета по токену (по его отпечатку, не по значению), и тогда
`GITHUB_RATE_LIMITED` перестанет быть утверждением обо всей фабрике, когда исчерпан один аккаунт. До этого
числа §4.45 остаются порядковыми, а не точными.

### 4.47 Записи о блокере не становятся работой

**Расхождение с §8.19 и §8.12, измерено 30.08.** Фабрика сама предписывает агенту остановиться и записать
блокер вместо цикла на восьмом сообщении. В живом контуре эти записи и производятся:

    PR #493  "Record concrete blocker for API Slice 2c3442ef"
    PR #496  "Blocker: Unresolvable specification misalignment for UI Slice ..."

Из **279** вишлистов проекта блокер не упоминает **ни один**. То есть находка в вишлист не превращается.

**Проверено по GitHub, 30.08 20:0x:** эти PR **не слиты** — `merged=False`, `changed_files 0`, `additions 0`,
закрыты без слияния. Онтологическая стратификация (§2) держится там, где спроектирована — в точке слияния;
заводская семантика в продукт не попала. Ранее я записал здесь обратное, это было неверно.

**Механика.** `reachedMain(τ)` истинен для слитого PR независимо от того, несёт ли он код;
`hasRequiredMergeEvidence(τ)` для роли, обязанной кодом, требует `hasCode`. Департамент реальности доставки
отбирает по первому, ценность считается по второму. Задача с записью блокера: `done`, PR слит,
`reachedMain = true` — департамент её не видит; `hasRequiredMergeEvidence = false` — ценность её не
засчитывает. Требование припарковано, и места, где это записано, не существует.

Это объясняет наблюдаемое: `done` 399 против 13 доставленных требований, и `13/19` неподвижно 4,5 часа.

**Размер множества измерен, 30.08 19:46:**

    16 done-задач доехали до main, не неся кода

Шестнадцать, не сотни. Переключение отбора на §8.19 заведёт по одному ремонту на каждую (дедупликация по
`source_task_id`), а не массовый вброс; WIP-пределы ниже по цепи ограничивают отправку. Число получено
замером, не предположением, и потому правку можно делать зряче.

**Что требуется.** Свести оба предиката к одному (§8.19) и проверить, что шестнадцать требований вернулись в
поток, а не что их стало шестнадцать в другом месте.

### 4.48 В ревью входят без предмета ревью

**Расхождение с §8.20, измерено 30.08.** Инвариант, приведённый к поквадачному квантору, назвал число:

    22:27   3 из 3 задач в ревью не несут собственного артефакта
    23:09   6 из 9
    23:11   0 из 9  — артефакты появились, инвариант pass

Третий замер снимает первое толкование: это **окно гонки**, а не растущая утечка. PR регистрируется позже
входа в ревью, и наблюдаемое число — доля задач, попавших в промежуток. Выход из состояния починен (задача, чья роль обязана кодом и у которой
на main ничего нет, уходит в `failed`, а её заявка освобождается), но **вход** остаётся безусловным:
`ClaimService.complete`, ветвь «исполнитель закончил», ставит `review` не спрашивая, существует ли PR.

**Чего делать нельзя.** Проверять артефакт прямо в момент входа опасно: PR может регистрироваться позже
завершения сессии, и отказ по гонке убьёт живую работу. §8.6, вторая строка: то, о чём ничего не
установлено, множество не покидает.

**Что требуется.** Условие входа формулируется не «есть ли артефакт сейчас», а «может ли он ещё появиться»:
задача входит в `review`, если артефакт есть **или** её сессия ещё жива. Когда сессия терминальна и
артефакта нет — попытка окончена, и это `failed`, состояние с выходами. Замерить долю каждого случая до
правки.

### 4.49 По 34 припаркованным задачам работа не заказывается

**Замер 02.09 после трёх суток без вмешательства.**

    задач done                408 → 488        слияний 410 → 496
    доставлено требований     13 из 19 → 13 из 19    ни одно из шести не сдвинулось
    припарковано              16 → 50
    свод департамента         «0 новых находок, 16 уже записано»

Пятьдесят задач доехали до main без артефакта своей роли, а находок записано шестнадцать. По остальным

припаркованности теперь один и тот же (§8.19). Значит цикл свода до них не доходит: либо прерывается, либо

**Рядом, в том же окне:** `Timeout trying to lock table "PROJECTS"`, пять раз, роняет такт оркестрации.

**Что требуется.** Замерить, на чём именно обрывается или отсеивается цикл свода: назвать причину для каждой
из тридцати четырёх, а не считать их разницей двух чисел.

## 5. Ошибочные утверждения — не воскрешать

11. **«Зависимость — это порядок работ, поэтому мёртвую можно не ждать» (§4.33, 29.08).** Введено мной в тот
    же день, что и §4.30, и **несовместимо с ним**: §4.30 объявляет зависимого при мёртвой зависимости
    тупиком и переводит в `blocked`, §4.33 разрешал его поднимать. Замер на клиентском эпике «Data Subject
    Rights and Privacy Consent», 29.08:

        19:01:38  ProjectFlowService блокирует 40dff79f — зависимость мертва окончательно
        19:02:45  допуск снимает её, дочерней работы не создаёт
        19:03:49  восстановление поднимает её, тратя единственный автоматический повтор
        19:03:50  через секунду блокировка повторяется по той же зависимости
        19:04:48  снята окончательно; эпик не доставил ничего

    Поднятие, отменяемое через секунду, — не восстановление, а расход единственного восстановления.
    Два правила о **одном** предмете обязаны проверяться на совместность до внедрения; я этого не сделал.
    Ворота возвращены: неудовлетворённая зависимость держит зависимого, а тупиковый случай завершается
    через `blocked`.



Все одной формы: вывод выдавался за измерение.

1. **«У рычага TOC ноль разрешённых наблюдений».** Считалось по одной величине, а промоция считает по
   другой. Не поднимается он из-за подменённой величины, а не из-за нехватки данных.
2. **«Фаза декомпозиции должна завершаться».** Не должна и не может: девять сервисов порождают вишлисты
   непрерывно, множество открытых брифов не опустеет никогда.
3. **«Бюджет должен списываться только на отвеченных попытках».** Ломает завершаемость: при вечно
   занятом канале вариантная функция не убывает. Верное решение — различать вердикты, а не менять её.
4. **«Реализовано» без сборки.** Весь массив правок пролежал несобранным; первая же сборка нашла отказ
   компиляции за 90 секунд.
5. **«`FAILED_PRECONDITION` означает исчерпание одновременных сессий».** Взято из надписи в интерфейсе
   Jules, а не из ответа Jules. Существующий тест это опроверг: тот же статус приходит и как
   «Repository access is not ready».
6. **«Миграция V111 навсегда закрепила настройку в базе».** Значение в живой базе — противоположное.
   Миграция присваивает один раз и ничего не запирает.
7. **«`teardown` лаунчера всегда безопасно звать».** Его `success` не означает, что что-то погашено:
   при потерянном указателе в памяти он возвращает успех, не сделав ничего.
8. **«Привязка компилятора к аккаунту — про квоту, значит её можно ослабить».** Ослабление отменено
   оператором: компилятор работает на своём аккаунте и только на нём.
9. **«Отсеять негодные задачи у каждого читателя».** Заплатка: фильтр поставили на один список отбора
   из двух, и дефект вернулся через второй. Негодное обязано покидать множество один раз (V117).
10. **Тесты, которые не могут упасть.** Подстановка на вызов, которого код больше не делает, возвращает
    пустоту — и тест, ожидающий пустоту, проходит, не проверяя ничего. Найдено дважды.

## 8. Математическая модель потока и что сделать в коде

Раздел нормативный и **исполнимый**. Формулировка — множествами и предикатами; под каждой — что именно
поменять в коде. Выполняет другой агент; порядок §7 обязателен для каждого пункта.

Словарь — три слова: **Вишлист**, **Задача**, **Эпик** (docs/GLOSSARY.md). Слово «фича» не употребляется.

### 8.0 Обозначения

    W  вишлисты   status(w) ∈ {pending, compiling, converted_to_task, dismissed}
    T  задачи     status(τ) ∈ {queued, claimed, in_progress, review, pending_review,
                               done, failed, blocked, spike_completed}
    E  эпики      epic(τ) ∈ E ∪ {∅}
    A  аккаунты   ceiling(a), dailyCeiling(a), occ(a,t) — открытых сессий в момент t
    S  сессии     одна сессия = одна ветка = один PR
    R  ревью      ciStatus(r), merged(r), session(r)

    carrier(τ)      ⟺ payload(τ).taskType ≠ ∅            носитель фабрики
    accepted(s)     ⟺ externalSessionId(s) ∉ {∅, skipped}  Jules принял сессию
    refused(s)      ⟺ externalSessionId(s) = ∅ ∧ status(s) = failed
    merged(τ)       ⟺ diff задачи присутствует в main
    terminal(τ)     ⟺ status(τ) ∈ {done, failed, spike_completed}

### 8.1 Цепь потока

    w ─κ─▶ (e, {τ₁…τₙ}) ─δ─▶ s ─▶ PR ─ρ─▶ гейты ─μ─▶ merged ─▶ done

`κ` компиляция, `δ` отправка, `ρ` ревью, `μ` слияние — частичные функции с предусловиями. Ни одна не
выполняется дважды для одного элемента без явного возврата предыдущего шага.

**Что сделать в коде:** ничего; это определение, к которому апеллируют остальные пункты.

### 8.2 Разделение носителей и продукта

    T = T_прод ⊔ T_нос,   τ ∈ T_нос ⟺ carrier(τ)
    замерено 29.08:  ∀τ (carrier(τ) → epic(τ) = ∅)   и   |{τ : carrier(τ) ∧ epic(τ) ≠ ∅}| = 0

**Инвариант.** Правило о продукте не применяется к носителю, и наоборот.

**Что сделать в коде.**
1. Свести предикат `carrier` к одному определению. Сейчас он написан минимум трижды:
   `ProjectFlowService.isWishlistCompilerTask` / `isHousekeepingCarrierTask`,
   `FlowSpineService.isFactoryCarrierTask`, инлайн в `JulesDispatchService.reconcileTaskStatusAgainstGitHubTruth`.
   Оставить один — методом на `TaskEntity`, — остальные заменить вызовами.
2. Структурный тест: `payload.hasNonNull("taskType")` встречается ровно в одном месте кодовой базы.

### 8.3 Правило бюджета

Пусть бюджет `B` со счётчиком `c` ограничивает повторы относительно предмета `X`, а `Ev(X)` — множество
событий, являющихся свидетельством о `X`.

    Δc = 1  ⟺  произошло e ∈ Ev(X)

| бюджет | предмет `X` | `Ev(X)` |
|---|---|---|
| `compileAttempts(w)` | бриф | компилятор ответил: пустой ответ **или** принятый |
| `A(τ)` = \|{s : task(s)=τ ∧ refused(s)}\| | потраченная ёмкость | всякий отказ; вина не вменяется |
| `retryCount(τ_нос)` | наши просьбы к одному носителю | каждая просьба |
| `resumeCount(τ)` | оживление задачи | одно на задачу |

**Следствие.** Попытка, не дошедшая до компилятора, бюджет брифа не тратит (сделано, §4.19). Попытка, ответ
на которую отвергла **наша** проверка, — тоже: о брифе она не сказала ничего.

**Что сделать в коде.**
1. Ввести константу пустого ответа рядом с `JulesDispatchService.compilerPlanRejection` — строку, которую та
   возвращает при `epics.isEmpty()`. Сравнивать по ней, не по подстроке.
2. В `completeWishlistCompilation`: при `rejection ≠ ∅ ∧ rejection ≠ EMPTY` вызвать новый
   `ProjectFlowService.returnCompileAttempt(Set<UUID> wishlistIds)` рядом с уже стоящим
   `releaseUnfinishedClaims`. То же в персистентном пути, где вычисляется `cycleRejection`.
3. `returnCompileAttempt` уменьшает `compileAttempts` на единицу, не ниже нуля, и ничего больше.
4. Миграция: вернуть бюджет брифам, чей вердикт вынесен до появления записи причины. Опознание точное и
   замерено: `status='pending' ∧ compiled_by_role IS NULL ∧ compile_attempts ≥ 3 ∧ last_compile_reached_at
   IS NOT NULL`, и ни один из них не породил ни одной задачи. Обоснование — §8.8: вердикт по нечитаемому
   свидетельству недействителен.
5. Тесты: отказ нашей проверки `compileAttempts` не двигает; пустой ответ двигает.

### 8.4 Правило цикла

    ∀ цикл L ∃ v: Состояние → ℕ,  v ограничена снизу,  v строго убывает на каждом обороте L

    отправка задачи:   v = A_max(τ) − A(τ),  A_max = 2·|{a : status(a) ≠ decommissioned}|
    компиляция брифа:  v = бюджет(w) − compileAttempts(w),  обороты разрежены кулдауном
    повторы носителя:  v = MAX_RETRIES − retryCount(τ)
    оживление:         v = 1 − resumeCount(τ)
    возврат бюджета:   каждый возврат потребляет строго более позднее событие канала

Цикл без такой величины — проживание, а не повтор. Запрещён.

**Что сделать в коде.**
1. Ревьюерский путь величины не имеет: `ProjectFlowService.dispatchReviewTasks` при отказе не считает
   попытку, не возвращает притязание и порога не знает. Устраняется пунктом 8.9 — после сведения к общей
   реализации он получает `A(τ)` и порог автоматически.
2. Структурный тест: всякое место, вызывающее `julesDispatchService.dispatch(...)` внутри цикла по задачам,
   обязано делать это через единую реализацию отправки.

### 8.5 Правило метки

    mark: Состояние → Время ∪ {−∞},  монотонна,  и ни один переход самого цикла её не продвигает

Метку двигает только событие внешней стороны: принятая сессия, слияние, ответ.

| метка | что двигает | чей канал |
|---|---|---|
| `A(τ)` | отказ при создании | наш расход |
| `W_c(project)` | принятая сессия на аккаунте компилятора | канал компилятора |
| отказной ряд аккаунта | принятая сессия этого аккаунта | канал аккаунта |
| `lastCompileReachedAt(w)` | сообщение действительно ушло компилятору | канал компилятора |
| `lastMessageSentAt` работника | отправленное сообщение | канал работника |

**Что сделать в коде.**
1. Для каждой метки — тест, что отказ её не продвигает.
2. Структурный запрет: метка не берётся из таблицы, в которую пишет сам механизм повтора, без фильтра
   «только успехи». Проверяется тем же структурным тестом, что и §5b.

### 8.6 Правило множества решения

    ¬∃ путь x → done   ⟹   x покидает множество решения ровно один раз, в данных
    ничего не установлено о x   ⟹   x множество НЕ покидает

Не отсеивается у каждого читателя: читателей со временем больше, один пропущенный возвращает дефект (§5.9).

**Что сделать в коде.**
1. Пройти фильтры знаменателей в `ClientDeliverableReadinessService.computeForSources` и
   `FlowSpineService.inputs`: каждое исключение обязано иметь рядом довод, почему элемент структурно не
   может дойти до `done`. Исключения без такого довода — снять.
2. Тест на симметрию: для каждого исключаемого класса существует случай «неизвестно», который **не**
   исключается.

### 8.7 Правило убеждения о внешней системе

    ceiling(a) ← ceiling(a) + шаг            при accepted(s) ∧ occ(a, t(s)) ≥ ceiling(a)
    ceiling(a) ← max(1, ⌊k · откат⌉)         при отказе, где k = occ(a, t) в момент отказа

Рост только от настоящего успеха, падение только от настоящего отказа, никогда — от собственной константы.
Начальное значение конфигурационное; до первого свидетельства поведение прежнее.

**Что сделать в коде.**
1. Сделано для дневной и параллельной ёмкости (`estimatedDailyCapacity`, `estimatedConcurrentCapacity`).
2. Добавить тест: значение из конфигурации не может ни поднять, ни опустить убеждение — двигают только
   `AccountHealthService.reportDispatchOutcome` на настоящих исходах.
3. Записать в коде различие: `WISHLIST_COMPILE_ATTEMPT_BUDGET` и `MAX_RETRIES` — **наши** проектные решения,
   не гипотезы о чужой системе, и этому правилу не подчиняются.

### 8.8 Правило сообщения

    denial(действие, состояние) = c,  где c — конъюнкт, который не выполнился

Не состояние, если состояние ни при чём. Не «недействителен», если проверок четырнадцать. Уровень записи
следует из того же предиката: норма пишется INFO, не WARN.

    отказ без читаемой причины  ⟹  он не может быть основанием поглощающего вердикта

**Что сделать в коде.**
1. Пройти все `log.warn`, повторяющие неизменный факт, и перевести на идиому «писать только при изменении»
   (образец — `ProjectFlowService.withholdFromCompileDispatch`).
2. Запретить сообщения, называющие несколько причин сразу: одно сообщение — один конъюнкт.
3. Тест: каждое сообщение об отказе содержит имя конъюнкта, а не перечисление возможностей.

### 8.9 Правило единственной реализации

    |impl(I)| = 1   для инварианта I = «как задача попадает в Jules»

Различие путей выражается **аргументом**, не второй копией: закреплённый аккаунт, исключаемые аккаунты,
режим (`IMPLEMENTER` / `REVIEWER`).

**Что сделать в коде.**
1. Свести `ProjectFlowService.dispatchReviewTasks` на `dispatchToGeneralPool` с режимом `REVIEWER`.
2. Свести `dispatchCompilerTask` на ту же реализацию с аргументом «только этот аккаунт по имени», сохранив
   решение §5.8 (компилятор ходит своим аккаунтом) как значение аргумента, а не как отдельный код.
3. Структурный тест: `accountRepository.lockNextJulesAccountWithCapacity` и `lockAccountByNameWithCapacity`

### 8.13 Правило готовности

2. Тест: потребитель, ждущий готовности, срабатывает дважды при двух фронтах и ни разу при удержании.

### 8.17 Правило ёмкости контура

Департаменты делят одну ёмкость — живые аккаунты.

    порядок допуска:  компилятор ≺ продуктовая работа ≺ самопорождённая ≺ носители фабрики

Выражается **порядком**, не запретом: запрет умеет сказать «никогда», порядок умеет сказать «позже» (§4.8).
Тяжёлые такты идут под верёвкой часового TOC и под бюджетом внешнего API.

Общая ёмкость обязана быть **относимой к потребителю**. Порядок допуска — утверждение о том, кто уступает
кому; применить его к расходу, который нельзя разложить по потребителям, невозможно в принципе.

    spend(o, W)  расход операции o за текущее окно предела W
    ∀ o: spend(o, W) наблюдаем, и при исчерпании окна разложение называется целиком

Это относится и к внешнему пределу: часовой лимит GitHub — общая ёмкость ровно того же рода, и его
исчерпание останавливает поток целиком (`GITHUB_RATE_LIMITED` глобально блокирующее). Предел, съеденный
неизвестно кем, повторится в следующем окне и в каждом следующем.

**Что сделать в коде.**
1. Дизайн-цех ходит своим тактом и своим флагом; его носители в порядке допуска общего пула не участвуют.
   Замерить, съедает ли он ёмкость у продуктовой работы, и при необходимости завести в тот же порядок.
2. Тест: `queuedDispatchClass` покрывает все классы задач, которые доходят до отбора аккаунта.
3. Бюджет внешнего API считает расход по операциям, а не хранит последнюю. Шов уже есть — `recordResponse`
   принимает имя операции; хранится только последнее. Ключ нормализуется до пути без строки запроса, иначе
   множество ключей неограниченно (номера страниц).

### 8.19 Правило предмета слияния

Слияние доставляет требование только если слитый diff несёт **код** — для роли, которая кодом обязана.

    landed(τ)  ⟺  ∃ r: merged(r) ∧ base(r) = main ∧ hasCode(r)        для роли, обязанной кодом
    landed(τ)  ⟺  ∃ r: merged(r) ∧ base(r) = main                     иначе

Фабрика намеренно разрешает агенту остановиться и **записать блокер** вместо бесконечного цикла — это её
собственное правило против зацикливания, и оно верно. Но запись блокера, слитая в main, есть находка, а не
доставка. По §8.12 находка обязана стать вишлистом и вернуться в цепь; иначе требование припарковано молча:
задача `done`, PR слит, доставки нет, и не существует места, где это записано.

Отсюда требование согласованности: предикат «доехало», по которому департамент решает, есть ли о чём
говорить, и предикат «доставлено», по которому считается ценность, обязаны отвечать на один вопрос одинаково
(§2, одна точка применения). Расхождение между ними — это в точности множество требований, о которых никто
не говорит.

**Что сделать в коде.**
1. `DeliveryRealityProducerService` отбирает по `reachedMain`, а ценность считается по
   `hasRequiredMergeEvidence`; первый не смотрит `hasCode`, второй смотрит. Свести к одному предикату.
2. Тест: задача, чей слитый PR не несёт кода, считается недоставленной обоими; задача со слитым кодом —
   доставленной обоими. Второй случай обязателен, иначе правило превращается в «всё недоставлено».

### 8.20 Правило предмета ревью

    review(τ)  ⟹  ∃ r: артефакт ревью, принадлежащий τ

Задача в состоянии ревью без собственного артефакта не может продвинуться: рецензенту нечего смотреть, а
`DISPATCH_REVIEW_TASKS` при этом разрешён и будет отправлять в пустоту.

Квантор здесь **по задаче**, а не по проекту. Проверка вида «есть ли в проекте хоть один открытый артефакт»
отвечает на другой вопрос и путает два разных положения:

    τ в ревью, артефакта нет вовсе        — дефект: состояние без выхода
    τ в ревью, её артефакт уже слит       — норма: задача вот-вот уйдёт дальше

Предупреждение, срабатывающее на втором, учит читателя, что предупреждения не про проблемы, — та же муда,
что и повторение неизменного факта каждый такт (§8.11 O9).

**Что сделать в коде.**
1. `FlowSpineService`: инвариант `review_requires_artifact` сравнивает `reviewTasks > 0` с
   `openReviews == 0` — агрегат против агрегата. Считать задачи в ревью, у которых **нет ни одной** строки
   ревью, и называть их число.
2. Тест: задача в ревью без артефакта нарушает инвариант; задача в ревью со слитым артефактом — не
   нарушает. Второй случай обязателен, иначе проверка снова срабатывает на норме.

### 8.21 Ремонт — это оборот цикла, и он обязан иметь вариантную функцию

§8.12 обязывает всякую находку стать вишлистом, §8.18 — считать требование погашенным по замыканию ремонта.
Вместе они описывают **цикл**: попытка не доставила → заведён ремонт → его задача не доставила → заведён
ремонт ремонта. По §8.4 у такого цикла обязана быть величина, ограниченная снизу и строго убывающая на
каждом обороте. У него её нет: каждый оборот создаёт **новую** личность задачи, поэтому ни `resumeCount`,
ни `retryCount`, ни `compileAttempts` не двигаются.

Замер 02.09, за трое суток без вмешательства:

    задач `done`                408 → 488
    слияний                     410 → 496
    доставлено требований       13 из 19 → 13 из 19        ни одного
    припарковано (доехало без артефакта своей роли)  16 → 50
        из них BARCAN-TAG-00     5 → 39

`BARCAN-TAG-00` — роль, которой клеймится сам ремонтный бриф.

**Замер глубины опроверг первое толкование.** Гипотеза была: ремонт ремонта компаундится. Распределение
глубин цепи, 02.09: `{1=122}` — второго порядка **нет ни одного**. Значит это не компаундящийся цикл, а
широкий веер первого порядка, и §8.4 здесь пока не нарушен. Величина цепи всё равно нужна — оборот второго
порядка возможен по построению и ничем не ограничен, — но срочности, которую я ей приписал, нет.

**Что измерение показало вместо этого.** Ремонтов 441 (272 стали задачами, 167 отброшены), припарковано 50
задач, а свод сообщает «**0 новых** находок, 16 уже записано». То есть по 34 припаркованным задачам работа
не заказывается вовсе: дуга §8.12 для них разомкнута, а не зациклена. Это и есть настоящее расхождение, и
оно противоположно тому, что я записал первым.

    v(w) = A(w) − repairDepth(w),   repairDepth = длина цепи ремонта того же требования

Величина принадлежит **требованию**, а не задаче: попытки различны, требование одно. `A(w)` не назначается —
она выводится тем же механизмом пересмотра, что и предел декомпозиции (§8.3, §4.36): вниз по настоящему
свидетельству, что очередной ремонт снова ничего не доставил, вверх — по успеху на самой границе.

Исчерпание величины поглощающе и обязано быть **записано**: требование, которое ремонт не доставил за
отведённые обороты, перестаёт порождать работу и остаётся названным как недоставленное — как
`decompositionRefused` для брифа. Молча прекращать нельзя: непорождающее и невыполненное требование, о
котором нигде не сказано, есть ровно та потеря, ради устранения которой §8.12 и написан.

**Что сделать в коде.**
1. Ремонтный вишлист несёт ссылку на исходный плановый элемент, чтобы глубина цепи была наблюдаема
   (`sourceTaskId` даёт только предыдущее звено).
2. Замерить распределение глубин до выбора `A(w)`. Число выводится из наблюдения, а не назначается.
3. Тест: цепь, исчерпавшая величину, перестаёт порождать ремонты и оставляет запись; цепь, у которой
   величина ещё есть, ремонт заводит. Второй случай обязателен, иначе правило гасит поток целиком.

### 8.18 Правило погашения требования

Требование несёт плановый элемент, а не задача. Задача — попытка. Когда попытка проваливается, департамент
реальности доставки заводит ремонт того же требования (§8.12), и этот ремонт обязан **гасить исходное
требование**, а не только производить работу рядом с ним.

    repairs(w′) = τ            ⟺  sourceTaskId(w′) = τ
    closure(w)  = {τ : sourceWishlist(τ) = w}
                ∪ {τ′ : sourceWishlist(τ′) = w′  ∧  repairs(w′) ∈ closure(w)}
    fulfilled(w) ⟺ ∃ τ ∈ closure(w) : merged(τ)

Требование погашено, если слит diff **любого** звена его цепи ремонта, а не только первой попытки. Замыкание
конечно: каждое звено ссылается на задачу, существовавшую раньше него.

Без этого правила департамент производит работу, которая структурно ничего не может погасить: ремонт лежит
на вишлисте, источник которого не входит в область продуктовой итерации, а задача ремонта ссылается на
вишлист ремонта, не на плановый элемент. Тогда исходное требование остаётся невыполненным навсегда, сколько
бы раз его ни доставили на самом деле. Это §8.15 наоборот: там `done` принимали за доставку, здесь настоящую
доставку не принимают ни за что.

**Что сделать в коде.**
1. `ClientDeliverableReadinessService`: `fulfilled` для планового элемента считать по замыканию ремонта, а не
   только по задачам самого элемента. Область источников (`PRODUCT_ITERATION_SOURCES`) при этом не
   расширяется — ремонт не становится отдельным требованием, он гасит существующее.
2. Тест: элемент, чья первая задача провалилась, а ремонт слит, считается выполненным; элемент, чей ремонт
   ещё не слит, — не считается. Второй случай обязателен, иначе правило превращается в «засчитать всё».
