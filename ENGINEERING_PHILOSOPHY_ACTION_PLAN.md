## 1. Как здесь работать (дорого добытое)

Нарушение любого пункта стоило этой сессии часов.

**Файловая шара Windows ненадёжна.** Она теряет записи и чтения под нагрузкой, отдаёт компилятору
только что записанные файлы как отсутствующие, и держит блокировки от убитых контейнеров. Проявления:
`MVStoreException ... read 0`, `Writing to FileChannel failed`, `cannot find symbol` сразу после успешной
компиляции, `The file is locked` на файле, который никто не держит.

* Живая база — только в томе Docker, никогда на шаре.
* Сборка и тесты — копировать исходники **внутрь** контейнера (`cp -r /src/src /build`), не собирать
  на монтировании. Это превращало воспроизводимый провал в зелёный прогон без единой правки кода.

**Ресурсы хоста ~3.3 ГБ.** Сборка образа при поднятом контуре не проходит; при остановленном проходит
с первой попытки. Полный `mvn test` одной командой сначала выдаёт выдуманные падения через
`Cannot allocate memory` при сканировании classpath, затем роняет демон Docker. Гонять тесты по классам.

**Замер базы достоверен только при остановленном сервисе.** Копия живого H2-файла рвана по определению:
одни и те же запросы давали противоречивые ответы, пока бэкенд писал. Мерить со статичной копии,
сверяя md5.

**Интероп WSL рвётся.** `accept4 failed 110` на `docker.exe`. Лёгкие команды переживают, тяжёлые — нет.
Оборачивать вызовы ретраями.

**Апостроф в комментарии внутри `@Query` — незакрытая кавычка.** Spring Data сканирует всё значение
аннотации на кавычные диапазоны и не исключает комментарии `--`. Один апостроф в слове с притяжательным
падежом уронил контекст на старте: `The string <SELECT ...> starts a quoted range at 3712, but never ends
it`, 43 перезапуска подряд, 29.08. Проверка — чётность апострофов внутри каждого блока `@Query(value = """`.

**Монитор — только на однократные события** (конец сборки, падение теста). Направленный на лог
работающей фабрики, он превращает каждую строку цикла в уведомление и топит канал.

## 2. Действующие инварианты

Не предложения, а норма. Нарушение — дефект, а не повод для обсуждения.

**Онтологическая стратификация.** `Code(t) ∩ ℒ_factory = ∅`. Проверяется в точке, где слияние физически
происходит, не у вызывающего.

**Одна точка применения (Хартия, инв. 10).** Проверка живёт там, где совершается действие. Тест на
верность предиката — не тест на его применение; нужен и второй.

**Точный знаменатель (Хартия, инв. 8).** Элемент, структурно неспособный дойти до «выполнено», обязан
покинуть множество, по которому принимается решение. Иначе решающий код блокируется молча.

**Независимый свидетель (Хартия, инв. 12).** Сторона, производящая результат, не может быть единственным
подтверждением его корректности.

**Монотонная метка (Хартия, инв. 7).** Механизм «повторить, если появилось новое» сравнивается с меткой,
которую сам не может продвинуть.

**Укоренённость.** `EE = 0.40·C + 0.35·K + 0.25·E_EMS`. Неклассифицированная ось стоит 20, а не середину:
неизвестное положение в паутине убеждений — самое слабое, а не среднее. При `E_EMS = 0` потолок 67.5,
то есть в CORE без верифицированного контракта не войти.

**Anti-Starvation.** Смена статуса атомарно пишет `t_state`; при `null` нижняя граница
`min(t_heartbeat, t_updated, t_created)`. Кулдаун с полным джиттером `U(T_base, T_ceiling)`. Гистерезис:
отказ `k ← min(k+1, k_max)`, успех `k ← max(0, k−1)`. `offline` со свежим пульсом релаксирует в `idle`.

**Zero Muda.** Механизм зарегистрированный, но ни разу не сработавший, — муда, а не защита.

## 3. Закрыто и подтверждено измерением

Строка стоит здесь только если рядом наблюдение, а не намерение.

**Штатное завершение контейнера.** `ENTRYPOINT ["sh","-c","exec java ..."]`. Наблюдено дважды: код
выхода `143` вместо `137` и строка `H2 store compacted on shutdown in 3772 ms`.

**База вне файловой шары** — в томе Docker; старт бэкенда ускорился в разы.

**Память ограничена у всех пяти служб.** `backend` 1 ГБ, `ml` 768 МБ (модель 0.22 ГБ + onnxruntime),
`judgment-proxy` 256 МБ, `runtime-launcher` 256 МБ, `frontend` 128 МБ. Сумма 2432 из 3500 МБ потолка
WSL. Пул Hikari 24 → 12. Второе число `-Xmx` из `Dockerfile.backend` удалено: величина одна — `mem_limit`.

**Образ 1.59 ГБ → 639 МБ.** Из `apt-get` убраны семь пакетов. Замер: JVM запускает процесс только через
`ProcessBuilder` или `Runtime.exec`; вторых ноль, первых три, и все три — `git`.

**Стоимость чтений на горячих путях.** `AutoMergeService` 10 полных чтений таблицы за такт → 0,
`JulesDispatchService` 4 → 2 (обе на ограниченных таблицах), `ContinuousOrchestrationService` 2 → 1.
Плюс пять мест сверх исходного порядка работ. Заслон: `ScheduledQueryCostInvariantTest` падает на любом
классе, который планирует работу чаще суточного и читает растущую таблицу целиком.

**Пока-ёкэ на слиянии.** `MergeChokePointPokaYokeTest` требует, чтобы всякое место, строящее
`PUT /merge`, сперва спросило гейт. Проверено: мусорный PR №170 закрыт, в `main` клиента не попал.

**Разбор PR не вклеивается в задание.** Задание на ревью несёт ссылку; ревьюер читает PR в
репозитории, где работает. До правки одно такое задание достигало 1 788 060 знаков при медиане 10 437.

**Отказы Jules различаются по тому, чьё условие не выполнилось.** `INVALID_ARGUMENT` — дефект фабрики,
аккаунт не наказывается; `401/403` и названные условия аккаунта — вина аккаунта; условие без названия
не вменяется никому. Наблюдено на живых данных: отказ пришёл, аккаунт остался цел.

**Отбор аккаунта не переизбирает сам себя.** Было `ORDER BY открытые сессии ASC, last_heartbeat DESC`,
а `ClaimService` пишет `lastHeartbeat` в момент притязания — выбранный становился самым свежим и
выбирался снова. Наблюдено: 34 отказа подряд через один аккаунт при шести свободных. Стало `ASC` в трёх
запросах отбора; четвёртый выбирает по имени, там порядок ни на что не влияет.

**Носители с заданием удалённого построителя закрыты в данных** (`V117`), а не отсеиваются при чтении.

**Отправка перестала быть незавершаемой** (бывш. §4.1, `4ea9bc4`). Цикл `queued → отказ при создании
сессии → queued` не имел убывающей величины: `retry_count` растёт только там, где сессия уже существовала.
Замер до правки: один носитель — 67 отказных сессий на 7 аккаунтах за 4.5 суток при `retry_count = 0`,
компиляторное задание — 123, и 375 из 775 сессий за всю историю — отказы, не породившие ничего. Допуск
`A(τ) < 2·N_live`, где `A` — число уже записанных отказов при создании (счётчик лежал в данных, монотонен,
растёт на 1 за итерацию), `N_live` — число не-`decommissioned` аккаунтов. Выход — `blocked` плюс
`NeedsHumanReview`, тем же путём, что у компилятора; вина не вменяется, фиксируется расход. Наблюдено
29.08 01:58:01 на живых данных: `Task b2c7e8fe ... left the dispatch queue: 14 refused session creations
against a budget of 14. Routed to human review rather than requeued.`

**Чистая база снова строится** (`f6891f8`). V113 удалял строки из трёх таблиц, которых на свежей цепочке
нет: `project_event_log` и `project_observer_watermark` удалены миграцией V58 за пятьдесят пять шагов до
него, `role_threads` переименована в `feature_threads` миграцией V45 за шестьдесят восемь — и V113 удалял из
обоих имён, так что старое было мёртвым всегда. Следствие было измерено дважды: `TaskClaimServiceTest` — 8
ошибок загрузки контекста, `OrchestrationStatusTest` — 1, обе с `Table ... not found`, и развернуть систему
с нуля было нельзя. Три мёртвых оператора удалены. Правка применённой миграции безопасна здесь и только
здесь: `validate-on-migrate` выключен, а `EneikProductionApplication` зовёт `flyway.repair()` до `migrate`.
Наблюдено с обеих сторон: на пустой схеме `Successfully applied 118 migrations ... now at version v118` и 9
из 9 тестов зелёные; на живой базе `Successfully repaired schema history table`, `Current version: 118`,
старт чистый, 0 перезапусков.

**Оживление провалившихся снова может сработать** (бывш. §4.12, `d026114`). Замер до правки: 311 `done`,
68 `failed`, 3 `queued`, открытых сессий ноль; все три очередные ждали провалившуюся зависимость.
`RECOVER_FAILED_FRONTIER` разрешался каждый такт и был пригоден **ни для одной из 68**: белый список
`PRODUCT_SOURCES` требовал источник вишлиста из четырёх названных, а у провалившихся источники были
`<none>` (58), `delivery_never_reached_main` (9), `frontend_unbacked_records` (1). Список поддерживался
руками и уже отклонял законную работу однажды — его собственный комментарий описывает, как попытки Gemini
молча отвергались три цикла подряд. Признак, который список подменял, замерен: из 68 у 60 есть `feature_id`,
8 — носители фабрики, **носителей с `feature_id` ноль**. Белый список и обязательный вишлист убраны, признаком
стало наличие фичи; карантин внецикловой работы сохранён и вынесен на `WishlistSource` одним определением для
обоих читателей. Сколько раз (`resumeCount < 1`) и почему (`RETIRED_WITH_NOTHING_LEFT_WORKING_IT`) — не
тронуты, радиус тот же. Наблюдено 29.08 05:19:42: `Resumed 3 existing planned task(s)`, и все три отправлены
за полминуты на `fivedmitr-sys`, `eneikcoworking-ctrl`, `EneikGroup`. 51 из 51 тестов зелёные.

**Отказ называет то, что его вызвало** (бывш. §4.6, `c3cbbd2`). Замер до правки: `policy denied
DISPATCH_REVIEW_TASKS` пятнадцать раз за пятнадцать минут, единственное запрещённое действие, с текстом
«denied by Flow Core state DECOMPOSING» — при том что в тех же тактах разрешён `CHECK_COVERAGE_AUDITS`, чьё
множество запрещающих состояний побайтово то же. Значит `DECOMPOSING` не запрещал ни того ни другого, а
отказ шёл по собственному конъюнкту действия (`reviewTasks > 0 || openReviews > 0`), то есть «ревьюить
нечего». Это стоило часа прямо в этой сессии: состояние разбиралось как блокирующее поток именно потому, что
его назвало сообщение. Введён предикат `stateBlocks(state, projectStatus)`; при его ложности отказ не
приписывается состоянию. Уровень записи следует из того же предиката: норма пишется INFO. Попутно множество
`{FROZEN, PROJECT_NOT_ACTIVE, ACCEPTED, ARCHIVED, GITHUB_RATE_LIMITED, BLOCKED_BY_DUPLICATE_CONTENT}`,
выписанное в файле одиннадцать раз, сведено к одной константе — десять копий заменены, одиннадцатая
намеренно оставлена литералом, потому что она есть то же множество **минус** одно состояние, и разница
должна быть видна на месте. Наблюдено 29.08 04:49: `DISPATCH_REVIEW_TASKS is not blocked by Flow Core state
DECOMPOSING; its own precondition is unmet - there is nothing for it to act on right now`, уровень INFO, ни
одного WARN за окно. 43 из 43 тестов зелёные, четыре новых в `OperationalPolicyReasonTest`.

**Состояние строится раз за такт, а не раз на вопрос** (бывш. §4.5, `5e1e301`). Замер до правки: 52 строки
`FlowSpine: delivery verification` за 20 минут, побайтово одинаковые (`passed=92 failed=0 REFUTED=45
NEVER ASKED=245 of 382 tasks`), до пяти в одну секунду. Каждая — полный пересчёт: вся история задач проекта,
вишлисты, сессии по этим задачам, ревью по этим сессиям, расчёт готовности и пятнадцать проходов стримом.
Спрашивал `ContinuousOrchestrationService`: **десять `isAllowed` за такт**, и
`authorize(projectId, action)` строил модель на каждый. Перегрузка `authorize(FlowCoreDto, action)` уже
существовала — не хватало способа получить снимок; добавлен `snapshot(projectId)`, такт берёт его один раз
на проект. Замер после: 8 тактов, 33 построения — **4 на такт**, из них одно от оркестрации вместо десяти.
Оставшиеся три — `requireAllowed` внутри `ProjectFlowService`, `AutoMergeService` и
`ClientDeliverableReadinessService`, то есть предусловия самих действий; по доводу этой же правки они
обязаны читать свежее состояние, и в снимок их не заводят. Заслон `ScheduledQueryCostInvariantTest` этого не
ловил и не ловит: он смотрит классы с `@Scheduled`, а `FlowSpineService` зовут из помеченного.

**Признак отказного ряда считает, а не даёт один бит** (бывш. §4.13, `47a8b19`). Введённый утром ведущий
член был двоичным, и под нагрузкой он насыщался ровно так, как предупреждало собственное предложение: недавний
отказ есть у всех, бит у всех равен единице, решает следующий ключ — «меньше открытых сессий», — а он
предпочитает того, кто ничего не несёт. Замер: за 15 минут 10 отправок против 37 отказов, из них 21 на
`eneikdru` при нуле успехов, и **`eneikdru` выбирался первым одиннадцать раз** при 0 занятых из 15 и восьми
часах без единой принятой сессии. Член заменён на число отказов, записанных после последней принятой сессии
этого аккаунта: у принимающего иногда он мал, у не принимающего равен всей серии, обнуляется единственным
событием, которое производит Jules. Наблюдено после развёртывания: **`eneikdru` не выбран первым ни разу** за
12 минут; первыми идут `sixdmitrsix-ops`, `eneikcoworking-ctrl`, `fivedmitr-sys`, `dmitriieneik-rgb`, отправки
прошли на пяти аккаунтах. 19 из 19 тестов зелёные, включая `AccountRepositoryIntegrationTest` на настоящей
H2 — проверку, которую открыл фикс V113. Доля отказов при этом не изменилась (15 против 6): почему Jules
отказывает, по-прежнему не установлено, это §4.3.

**Отбор больше не предпочитает аккаунт за то, что тот ничего не несёт** (бывш. §4.11, `7a6beff`,
исправление `e125c79`). Замер 29.08 03:30: `eneikdru` — `idle`, **ноль занятых сессий**, потолок 15, то есть
самый пустой и самый ёмкий в пуле, при 206 отказах подряд; остальные шесть — по 0–1 сессии, потолок 3, все
принимали в последний час. Порядок `открытые сессии ASC, last_heartbeat ASC` ставил его первым, потому что
отказ сессий не создаёт: та же форма, что §3 уже закрыл для `last_heartbeat`, одним ключом выше. Добавлен
ведущий член `inRefusalRun` — единица, если последняя по времени запись аккаунта среди принятых сессий и
отказов при создании есть отказ. Отказом его не улучшить: отказ пишет строку без внешнего идентификатора и
двигает аккаунт назад; выйти из ряда можно только принятой сессией, которую производит Jules. Порядок, не
исключение: если в ряду окажутся все, порядок совпадёт с прежним. Миграция V118 добавляет индекс
`jules_sessions(account_id, created_at)`, которого не было вовсе, — он обслуживает и уже существовавший
подзапрос в том же `ORDER BY`. Наблюдено после развёртывания: обе отправки общего пула ушли на
`dmitriieneik-rgb` и `fivedmitr-sys`, `eneikdru` не выбран ни разу, хотя по прежнему порядку стоял бы первым;
две попытки на нём — закреплённый компиляторный путь, отбирающий по имени и не затронутый. 39 из 39 тестов
зелёные, два новых структурных в `AccountSelectionFairnessTest`.

**Возврат бюджета брифам питается с нужного канала** (бывш. §4.10, `30cae23`). Знак возврата из `dc8a586`
был определён как последняя принятая сессия для проекта — любая. Аккаунт компилятора `eneikdru` не принял ни
одной сессии с 28.08 21:36, а шесть других принимают работу общего пула постоянно, и каждая приёмка двигала
знак. Замер 29.08: цикл `restored 6 brief(s)` → компиляторное задание → 14 отказов → `left the dispatch
queue` → `reopened 6 wishlist(s)` → снова, каждые ~13 минут, при полностью здоровом общем пуле (2 отправки,
0 отказов за те же 25 минут). Знак сужен до аккаунта компилятора: `W_c` — последняя принятая сессия **на нём**,
любой задачи. Не до компиляторных сессий: это дало бы тупик — без бюджета нет задания, без задания нет
сессии, без сессии нет знака. Наблюдено после развёртывания: восстановлений ноль, счётчик брифов пошёл вниз
вместо сброса, компиляторное задание снялось по порогу и **нового не создано**; за последние три минуты
окна — ни одного отказа компилятора, тогда как до правки они шли непрерывно. 39 из 39 тестов зелёные.

**Отправка сведена к одной реализации** (бывш. §4.9, `1d2952c`). `dispatchQueuedTasks` держал вторую копию
`dispatchToGeneralPool`, отличавшуюся ровно там, где это важно: она передавала `null` вместо исключаемого
имени и при отказе переходила к следующей **задаче**, а не к следующему **аккаунту**. Замер 29.08, живой
лог за 20 минут: 126 отказов, **все на `eneikdru`**, при 7 успешных отправках на шести других аккаунтах в
том же окне — и отказы приходили на строке именно этой ветки, не закреплённой компиляторной. Поворот по
аккаунтам уже был написан в общем методе; его просто не звали отсюда (инвариант 10). Ветка заменена вызовом;
два поведения, которых у общего метода не было — блокировка при `jules_source_not_found` и запись
«нет свободного слота» в саму задачу, — перенесены в него. Наблюдено 29.08 02:55:39: очередная задача ушла
строкой `Dispatched task ... to general-pool account fivedmitr-sys`, которую пишет только общий метод.
Поворот на отказе в окне наблюдения не проверен — отказов в нём не было. 38 из 38 тестов зелёные.

**Отозвано в тот же час:** порог отправки пробовали считать по числу аккаунтов, реально нёсших попытку
(`515c6b8`), — вывод верен для закреплённого задания и неверен, пока отбор не поворачивается: за 8 минут
9 заданий снялись с очереди при пороге 2, каждое после отказа на единственном нёсшем их `eneikdru`, шести
принимающим аккаунтам их не предлагали ни разу. Откачено (`38df792`); знаменатель — живой пул. Порог не
чинит отбор.

**Очередь больше не стоит за булевой блокировкой** (бывш. §4.8, `aff5092`). `dispatchQueuedTasks` держал
самопорождённую работу через `if (buildPhase && isSelfGeneratedWork(task)) continue;` — без записи в задачу
и без строки в логе. Замер 29.08: в очереди 26 задач, **клиентских ноль**; клиентский бриф дал 4 задачи, все
`done`; 17 задач самопорождённые с `jules_dispatch_status = NULL` с 28.08 04:07, и ещё 7 «Test Coverage»
ждали ровно этих семнадцати. Блокировка снимается только слиянием клиентских поставок, а клиентских задач в
работе не осталось — событие, которого гейт ждал, не мог произвести никто. Тот же метод 28.08 уже снял
соседнюю такую блокировку с записанным доводом «порядок умеет сказать позже; булево умеет только никогда»;
эта осталась стоять. Замысел перенесён в `queuedDispatchClass`, расширенный до полного порядка на четырёх
структурных классах — компилятор, клиентское, самопорождённое, хозяйственные носители, — булево удалено;
порогов не введено. Наблюдено 29.08 02:24:25–02:25:14: пять из семнадцати задач ушли за 50 секунд, каждая на
свой аккаунт (`dmitriieneik-rgb`, `fivedmitr-sys`, `sixdmitrsix-ops`, `EneikGroup`, `eneikcoworking-ctrl`),
первой — `8b362206`, простоявшая 22 часа. 38 из 38 тестов зелёные.

**Свидетель канала стоит на канале, который используется** (бывш. §4.2, `dc8a586`). Фабрика работает
одноразовым путём, а `markCompilerReached` вызывался только с путей персистентного работника: замер —
`last_compile_reached_at` пуст **у всех строк за всю историю** при 103 компиляторных заданиях. Возврат
бюджета `restoreUnreachedBriefs` читал знак у работника `WISHLIST_COMPILER`, которого никогда не
существовало (в таблице одна строка, `PHILOSOPHICAL_AUDIT`, отставлена 25.08), и потому возвращал 0 всегда.
Шесть брифов с исчерпанным бюджетом и недостигнутым компилятором держали проект в `DECOMPOSING`, а за ними
стояли 25 задач в `queued`. Знак стал `max(знак работника, W)`, где `W` — последний момент, когда Jules
доказанно принял сессию для проекта (монотонен; отказ не пишет внешний идентификатор, поэтому собственная
неудачная попытка брифа не двигает его же знак). Наблюдено 29.08 01:45:48: `restored 6 brief(s) ...
watermark 2026-08-29T00:18:17.420141Z` — те самые шесть и то самое значение, названное в плане заранее.

## 4. Открытые задачи

### 4.3 Безымянное `FAILED_PRECONDITION` — привязка к аккаунту опровергнута

**Что было записано и отозвано.** 29.08 04:00 это стояло в §3 как закрытое: 206 таких отказов, все на
`eneikdru`, ни одного на прочих шести — значит свойство аккаунта. Вывод был сделан на данных, где **никого,
кроме `eneikdru`, и не спрашивали**: общий пул стоял пустым, работал только закреплённый компиляторный путь.
Отсутствие отказов там, где не было попыток, я прочёл как отсутствие условия. Утверждение отозвано.

**Замер 29.08 05:40, когда работа пошла на шесть аккаунтов.** За 20 минут: 19 отправок и **39 безымянных
отказов**, распределение по аккаунтам — `eneikdru` 20, `sixdmitrsix-ops` 7, `fivedmitr-sys` 7,
`dmitriieneik-rgb` 3, `EneikGroup` 2. Условие возникает на каждом аккаунте, которому дают работу.

**Что при этом установлено твёрдо.** Занятость аккаунта, как её считает фабрика, отказ не объясняет — и
объясняет наоборот. Два аккаунта **у потолка** (`dmitrefrem-eneik` 3/3, `eneikcoworking-ctrl` 3/3) не
отказали ни разу: запрос ёмкости их не возвращает, их не спрашивают. Отказывают те, кто **ниже** потолка:
`eneikdru` при 0 из 15, `fivedmitr-sys` и `sixdmitrsix-ops` при 1 из 3. То есть фабрика полагает, что место
есть, и получает отказ.

**Чего это не воскрешает.** Толкование «`FAILED_PRECONDITION` означает исчерпание одновременных сессий»
остаётся отозванным (§5.5): оно было прочитано с интерфейса Jules, а не измерено, и здесь не измерено тоже.
Установлено другое и более слабое: **наша собственная оценка ёмкости не опровергается ничем** — Хартия,
инвариант 15, который прямо называет `jules.max-concurrent-sessions-per-account` оставшейся фиксированной
константой.

**Что разделит.** Накопление пар «занятость в момент попытки → исход». Если доля отказов растёт с занятостью
аккаунта, ёмкость и есть предмет; если не растёт — предмет другой. Пока пар мало: два аккаунта, которые
могли бы дать точку у потолка, до потолка просто не доходят, потому что отбор их туда не пускает. Правку
делать не на чем — это записано как задача замера, а не как предложение кода.

### 4.4 Освобождение аккаунта происходит только по таймеру

Выйти из `api_blocked` можно единственным путём — по выдержке. Ни один механизм не проверяет, годен ли
аккаунт на самом деле. Оператор освобождает аккаунт в Jules, фабрика об этом не узнаёт.

Это вера без опровергателя — то, что Хартия запрещает инвариантом 15. Механизм выдержки при этом
исправен и считает её по истории каждого аккаунта; трогать его не надо, надо добавить путь, которым
свидетельство о годности попадает в запись.

### 4.14 Список для человека копит уже отвеченные вопросы — правка развёрнута, не наблюдена

**Замер 29.08 06:30.** В `needs_human_review` 18 строк, и **8 из них о заданиях, уже `done`** — 44% списка,
который просят читать человека, про работу, которая закончилась. Из них 10 строк написаны отозванной
правкой порога («the budget for 1 account(s)»), и её пострадавшие починились сами: 8 из 10 заданий подобрало
оживление и довело до `done`. Строки остались.

**Правка** (`5036cf3`): при завершении задания через `ClaimService` его строки human-review удаляются —
множество покидается один раз, в данных, а не отсеивается у каждого читателя (§5.9). Область — путь, где
притязание завершается статусом `done`; системные носители, которых другие службы помечают `done` напрямую,
не покрыты, и их строки остаются.

**Не наблюдено.** Чистка срабатывает в момент завершения задания, несущего такую строку; за окно наблюдения
таких не завершилось. 21 из 21 тестов зелёные, включая прямую проверку удаления. Пункт остаётся здесь до
наблюдения.

### 4.15 Два списка «сессия жива», расходящиеся ровно на `stuck`

**Замер 29.08 06:50 по логу и статичной копии.** `Self-healing: Releasing stuck claim for task ... because
session is skipped, failed, or missing` — по три раза на каждую из задач `549a333a` и `88d40685`. У обеих
есть настоящая сессия Jules со статусом `stuck`, внешний идентификатор непуст, `updated_at` — 06:38 и 06:43,
то есть минуты назад. Обе задачи стоят в `claimed` с записью `already dispatched, skipping duplicate`.

**Причина — два списка на один вопрос.**

    JulesDispatchService.ACTIVE_SESSION_STATUSES = {running, queued, revising, pr_opened, stuck}
    ClaimService.isActiveExternalJulesSession    = {running, queued, revising, pr_opened}

Расхождение ровно в одном значении, и именно на нём вертится цикл: самолечение не видит живой сессии и
снимает притязание, задача возвращается в очередь, отправка находит ту же сессию активной и отвечает
«already dispatched, skipping duplicate», притязание берётся снова — и через пять минут снимается опять.
`stuck` при этом не значит «сессии нет»: это состояние, которое фабрика сама выставляет живой сессии, и у
неё есть собственный путь восстановления (`shouldSendStuckRecovery`, `forceUnblockOverflowedSessions`).

Форма та же, что §3 уже записал про `STUCK_CANDIDATE_STATUSES`: второй, независимо поддерживаемый список,
отвечающий на тот же вопрос другим составом. Инвариант 10 Хартии.

**Решение:** `ClaimService` читает существующую публичную константу `ACTIVE_SESSION_STATUSES` вместо
собственной копии. Ни нового механизма, ни числа — одно определение, два читателя.

**Попутно** сообщение называет три причины наугад («skipped, failed, or missing»), хотя предикат знает
только «живой сессии нет». Это стоило замера прямо здесь: по строке было не определить, какое из трёх
условий сработало.

### 4.7 Остальное, замеченное но не разобранное

* **`closed_at` не пишется на терминальном пути.** 385 из 775 строк `jules_sessions` не имеют `closed_at`,

## 5. Ошибочные утверждения — не воскрешать

Все одной формы: вывод выдавался за измерение.

1. **«У рычага TOC ноль разрешённых наблюдений».** Считалось по одной величине, а промоция считает по
   другой. Не поднимается он из-за подменённой величины, а не из-за нехватки данных.
2. **«Фаза декомпозиции должна завершаться».** Не должна и не может: девять сервисов порождают вишлисты
   непрерывно, множество открытых брифов не опустеет никогда.
3. **«Бюджет должен списываться только на отвеченных попытках».** Ломает завершаемость: при вечно
   занятом канале вариантная функция не убывает. Верное решение — различать вердикты, а не менять её.
4. **«Реализовано» без сборки.** Весь массив правок пролежал несобранным; первая же сборка нашла отказ
   компиляции за 90 секунд.
5. **«`FAILED_PRECONDITION` означает исчерпание одновременных сессий».** Взято из надписи в интерфейсе
   Jules, а не из ответа Jules. Существующий тест это опроверг: тот же статус приходит и как
   «Repository access is not ready».
6. **«Миграция V111 навсегда закрепила настройку в базе».** Значение в живой базе — противоположное.
   Миграция присваивает один раз и ничего не запирает.
7. **«`teardown` лаунчера всегда безопасно звать».** Его `success` не означает, что что-то погашено:
   при потерянном указателе в памяти он возвращает успех, не сделав ничего.
8. **«Привязка компилятора к аккаунту — про квоту, значит её можно ослабить».** Ослабление отменено
   оператором: компилятор работает на своём аккаунте и только на нём.
9. **«Отсеять негодные задачи у каждого читателя».** Заплатка: фильтр поставили на один список отбора
   из двух, и дефект вернулся через второй. Негодное обязано покидать множество один раз (V117).
10. **Тесты, которые не могут упасть.** Подстановка на вызов, которого код больше не делает, возвращает
    пустоту — и тест, ожидающий пустоту, проходит, не проверяя ничего. Найдено дважды.

## 7. Порядок работы

Установлен оператором и обязателен:

1. **Диагностика** — измерением, не рассуждением.
2. **Инженерно-философский разбор** — на корпусе: Хартия инвариантов, BARCAN-теги, планы E³ и
