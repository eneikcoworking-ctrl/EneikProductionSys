## 2026-08-27 — находки статического анализа

### 1. Калькулятор укоренённости вырожден

`FeatureService.calculateEpistemicEntrenchment` реализует `EE = 0.55·C + 0.45·K`. План E³ задаёт
`EE = 0.40·C + 0.35·K + 0.25·E_EMS`. Член EMS отсутствует, оставшиеся веса перенормированы:
0.40/0.75 ≈ 0.53, 0.35/0.75 ≈ 0.47.

Главный путь создания фичи — `resolveOrCreateFeatureId`, строка 52 — вызывает формулу как
`calculateEpistemicEntrenchment(null, null)`. Умолчания внутри: `null → complex → 35`,
`null → one-dimensional → 60`. Отсюда

    EE = 0.55·35 + 0.45·60 = 19.25 + 27 = 46.25

— **константа для каждой фичи, созданной этим путём**, а путь вызывается компилятором на каждую
компилируемую задачу.

**Следствие первое.** Предпорядок `≤_EE` вырожден. Сжатию AGM `K ÷ ¬φ` нечем упорядочивать, и
отсекается произвольное — идентичность Леви работает вхолостую.

**Следствие второе.** При порогах `≥75 → CORE`, `≥45 → CONTRACT` константа 46.25 даёт `CONTRACT`,
обойдя границу на 1.25. `EpistemicLayerInvariantGate.check` не делает ничего, если слой не
`PERIPHERY`, и возвращает `passed=true`. Гейт не может сработать ни разу, и его непримение
неотличимо от чистой проверки — ACP-105.

Верный ответ дал только запрос к живым таблицам — с него следовало начать.

### Отдельная методическая ошибка: замер живой базы

Числа скакали (323 против 0), потому что я копировал файл, в который в этот момент писал самопроизвольно
поднявшийся бэкенд. Копия живого H2-файла рвана по определению. За 26 минут такой работы файл вырос до
2155 МБ.

**Правило:** замер базы достоверен только при остановленном сервисе, и лучше — из статичной копии с
проверенным md5. Все итоговые числа выше получены так.

### Ещё раз про хук компактификации

`SHUTDOWN COMPACT` сжимает 226.8 МБ до 62 МБ — механизм рабочий. Но при штатной остановке он не
выполняется ни разу: `DB_CLOSE_ON_EXIT=TRUE` закрывает базу раньше, чем Spring доходит до `@PreDestroy`,
и в логе каждый раз `The database has been closed`. Сжатие сегодня делалось вручную. Флаг и хук
конфликтуют — чинится снятием `DB_CLOSE_ON_EXIT` либо переносом в `SmartLifecycle` выше DataSource.

### Состояние на момент записи

Фабрика работает: `health` 200, один проект (пятидесятый, active), база 61.7 МБ, отказов `read 0` нет,
свободной памяти 953 МБ. Пока-ёкэ отгружен и покрыт тестами, но на живых данных не срабатывал ни разу —
в логе только сверки. CI клиента остаётся красным: 15 падений с `401`, это следующая цель конвейера.

## 2026-08-28, полдень — почему хук сжатия не работал: одна строка в Dockerfile

### Опровержение двух моих прежних записей

Выше в этом журнале дважды записано, что `SHUTDOWN COMPACT` не выполняется из-за конкуренции хуков
завершения: якобы `DB_CLOSE_ON_EXIT=TRUE` заставлял H2 закрыть базу раньше, чем Spring доходил до
`@PreDestroy`. **Это неверно.** Обе записи оставляю, помечая опровергнутыми.

Настоящая причина — в точке входа образа:

    ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

Без `exec` первым процессом контейнера остаётся `sh`, а `java` — его потомок. SIGTERM при
`docker compose stop` приходит в `sh`, который его не передаёт. Java не получала сигнала **никогда**,
Spring ни разу не закрывал контекст, `@PreDestroy` не выполнялся, H2 не закрывалась чисто, и по
истечении отсрочки Docker убивал контейнер.

Признак лежал на поверхности всю сессию: каждая остановка давала `Exited (137)`, то есть SIGKILL, и в
логе не было ни одной строки о закрытии контекста. Я читал `137` как «контейнер остановлен» и не
спросил, почему не `143`.

### Проверка после правки

`ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]`. Наблюдения при контролируемой остановке:

| | До | После |
| :--- | :--- | :--- |
| PID приложения в логе | 7 | **1** |
| Код выхода | 137 (SIGKILL) | **143** (SIGTERM) |
| Строка о сжатии | отсутствовала | `H2 store compacted on shutdown in 1518 ms` |
| Размер базы при остановке | рос | **30 208 000 → 17 317 888 байт** |

Впервые за сессию база сжалась сама.

### База ушла с файловой шары Windows

Перед этим H2 начала терять **записи**: `Writing to FileChannel failed`, 16 раз за три минуты, при
43 ГБ свободного диска и файле 62 МБ. Тот же источник, что весь день давал `read 0`, рваные копии и
залипшие блокировки. Живая база перенесена на том Docker (`eneikproductionsys_eneik-db`,
`/var/lib/eneik`); `./data` остался смонтированным для логов, design-assets и бэкапов — они переносят
разовый сбой, журнал предзаписи не переносит.

Побочный эффект, который стоит отметить: старт бэкенда ускорился со 157 секунд до 14.3.

### Что осталось незакрытым

- **Доставка не верифицируется:** `NEVER ASKED=365 of 365 tasks`, каждый цикл. Ни одна задача ни разу
  не спрошена о доставке.
- **TOC в теневом режиме:** `subordination says deny … Effective decision: allow`, шесть раз за старт.
  Ограничение опознано, затор зафиксирован пять раз — и загрузка продолжается.
- **Пока-ёкэ не срабатывал на живых данных** — ни одного `POKA-YOKE REFUSE`.
- **Ни одной фичи в CORE:** `E_EMS = 0` у всех, потолок 67.5. Гейт слоёв защищает пустой слой.

### Общий урок сессии

Все мои ошибки сегодня имели одну форму: **объяснение вместо измерения.** «Пятидесятого нет в базе» —
из одного эндпоинта при живых 323 задачах. «Хук не работает из-за конкуренции хуков» — трижды, при
`Exited (137)` в каждой строке. «Пять раз рвётся интероп» — при том что не хватало памяти, и оператор
увидел это сразу. «Заслон поставлен» — при том что он стоял в одной точке из десяти.

Каждый раз признак был доступен, и я его не прочёл, потому что уже располагал объяснением.
